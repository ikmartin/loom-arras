# 11. The AI layer

Loom is not about AI; the AI layer is an optional client of loom. This chapter specifies that client: what `ai/` contains, how an agent is oriented, what a session is, what the modes are and what they must produce, how an agent writes annotations, how its output reaches the quilt, and what it may never do. The full text of the orientation document and the mode templates is in Appendices C and D.

## 11.1 Three rules

**[decided]**

1. Nothing in loom's core imports a model SDK, holds a credential, or calls a hosted API. Models are reached through local interfaces only (P8, P9): an agent the author started, or the author's own command, which `loom serve` may run for a turn (11.9).
2. Every AI operation consumes only what loom already produces for humans (bundles, `status`, the manifest, digests) and writes only to its own directory and to proposals. Nothing an agent produces enters the paper or the ledger without a human copying or accepting it.
3. The layer is absent from a quilt unless the author asks for it (`loom ai init`).

## 11.2 Layout

**[decided]** Created by `loom ai init`, beside `.loom/sessions/`, which sessions write (11.4):

```
ai/
  README.md                which files are the author's to edit and which are regenerated
  orientation.md           where an agent is: the quilt, its layout, its commands (Appendix D)
  rules.md                 how to work: standing rules, the contracts, the blocks (Appendix C)
  formatting.md            how to write what the author reads in the viewer (11.3)
  .loom-modes-version      one line per tracked file, `<name>.md <sha256>` of the shipped text, so upgrade can tell edited from unedited
  modes/
    audit.md  referee.md  review.md  simplify.md  question.md
    quick.md  draft.md  ingest.md  brainstorm.md
.loom/sessions/            not written by `loom ai init`; see 11.4
  index.jsonl              append-only: created, renamed, purposed, resumed, closed, deleted
  active                   the active session's id
  s-2026-09-16-0001/       one directory per session, made when it first has something to hold
    run.log                every loom command invoked with --session (automatic)
    inbox.jsonl            the session's chat: every message either party said, in order
    attached.json  cursors/   who is attached, with a heartbeat, and how far each reader has read
    agent.json  agent.log  a launched turn's state and output (11.9)
    (annotations go to annotations/log.jsonl at the quilt root)
    plan-rl-0019.md        the author's plan for a draft
    referee-rl-0004.notes.md
    referee-rl-0004.check.py
    draft-rl-0019.tex      a complete node for the author to read and paste
    proposal-rl-0004.diff
CLAUDE.md                  generated at the quilt root; see 11.3
AGENTS.md                  generated at the quilt root; see 11.3
.claude/settings.json      generated permission settings, written with ai/; see 11.8
.codex/rules/loom.rules    the same, as Codex's rules; see 11.8
.claude/skills/loom-<mode>/SKILL.md   optional generated skill stubs, one per mode; see 11.12
.claude/commands/<mode>.md            optional generated slash commands for target-taking modes; see 11.12
```

`ai/` is visible, not hidden: humans read and edit the mode templates. The `.gitignore` that `loom init` writes leaves out each session's `attached.json`, `cursors/` and `agent.*`, which are this machine's runtime state; everything else under `.loom/sessions/` is committed, because review records and drafts are shared with coauthors. `loom ai init` refuses to run when `ai/` exists; `loom upgrade` is the refresh. Session directories, fetched sources, and `.claude/` are never scanned as quilt text (DR-70).

**[decided]** `loom upgrade` refreshes `loom.sty`, `ai/README.md`, the root files, and whichever of the permission settings and stubs exist, unconditionally, and refreshes a **tracked document** — `ai/orientation.md`, `ai/rules.md` and every mode file — only if its hash still equals the shipped version recorded in `.loom-modes-version`; an edited one is left alone and reported, with the new shipped version written beside it as `<name>.md.new` for the author to merge, and its recorded hash kept so a later upgrade still recognises the edit. `loom doctor` runs the same comparison without writing and warns on what an upgrade would refresh, and on an edited file whose newer shipped version is not beside it yet (DR-288-ikmartin). **[decided]** The `.new` convention (M6). **[decided]** The orientation is tracked (DR-170): it is the first document an author tailors — a standing rule about this quilt, a mode the agent should not reach for — and it was the one shipped document with no policy at all.

## 11.3 Orientation

**[decided]** Two layers, so that any agent finds the rules on its first action without loom assuming which agent it is.

1. Static: `ai/orientation.md`, `ai/rules.md` and `ai/formatting.md`, generated by `loom ai init`, refreshed by `loom upgrade`, and printed together by `loom ai orient`. `formatting.md` says how to write what the author reads in the viewer: `quilt:` and `cited:` links printed by `loom link` and checked when posted, mathematics for MathJax, proposed text and proposed dependency edges as suggestions (DR-271-ikmartin). Its contents are Appendix D: what a quilt is, the layout with read/write permissions per directory, the source contract in one page, the ledger and what states mean, the commands an agent uses and when, the write policy, the modes and their contracts, context economy.
2. Dynamic: `loom ai orient [--session SESSION]` prints the static document followed by what only the moment knows: the quilt's name, prefix, and masters, the `status` summary line, the lint error count, undigested citekeys, the open sessions with the active one marked, and, with `--session` (`LOOM_SESSION` is its default), the last twenty messages of that session's chat, its `run.log`, and its file list, so a later sitting picks up the conversation (M6, DR-264-ikmartin).
3. Vendor files: `CLAUDE.md` and `AGENTS.md` at the quilt root, which carry one line of loom's and are otherwise the author's (DR-151): "This directory is a quilt managed by loom. Before doing anything, run `loom ai orient` and follow it. Write only under your session's directory in `.loom/sessions/`." **[decided]** One instruction, not two: `loom ai orient` prints both standing documents, because "run this and also read that" has a second half that fails silently where a command does not. Claude Code reads the first, Codex the second. **[decided]** Both stay identical one-sentence copies: Claude Code supports `@path` imports, but `AGENTS.md` readers may not, so neither file imports `ai/orientation.md` by reference (M6).

## 11.4 Sessions

**[decided]**

1. **[decided]** A session is a stretch of work on the quilt, which a person and an agent may share (DR-199). It has a **stable id**, `s-YYYY-MM-DD-NNNN`, minted once and never changed, which is what a record, a URL and its directory use; and a **title**, the author's own words, changed whenever they like with `loom session rename` or `loom ai name`, and never an address. `.loom/sessions/index.jsonl` is append-only — `created`, `renamed`, `purposed`, `resumed`, `closed`, `deleted` — and the state that stands is the replay. A **round** is the span between an opening and the next close or resume, which is what "changed since last time" measures. One session is active at a time, named in `.loom/sessions/active`; writing with nothing active opens one, for a person and an agent alike. Deleting is a tombstone; `loom session delete --purge` really erases, is CLI-only, counts what it will remove and asks first. **[decided]** Loom does not launch the agent for a sitting. `loom ai init` writes the one line in `CLAUDE.md` and `AGENTS.md` that tells an agent to run `loom ai orient`, so a session starts by typing the agent's own command, and `loom ai start` is what the agent runs when the author asks it to begin a session. Launching it from loom for a whole session meant owning a vendor's argv convention and holding the process tree, which is the runner declined as WQ-15 in miniature (DR-149, retiring DR-72). What loom may do is start the author's own command for **one turn** when a message waits (11.9, DR-273-ikmartin).
2. A session has no mode. Modes are applied inside it, any number, in any order.
3. Everything the session produces lives in its directory under `.loom/sessions/<id>/`, named by mode and target: `referee-rl-0004.notes.md`, `draft-rl-0019.tex`, `proposal-rl-0004.diff`, `ingest-Man12.tex`.
4. `run.log` is written by loom — What it did reads it (15.3.9): every command invoked with `--session SESSION` (`LOOM_SESSION` is the default, and `loom annotate` uses the active session when neither is given) appends a line, time then command; `source`, `compile`, `annotate`, `status`, `search`, `deps`, `unravel`, `lint`, `id`, `new`, `ai orient` and `ai annotations` log themselves. The agent's account of its work goes in the chat: after each significant exchange it says, with `loom session say`, what was asked, what it did, what it decided and what remains. The orientation asks for that; loom guarantees `run.log`. `loom annotate` logs after it has acted, one line per annotation it made or changed, with the verb as used and the annotation's id after an arrow — `loom annotate sh-0009 --quote --kind objection → a-2026-09-16-0001`, `loom annotate --resolve a-… → a-…` — so the record says which annotation each line was; a refused annotation is not logged (DR-277-ikmartin).
5. **[decided]** `loom ai orient --session SESSION` rejoins a session: it prints the orientation, the live state, the last twenty messages of that session's chat and its `run.log`, which is what a later sitting resumes from. There is no separate attach command, because that is what rejoining is. A session is named by its id, its title, or part of either, and every command that takes `--session` resolves it the same way: the id exactly, then the title exactly, then a unique id suffix, then a unique part of a title. An ambiguous value names its matches and refuses rather than guessing, as `refs resolve` does with candidates; a value matching nothing is an error. **[decided]** Resolving a session never creates anything (DR-167). **[decided]** `loom id` and `loom new` take `--session` and log themselves like the rest: allocating an id is the one call whose result the author must later trust, and its absence from the log was a gap in provenance. `loom check` and `loom history` do not, being whole-quilt queries rather than acts on a result. **[decided]** `loom session list [--all]` lists them, open by default, and `loom ai annotations --session SESSION` prints what a session has annotated, which is what a re-check needs in order to resolve and edit its own findings by id. **[decided]** `--json` carries the whole finding — `message`, `payload` and `placement` as well as the id, the target and the quote — so a second pass can tell a finding it already made from a new one without reading the log itself, which is the contract 0.10 was built to support (DR-168). Withdrawn findings are left out unless `--all` is given, which also prints why each was withdrawn; `--severity`, `--kind` and `--status` filter as they do on `loom status`.
6. Discard (7.8) marks the session's records ignored without deleting anything, and closes the session: a sitting whose every finding is dismissed has no business in the list of what is open.
7. **[decided]** **Dispatch is a mailbox** (DR-203, DR-195). A session carries `inbox.jsonl`: append-only, **read and never consumed**, a cursor per reader and a sequence number per event, so a message survives being read, a second reader sees it too, and an agent that crashed resumes where it was. `loom session send "…"` posts for a person and `loom session say "…" --as NAME` for an agent, `loom session watch [ID]` tails for a person, and `loom session next --wait N --json` parks for an agent and returns the moment something lands, so one call is one turn and latency is an append and a wakeup. Loom appends and a parked reader wakes; **nothing is assigned** — two attached agents both see everything and neither is handed a task, which is the honest behaviour for a tool that is not orchestrating. The one thing loom may start is the author's own agent for a turn, where the quilt allows it (11.9). A message lands whether or not anybody is listening, and the surface that posted it says which: refusing would lose what was typed for a reason the browser cannot fix. Presence is `attached.json` — who, kind, pid, heartbeat — and a stale heartbeat (90 s) means detached; a parked reader renews its beat every 30 s rather than on every wake, since `loom serve` rebuilds when the file changes. **[decided]** **The inbox is the transcript** (DR-264-ikmartin): the one record of the conversation, written only by the two parties — the person through the viewer's input or `send`, the agent through `say` — and never by loom, with no journal beside it. Posting takes a lock, so two writers never draw the same sequence number, and `loom serve` reads it by an index of where each event starts, so a poll reads only what is new (DR-265-ikmartin). The viewer's Chat reads new messages from that poll, so `loom serve` does not rebuild the manifest when a message lands (DR-267-ikmartin). **[decided]** **What the person marks goes with their next message** (DR-272-ikmartin). A message carries its sender's own annotations and replies in that session that no earlier message carried — another person's wait for that person's next message, and the agent's own never go back to it — each whole: its body, the words it is on, what it proposes, its severity. `session next` prints them beneath the message, and the viewer's tray previews them in the same words before they are sent (`GET /_api/packet`). A message may be those annotations alone: `loom session send` with no text, or the viewer's send with nothing typed. **A link an agent writes is checked when it is posted**: `loom session say`, and `loom annotate` under an agent's name, refuse one that names nothing the viewer shows, naming it, and `loom link` prints a correct one (DR-268-ikmartin).
8. Sessions publish as threads in the manifest (specs/manifest.md §10): every session becomes a thread with its title, `run.log` as the log, attachments by file name and kind, participants from the annotations' authors, and targets from the annotations. Each thread has a search entry (M6). The conversation is not in the manifest, which every viewer polls: the build writes each transcript beside it in pages of a hundred events (specs/manifest.md §10.1), which a viewer reads with or without a publisher running (DR-264-ikmartin).

## 11.5 Modes

A mode is a prompt template in `ai/modes/` with an input contract (what loom hands the agent) and an output contract (what the agent must leave in its session's directory). The templates are adapted from the author's existing review rules; their full text is Appendix C. Chat-specific parts of those rules (KaTeX formatting, the variable-definitions preamble, the intuition block) do not transfer, because outputs are files; the modes and blocks do.

**[decided]** The modes, their inputs, and their outputs:

| mode | purpose | input (via `loom source KEY --closure` and context) | required output in the session |
|---|---|---|---|
| audit | load-bearing audit: hypothesis ledger, citation ledger, self-containedness, sharpenings, uses-ledger | the closure; ledger states of the closure; digest entries for cited results | `audit-<key>.notes.md` with the ledgers; annotations via `loom annotate` for each finding |
| referee | hostile review: gaps, worked examples, counterexamples, verdict | the closure; same context | `referee-<key>.notes.md`; annotations via `loom annotate` |
| review | a referee reading to improve rather than reject: citations, hypotheses, errors, wording, each finding graded by severity | the closure; same context | `review-<key>.notes.md`; annotations with `--severity`, and `--payload` where text is proposed |
| simplify | shorter text with identical mathematics | the closure | `proposal-<key>.diff` (unified diff against the node file) plus `simplify-<key>.notes.md` listing each change with its license |
| question | answer a question about a key or the quilt | the closure or `status --json` | `question-<slug>.md` |
| quick | a short, durable answer: worth re-reading in a week, not worth a document | as question | `quick-<slug>.notes.md`, `[answer]` alone |
| draft | write a complete node from a plan the author supplies | the plan, the closure statements (`loom source --closure` of the intended dependencies), the skeleton from `loom new --print` | `draft-<id>.tex`, a complete node file obeying the source contract |
| ingest | produce or complete a digest | the work's PDF, which `loom refs path CITEKEY --pdf` locates (or its text), or an extracted digest to complete, plus the digest chapter's format | `ingest-<citekey>.tex` (a complete digest) or `proposal-<citekey>.diff` |
| brainstorm | explore a topic before anything is proved: make the author's idea precise, compute small cases, search the digests, record what was tried | `status --json`, `search --json`, the closures of the definitions the topic touches, digest overviews, the outline master via `assemble` | `brainstorm-<slug>.notes.md` with `[summary]`, `[candidates]`, `[dead-ends]`, `[known-results]`, `[open-questions]`; `draft-cand-*.tex` per candidate; `brainstorm-<slug>.check.py` |

Rules common to every mode:

1. **[decided]** The agent obtains context through loom commands, not by reading directories wholesale: `loom source KEY --closure` for a key, `loom status --json` for the quilt, `loom search` for ids, `loom deps` and `loom unravel` for the graph. The orientation document says so.
2. **[decided]** Review findings are annotations, one `loom annotate` call per finding (or one `--batch`), anchored by `--quote` to the sentence they concern; the notes file summarizes. This is the mode's output contract, and it is what makes findings appear as marks on the text (15.3.1). **Since 0.11 the notes file is read as well as kept**: the publisher parses its bracketed headings into blocks and links each finding's trailing annotation id to the annotation, so the viewer can show the report beside the document and scroll one to the other (DR-158). Nothing about how a mode writes changes — the brackets and the trailing ids were always the contract, and were simply never read.
3. **[decided]** The audit mode's uses-ledger: for each proof, list facts the argument invokes that no `\ref`, `\uses`, or matched citation names (candidates for `\uses` entries or new nodes), and `\uses` entries the argument never consumes. Each is an annotation anchored to the invoking sentence.
4. **[decided]** Nothing a mode produces is applied. A drafted node is pasted by a person and a digest is not written by an agent at all (11.7); proposals are applied by a person with their own tools.
5. **[decided]** Every mode file begins with a "Before you begin" block stating the write policy, every notes file begins with a `[summary]` block, and every mode file ends with the output contract as a checklist the agent copies into the notes and ticks.
6. **[decided]** Proposals and drafts are compiled before promotion with `loom compile KEY --with FILE` and `loom compile --draft FILE` (12.5); a mode that produces LaTeX reports the compile result in its notes.
7. **[decided]** An agent that needs a whole document in context uses `loom source PATH`, which prints it flattened, every `\input`, `\include` and `\nest` expanded in place and nothing written. Masters are not keys, so the closure form does not apply to one; and `loom linearize`, which flattens a document into a file, supersedes what it flattened and is denied to the agent (11.5), so until `loom source` took a path there was no command an agent could use for this (DR-155).

## 11.6 Annotations from agents

**[decided]** `loom annotate TARGET "message" --quote TEXT --kind KIND --as NAME [--session SESSION]` is the only way an agent records a finding. The kind is one of five — `objection`, `suggestion`, `question`, `citation`, `note` — and defaults to `note`, so a finding says `--kind`; `--severity` grades an objection or a suggestion and is refused on the rest (7.4.2). A claim that holds for the node only as read in one document says so with `--in DOC` (7.4.3 item 7), and a re-check answers its own earlier finding with `--edit`, `--resolve` or `--discard` by id rather than a new annotation. Loom computes the anchor, records the target hash, appends a `created` event to `annotations/log.jsonl` with the declared name as the author and the session (the active one unless `--session` names another) as where it belongs, and appends to that session's `run.log`. An agent never writes the log by hand; a hand-written line is not a review record (`loom lint` and `loom check` report `loom:foreign-annotations`, warning, for a file in the record locations that fails validation, **[decided]** DR-52 and DR-61). `--batch` reads JSON lines (`target`, `message`, `quote`, `kind`, `reply`, `resolve`, `edit`, `discard`, `severity`, `payload`, `placement`, `page`, `box`, `in`) from stdin so forty findings are one process.

**[decided]** An agent annotates **a page of a cited work** the same way it annotates a key (DR-209): `loom annotate CITEKEY "message" --page N --quote "exact text from loom refs page"` — the quotation must be on that page, and loom refuses one that is not, naming `loom refs page CITEKEY N` as the text to quote from — or `--box x0,y0,x1,y1` for a rectangle, in points with the origin at the top left, which `loom refs locate` prints for any phrase. The note targets the work by its identifier, lands in the agent's session, and appears in `loom ai annotations` with the citekey and the page. It is the reading counterpart of `loom refs propose`: a proposal claims a result is on the page, a note says something about what is there.

An agent may `--resolve` its own earlier annotations after a re-check, and may reply to a person's.

## 11.7 Nothing an agent writes is copied into the quilt

**[decided]** **There is no promote command** (DR-173). `loom ai promote` existed to copy a digest an agent had typed into `digests/`, and an agent no longer produces digests: `loom digest extract` makes one mechanically from the cited paper's LaTeX source, and ingest mode checks that output against the paper rather than authoring a replacement for it. A typed transcription is unfalsifiable; an extracted one can be diffed against its source, which is the whole reason a reader can trust a digest without opening the paper.

**[decided]** A work that exists only as a PDF is not typed into a digest either; it is **read and proposed** (DR-178). The agent quotes the page's own words through `loom refs page` and `loom refs propose`, loom checks the quotation against the page before storing anything, and the proposal waits in `digests/<citekey>.proposed.tex`, which nothing inputs, until the author verifies it against the page (8.14). This narrows DR-173 rather than reversing it: what DR-173 ruled out is an *unanchored* transcription, and a proposal is anchored. For a work with a LaTeX source, a result the extractor missed is quoted from the source (`--source-file`), never from the PDF's text layer.

**[decided]** A drafted node is not promoted either (DR-140). The author reads it in arras, copies it, and pastes it where they decide, taking an id from `loom id --next` or letting `loom id FILE` write one. Pasting is more intentional than a command that files a stranger's lemma into `nodes/`, it is the same act as accepting any other suggestion, and it needs no machinery.

## 11.8 Write policy and permissions

**[decided]** An agent writes only under its own session's directory in `.loom/sessions/` and under `build/`. `.loom` is therefore no longer denied wholesale: `.loom/history` and the two record files are named instead (DR-199). Everything else in the quilt is read-only to it, and **the commands it may run are an allow-list, not a list of prohibitions** (DR-173): one table in `ai/layout.py` names them, `ai/rules.md`'s `Never` section is generated from it, and `loom ai init` generates `.claude/settings.json` and `.codex/rules/loom.rules` from the same table, for every quilt with an `ai/` whichever tool its person uses, and `loom upgrade` writes either when it is missing (DR-289-ikmartin): `.claude/settings.json` from it, allowing the table's commands outright — an agent `loom serve` starts for a turn cannot answer a prompt, and the Claude preset passes the file with `--settings`, since Claude Code ignores a project's own settings until someone accepts its trust dialog there — and path rules as `Edit` only, the rule Claude Code matches for every file-editing tool (DR-275-ikmartin); and denying every leaf command the table does not admit and every directory outside the two it may write. A command added to loom later is the author's until the table admits it. **[decided]** **The table is loom's, and a quilt does not change it** (DR-283-ikmartin, provisional): it is rendered for each tool loom knows — `.claude/settings.json`, and `.codex/rules/loom.rules` as Codex's command-prefix rules, with no counterpart for the path rules — and `loom upgrade` rewrites both; a person's own rules go in their tool's local file, which loom never touches. A launched turn and the person's own session in the same quilt run under the same rules, and `agent.log` opens with where the turn's came from. Claude Code's deny rules take precedence over allow rules and an allow-only whitelist cannot be expressed, which is why the generated file still enumerates refusals (DR-71) — but it enumerates the complement of one list rather than a list somebody remembered to extend. The hand-written pair had drifted by seven commands, `loom upgrade` and both spellings of `loom canonize` among them, so `loom canonise` walked through the deny on `loom canonize`. `loom upgrade` regenerates the file. Codex has no project-level permission file loom could write; for it the write policy rests on `AGENTS.md` and `loom ai check` (M6).

**[decided]** The author's verbs refuse an **agent identity**, not an environment (DR-185, moved by DR-203). `loom accept`, `loom refs verify`, `loom refs discard`, `loom refs unreadable` and `loom refs forget` refuse when the declared writer is an agent, whichever door it came through. **Identity is declared, not sniffed**: `--as` or `--author` names the writer, an agent is asked to include `Agent` or `AI` in its own name, and an explicit identity wins — so an author who says who they are is the author even from a shell an agent is running, and a marker with nothing declared refuses rather than guesses. The guard had to move because both things it keyed on stopped meaning what they meant: a session is now shared by a person and an agent, and the write API is no longer only the author's own click. **An agent asks for one of these verbs by writing a `suggestion` on the result**, which surfaces where the author verifies anyway; there is no request object, deliberately, because one becomes a queue that nags and an agent that "requested verification" is a summary away from reporting that it verified.

After any sitting, `loom ai check SESSION` (**[decided]** a command of its own, M6; resolved as 11.4 describes) reports files outside the session's directory, `annotations/`, `build/`, and `.loom/` whose mtime is later than the current round's opening, as `loom:agent-wrote-outside-run` (error), exiting 1; the index records whole seconds, so a file written in the round's first second is not reported. It does not revert.

## 11.9 Triggers

**[decided]** **A message may start the author's agent for one turn** (DR-273-ikmartin, DR-274-ikmartin). Where `config.toml` says `launch = true` under `[ai]` — off unless the author says so, at `loom init --launch-agents` or later — `loom serve` checks each open session every second. When a person's message lies after the configured agent's cursor — an agent's never starts one — no other agent is attached, and no turn is running there, it runs the command in `ai/ai-config.toml` (the person's own; their user config's `[agent]` table under it, key by key): `start` the first time, `resume` after, placeholders `{session}`, `{agent_session}` (a conversation id loom chooses at the session's first turn and keeps in `agent.json`; `resume` is used only for a conversation a turn finished in), `{prompt}` and `{quilt}` filled item by item and never through a shell. The prompt asks for one turn: orient, read with `next --wait 0`, answer with `say`, stop; after a stop, it also says the author stopped the last turn and not to carry on with it unasked. The turn runs in its own process group with `LOOM_SESSION` set, so its commands land in `run.log`; its state is `agent.json` and its output `agent.log`, and a failed turn is not retried until the next message. **Starting, `loom serve` takes every inbox it finds as answered** — before its socket accepts a write, so a message sent while the first build runs does start a turn — and ends any turn a previous server left running, recording it stopped, so turning launching on never wakes old sessions; a SIGTERM stops it as Ctrl-C does, ending its turns (DR-278-ikmartin). **Loom refuses to run an `ai-config.toml` that git tracks**: that is a command whoever committed it wrote. The Chat reports the turn, or what keeps it from starting, and offers stop (15.3.9), and `loom agent check` tests the configuration without running it; `loom doctor` reports what it finds. `loom init` asks which AI the person uses — Claude, Codex (a preset nobody has run yet), another, none — and writes the file, installing the layer for the first two; it says plainly whether agents will be launched and where to change that. This is not the runner below: loom owns no argv convention, holds no process beyond the turn, calls no model and forwards nothing.

**[decided]** In interactive use there is no queue, and nothing runs unattended but such a turn. `loom status` is the to-do list: undigested citekeys are the ingest trigger; stale accepted keys and draft keys are the review triggers; the orientation document tells the agent to run `status` first and propose work from it. A runner contract was specified for a non-interactive future (`loom ai run --queued`, `--auto`) and has been declined: loom prepares an agent's context and records what it did, and supervising the process would mean holding credentials and tracking vendors' flags for three features that were never built. `specs/runner.md` is kept as a declined design and its `[ai] runner` config key is withdrawn (`docs/work-queue/closed.md`, WQ-15).

## 11.11 An example session

```
$ claude
```

The agent reads `CLAUDE.md`, whose one line tells it to run `loom ai orient`. That prints the orientation, the quilt's live state and the open sessions. The author asks for a referee pass on `rl-0004`, so the agent runs `loom ai start "Referee of rl-0004"`, which opens a session, makes it active and prints its id; from the live state it sees `rl-0004` is draft and never reviewed. It runs `loom source rl-0004 --closure`, reads it, applies the referee template, and issues:

```
loom annotate rl-0004 "The hypothesis 'quasi-compact' is not stated; rl-0002 assumes it." \
  --quote "Let $\iota$ be an embedding" --kind objection --as "Referee Agent"
loom annotate rl-0004/proof "Domination of two embeddings by a third is asserted, not proved." \
  --quote "Two embeddings are dominated by a third" --kind objection --as "Referee Agent"
loom annotate rl-0004/proof "Consider citing Man12 Prop 3.2 here." \
  --quote "the pullback commutes" --kind suggestion --as "Referee Agent"
```

It writes `referee-rl-0004.notes.md` with the six blocks of the referee mode and says in the chat what it found. The author opens arras: three marks on the node page, the badge reads "draft · 2 open objections, 1 suggestion". The author fixes the proof, asks the agent to re-check; it resolves its second objection and writes `loom annotate rl-0004/proof --kind note --as "Referee Agent"`. The author accepts.

## 11.12 Vendor wrappers: skills and commands

**[decided]** The mode files are the content; anything vendor-specific only points at them. Where an agent supports it, `loom ai init --skills` generates two kinds of wrapper so that a mode is reached without the author naming a file (DR-71):

- A skill stub per mode, `.claude/skills/loom-<mode>/SKILL.md` for Claude Code: frontmatter with `name: loom-<mode>` and a trigger description ("when the user asks to referee, review, or find gaps or errors in a node of this quilt"), and a body of a few lines: run `loom ai orient` if not yet done, and `loom session list` to see the open sessions, `loom ai start "a name"` opening a new one; writing lands in the active session and `--session` names another; read `ai/modes/<mode>.md` and follow it exactly; begin with the mode's first command; and, for the target-taking modes, "The target is `$ARGUMENTS`". It contains no block definitions and no procedure.
- A slash command per target-taking mode (`audit`, `referee`, `review`, `simplify`, `draft`, `ingest`), `.claude/commands/<mode>.md`: a `description` and `argument-hint: KEY` in its frontmatter and a short paragraph: apply `ai/modes/<mode>.md` to `$ARGUMENTS`, with the same lines on sessions as the skill. Claude Code documents commands as a legacy form of skills, so the skills carry the target and the commands only wrap them.

Rules: stubs are regenerated by `loom upgrade` and never edited by hand; the layer must work with every stub deleted (the orientation document lists the modes by name for agents with no such mechanism, Codex among them); a stub that duplicates mode content fails `test_ai_init_skills_generated_pointer_only`. **[decided]** The locations and frontmatter were verified against Claude Code's documentation at implementation time (DR-71); the shipped templates live at `src/loom/assets/ai/vendor/claude/` (`SKILL.md`, `command.md`), beside the root files' text in `vendor/root.md`; the permission settings are generated from the table in `ai/layout.py` (11.8).
