# 11. The AI layer

Loom is not about AI; the AI layer is an optional client of loom. This chapter specifies that client: what `ai/` contains, how an agent is oriented, what a run is, what the modes are and what they must produce, how an agent leaves comments, how its output reaches the quilt, and what it may never do. The full text of the orientation document and the mode templates is in Appendices C and D.

## 11.1 Three rules

**[decided]**

1. Nothing in loom's core imports a model SDK, holds a credential, or calls a hosted API. Models are reached through local interfaces only (P8, P9).
2. Every AI operation consumes only what loom already produces for humans (bundles, `status`, the manifest, digests) and writes only to its own directory and to proposals. Nothing an agent produces enters the paper or the ledger without a human copying or accepting it.
3. The layer is absent from a quilt unless the author asks for it (`loom ai init`).

## 11.2 Layout

**[decided]** Created by `loom ai init`:

```
ai/
  README.md                which files are the author's to edit and which are regenerated
  orientation.md           what a quilt is and how to work in it (Appendix D)
  .loom-modes-version      hash of the shipped mode files, so upgrade can tell edited from unedited
  modes/
    blocks.md              the block definitions shared by modes (Appendix C)
    audit.md  referee.md  simplify.md  question.md  quick.md  draft.md  ingest.md
  runs/
    2026-09-16T14-02-referee/     one directory per run
      run.toml             created, slug, agent session id if known, discarded
      run.log              every loom command invoked with --run (automatic)
      thread.md            the agent's journal (requested)
      annotations.json     written by loom comment --run
      bundle-rl-0004.tex   copied by loom bundle --run (gitignored: regenerable)
      plan-rl-0019.md      the author's plan for a draft
      referee-rl-0004.notes.md
      referee-rl-0004.check.py
      draft-rl-0019.tex    a complete node awaiting promote
      proposal-rl-0004.diff
CLAUDE.md                  generated at the quilt root; see 11.3
AGENTS.md                  generated at the quilt root; see 11.3
.claude/settings.json      optional generated permission settings; see 11.8
.claude/skills/loom-<mode>/SKILL.md   optional generated skill stubs, one per mode; see 11.12
.claude/commands/<mode>.md            optional generated slash commands for target-taking modes; see 11.12
```

`ai/` is visible, not hidden: humans read and edit the mode templates. `loom ai init` also appends `ai/runs/*/bundle-*.tex` to `.gitignore`; everything else under `ai/runs/` is committed, because review records and drafts are shared with coauthors.

**[decided]** `loom upgrade` refreshes `orientation.md`, `README.md`, the vendor files, and the stubs unconditionally, and refreshes a mode file only if its hash still equals the shipped version recorded in `.loom-modes-version`; an edited mode file is left alone and reported, with the new shipped version written beside it as `<mode>.md.new` for the author to merge. (**[assumed]** the `.new` convention.)

## 11.3 Orientation

**[decided]** Two layers, so that any agent finds the rules on its first action without loom assuming which agent it is.

1. Static: `ai/orientation.md`, generated by `loom ai init`, refreshed by `loom upgrade`. Its contents are Appendix D: what a quilt is, the layout with read/write permissions per directory, the source contract in one page, the ledger and what states mean, the commands an agent uses and when, the write policy, the modes and their contracts, context economy.
2. Dynamic: `loom ai orient [--run RUN]` prints the static document followed by what only the moment knows: the quilt's config, the `status` summary, open runs, undigested citekeys, and, with `--run`, that run's `thread.md` and `run.log` so a later session picks up the context.
3. Vendor files: `CLAUDE.md` and `AGENTS.md` at the quilt root, generated as copies of one short text: "This directory is a quilt managed by loom. Before doing anything, run `loom ai orient` and follow it. Write only under `ai/runs/`." Claude Code reads the first, Codex the second. **[deferred]** Whether either supports importing `ai/orientation.md` by reference; copies are safe and are what `loom ai init` writes.

## 11.4 Runs

**[decided]**

1. A run is a directory under `ai/runs/`, created by `loom ai start [SLUG]`, named `<timestamp>-<slug>`; `SLUG` defaults to `run`. `loom ai start` writes `run.toml` and prints the path. If `[ai] agent` is set in `config.toml`, it then launches that command in the quilt root with the orientation (including the run path) as its initial prompt; **[deferred]** exact launch flags per agent, verified at implementation.
2. A run is one chat thread with an agent and nothing more. It has no mode, no state, no lifecycle. Modes are applied inside it, any number, in any order.
3. Everything the run produces lives in its directory, named by mode and target: `referee-rl-0004.notes.md`, `draft-rl-0019.tex`, `proposal-rl-0004.diff`, `ingest-Man12.tex`.
4. `run.log` is written by loom: every command invoked with `--run DIR` appends a line (time, command). `thread.md` is written by the agent: a dated entry per significant exchange (what was asked, what it did, what it decided, what remains). The orientation document asks for `thread.md`; loom guarantees `run.log`.
5. `loom ai orient --run RUN` reopens a run for a new session; `run.toml` may record the agent's own session identifier so the thread can be resumed in the agent as well.
6. Discard (7.8) marks the run's records ignored without deleting anything.
7. Runs publish as threads in the manifest (specs/manifest.md §10): `thread.md` rendered as messages, attachments listed, `run.log` as the log.

## 11.5 Modes

A mode is a prompt template in `ai/modes/` with an input contract (what loom hands the agent) and an output contract (what the agent must leave in the run directory). The templates are adapted from the author's existing review rules; their full text is Appendix C. Chat-specific parts of those rules (KaTeX formatting, the variable-definitions preamble, the intuition block) do not transfer, because outputs are files; the modes and blocks do.

**[decided]** The modes, their inputs, and their outputs:

| mode | purpose | input (via `loom bundle KEY --run DIR` and context) | required output in the run |
|---|---|---|---|
| audit | load-bearing audit: hypothesis ledger, citation ledger, self-containedness, sharpenings, uses-ledger | bundle; ledger states of the closure; digest entries for cited results | `audit-<key>.notes.md` with the ledgers; annotations via `loom comment --run` for each finding |
| referee | hostile review: gaps, worked examples, counterexamples, verdict | bundle; same context | `referee-<key>.notes.md`; annotations via `loom comment --run` |
| simplify | shorter text with identical mathematics | bundle | `proposal-<key>.diff` (unified diff against the node file) plus `simplify-<key>.notes.md` listing each change with its license |
| question | answer a question about a key or the quilt | bundle or `status --json` | `question-<slug>.md` |
| quick | brief answer, brevity first | as question | `quick-<slug>.md` |
| draft | write a complete node from a plan the author supplies | the plan, the closure statements (`loom bundle` of the intended dependencies), the skeleton from `loom new --print` | `draft-<id>.tex`, a complete node file obeying the source contract |
| ingest | produce or complete a digest | `refs/pdf/<citekey>.pdf` (or its text), or an extracted digest to complete, plus the digest chapter's format | `ingest-<citekey>.tex` (a complete digest) or `proposal-<citekey>.diff` |

Rules common to every mode:

1. **[decided]** The agent obtains context through loom commands, not by reading directories wholesale: `loom bundle` for a key, `loom status --json` for the quilt, `loom search` for ids, `loom deps` and `loom unravel` for the graph. The orientation document says so.
2. **[decided]** Review findings are annotations, one `loom comment --run` call per finding (or one `--batch`), anchored by `--quote` to the sentence they concern; the notes file summarizes. This is the mode's output contract, and it is what makes findings appear in the margin.
3. **[decided]** The audit mode's uses-ledger: for each proof, list facts the argument invokes that no `\ref`, `\uses`, or matched citation names (candidates for `\uses` entries or new nodes), and `\uses` entries the argument never consumes. Each is an annotation anchored to the invoking sentence.
4. **[decided]** Nothing a mode produces is applied. Drafts and digests are promoted by a person (11.7); proposals are applied by a person with their own tools.
5. **[decided]** Every mode file begins with a "Before you begin" block stating the write policy, every notes file begins with a `[summary]` block, and every mode file ends with the output contract as a checklist the agent copies into the notes and ticks.
6. **[decided]** Proposals and drafts are compiled before promotion with `loom bundle KEY --with FILE` and `loom bundle --draft FILE` (12.5); a mode that produces LaTeX reports the compile result in its notes.

## 11.6 Comments from agents

**[decided]** `loom comment TARGET "message" --quote TEXT --kind KIND --run DIR` is the only way an agent records a finding. Loom computes the anchor, records the target hash, writes `DIR/annotations.json`, and appends to `run.log`. An agent never writes `annotations.json` by hand; a hand-written file is not a review record (lint reports `loom:foreign-annotations`, warning, for a file in the record locations that fails validation, **[assumed]**). `--batch` exists so forty findings are one process.

An agent may `--resolve` its own earlier annotations after a re-check, and may reply to a person's.

## 11.7 Promote

**[decided]** `loom ai promote PATH` copies a file from a run into the quilt:

- `draft-<id>.tex` or any file containing exactly one node: to `nodes/<id>.tex`. If the draft carries no id-shaped label, loom allocates one under the quilt's prefix (or `--prefix`) and inserts it into the copy; if it carries one, loom checks it is unallocated or matches an existing loose skeleton the author created for it. Then lint runs on the result.
- `ingest-<citekey>.tex`: to `refs/<citekey>.tex`, refusing if it exists (`--replace` to overwrite after showing a diff).

Promote is a copy plus a check. It never modifies the run's file, never inlines into a master (the author adds the `\input` line), and never accepts anything.

## 11.8 Write policy and permissions

**[decided]** An agent writes only under `ai/runs/`. `nodes/`, `drafts/`, the root files, `refs/`, `comments/` (except through `loom comment`), and `.loom/` are read-only to it. The orientation document states this; `loom ai init --permissions` additionally generates the agents' project-level permission settings that deny writes outside `ai/runs/` and `build/`, in the formats Claude Code and Codex read (**[deferred]** formats verified against current documentation at implementation time; regenerated by `loom upgrade`).

After any run, `loom ai check RUN` (**[assumed]**, or part of `loom check`) reports files outside the run directory whose mtime changed since the run started, as `loom:agent-wrote-outside-run` (error). It does not revert.

## 11.9 Triggers

**[decided]** In interactive use there is no queue and nothing runs unattended. `loom status` is the to-do list: undigested citekeys are the ingest trigger; stale accepted keys and draft keys are the review triggers; the orientation document tells the agent to run `status` first and propose work from it. The runner contract (`specs/runner.md`) specifies `loom ai run --queued` and `--auto` for the non-interactive future and is not built in the MVP.

## 11.10 Two agents, one layer

**[decided]** Claude Code is the author's primary agent and Codex must work equally. Nothing in `ai/` is vendor-specific except the two generated root files and the optional permission settings, all generated from one source and regenerated by `loom upgrade`. Mode templates and the orientation document are vendor-neutral Markdown.

## 11.11 An example session

```
$ loom ai start referee-rl-0004
ai/runs/2026-09-16T14-02-referee-rl-0004
(launching: claude)
```

In the agent: it runs `loom ai orient --run ai/runs/2026-09-16T14-02-referee-rl-0004`, reads the orientation and the status summary, sees `rl-0004` is draft and never reviewed, and is asked to referee it. It runs `loom bundle rl-0004 --run ...`, reads `bundle-rl-0004.tex`, applies the referee template, and issues:

```
loom comment rl-0004 "The hypothesis 'quasi-compact' is not stated; rl-0002 assumes it." \
  --quote "Let $\iota$ be an embedding" --kind objection --run ai/runs/...
loom comment rl-0004/proof "Domination of two embeddings by a third is asserted, not proved." \
  --quote "Two embeddings are dominated by a third" --kind objection --run ai/runs/...
loom comment rl-0004/proof "Consider citing Man12 Prop 3.2 here." \
  --quote "the pullback commutes" --kind suggestion --run ai/runs/...
```

It writes `referee-rl-0004.notes.md` with the six blocks of the referee mode and appends to `thread.md`. The author opens arras: three marks on the node page, the badge reads "draft · 2 open objections, 1 suggestion". The author fixes the proof, asks the agent to re-check; it resolves its second objection and writes `loom comment rl-0004/proof --kind ok --run ...`. The author accepts.

## 11.12 Vendor wrappers: skills and commands

**[decided]** The mode files are the content; anything vendor-specific only points at them. Where an agent supports it, `loom ai init --skills` generates two kinds of wrapper so that a mode is reached without the author naming a file:

- A skill stub per mode, `.claude/skills/loom-<mode>/SKILL.md` for Claude Code: frontmatter with `name: loom-<mode>` and a trigger description ("when the user asks to referee, review, or find gaps in a node of a quilt"), and a body of a few lines: run `loom ai orient --run $LOOM_RUN` if not yet this session; read `ai/modes/<mode>.md` and follow it exactly; begin with the mode's first command. It contains no block definitions and no procedure.
- A slash command per target-taking mode (`audit`, `referee`, `simplify`, `draft`, `ingest`), `.claude/commands/<mode>.md`, taking the target as its argument and expanding to "apply `ai/modes/<mode>.md` to `<target>` in run `$LOOM_RUN`".

Rules: stubs are regenerated by `loom upgrade` and never edited by hand; the layer must work with every stub deleted (the orientation document lists the modes by name for agents with no such mechanism, Codex among them); a stub that duplicates mode content fails `test_ai_init_skills_generated_pointer_only`. **[deferred]** The locations and frontmatter Claude Code expects for skills and commands, and whether either can reference a file by path, are verified against its current documentation at implementation time; the shipped templates live at `src/loom/assets/ai/vendor/claude/`.

## Open questions

- The formats and locations of skill and command stubs. **[deferred]**
- Whether `loom ai start` should refuse to launch an agent when `[ai] agent` names a command not on the path. **[assumed]** Yes, with the path printed.
- Whether runs should be nested (a run about a run). **[assumed]** No.
- Whether the mode templates should be per-quilt (in `ai/modes/`) or per-user (in `~/.config/loom/modes/`) with quilt overrides. **[assumed]** Per-quilt in the MVP; a user-level default set is a later addition.
- The exact form of the permission settings files. **[deferred]**
- Whether `thread.md` should have a required structure. **[assumed]** Dated headings; otherwise free.
