New workflow idea: drafts/ exist as stable copies of a document, workbench/ contains working draft edits. The workflow is drafts/ -> workbench/ -> make edits -> drafts/ repeat. This cleanly separates "milestone fixed state" from "actively being modified" state, and the act of canonizing a workbench "active" draft to a drafts "stable" draft leaves a concrete edit trail behind, so that changes can be visualized and tracked between stable drafts. First some definitions:

- atomic format: refers to the format of a tex file/notes file. Means that the file is designed around input statements with text surrounding.
- linear format: refers to the format of a tex file/notes file. Means that the document prefers a single linear structure,\begin{}...\end{} blocks in the document rather than separated into atomic files. I'm open to naming suggestions, perhaps "expanded format" is better. I like the verb pair better, "expand" is logically the opposite of "atomize" in this context.

Neither of these are rigorous definitions, they are more like philosophies. However they do refer to two different kinds of outputs of various commands in loom.

Nearly every mathematician on the planet prefers working with single large documents rather than atomic structures. This DOESN'T mean we abandon nodes, it means the role changes. Here is my proposed breakdown.

1. Add a draft draft1.tex to drafts/, either by loom init or by dropping it in. Callin loom init NO LONGER creates a record from the draft, it simply sets up the empty quilt with default config and if a --from is specified it copies the draft into drafts/ with absolutely no changes. Cal
2. Call `loom atomize draft1.tex`. This does a few things: it creates node files for every node in draft1.tex, it creates a saved version of draft1.tex in an "atomic" form and it creates an active workbench copy of draft1.tex. Here is the breakdown
   - a workbench "active" copy of draft1.tex is created. It requires passing a filename, `loom atomize draft1.tex workingdraft.tex` or `loom atomize draft1.tex --to workingdraft.tex` and must be a tex file. By default this is in "linear" format, not "atomic" format. Default format can be specified in a quilt's config, is "linear" by default, and can be changed at the command level by passing `--format atomic` or `--atomic` to the atomize command (with parallel commands for linear format).
   - every node gets a copy in nodes/ with an id. First time this is called two copies of each node get created: a stable version and an active version: rl-0001.tex and rl-0001-01.tex. The former is active and the latter is stable. There is another discernment: the active has % !LOOM state: active and the other % !LOOM state: stable. If the format specified was linear, rl-0001.tex lives in the active file. If atomic was specified, it lives in nodes/. In either case the stable version rl-0001-01.tex lives in nodes.
   - a copy of draft1.tex is made somewhere (I'm not sure where, probably a hidden directory) in "atomized" form. This is for historical purposes if draft1.tex is ever changed. Not sure where this should go yet, please discuss. In quilt metadata somewhere (ledger.json? not sure where it should go, should maybe be .ledger.json) a ledger line is added marking that draft1.tex is the starting point. The permanent copy should be named with id, maybe draft-0001.tex or something even more safe in case a user chooses "draft" as a node prefix, and it should contain a loom metadata line with the date down to the seconds: % !LOOM date-created: 2026-09-17:06:00:05. The type of action which created it is also recorded in the ledger, "atomized" along with the name of the file whence it came "draft1.tex". It is not assumed that draft1.tex will remain stable after this point, the user is free to change it.
3. Edits to workingdraft.tex are made. AI is consulted, annotations left, nodes added, accepted.
4. A new landmark is reached and the user is ready to "commit" a stable version. They now call `loom cannonize workingdraft.tex draft2.tex` or `loom cannonize workingdraft.tex --to draft2.tex` and draft2.tex is created in drafts/, a copy of workingdraft.tex intended as a new stable record. A line is added to the ledger, a new permanent copy created, action recorded as "canonized".
   - a new stable version of every node is recorded, rl-0001-02.tex, etc. Allowing for tracking of nodes across time. Can see what is modified, what is added, what is deleted across versions. Hashes allow one to see if content changed or not.
5. Process can now repeat. Or the user can keep editing the existing workingdraft.tex file and canonize again. Draft2.tex could be edited directly for a while (though not intended it's perfectly fine and causes no problems) and then atomized called again to create workingdraft2.tex.

Questions before implementation:
- should there be an offer to delete workingdraft.tex upon canonicalization, or a suggestion to the user to delete it? This is good practice, it protects against two parallel files or editing the wrong file.
- how should historical records be kept? Making a copy of the draft1.tex file somewhere with an id seems safest because it protects the surrounding text, but maybe the same thing can be achieved with a hash or something. We're already storing stable node version, so an atomized format of draft1.tex would be sufficient, so long as the surrounding text is also kept.
- what do you think of the format names and the "atomize/canonize" pair? For the format I like "atomic" but am unsure whether "linear" or "expanded" is better. For the "atomize/canonize" pair I like canonize but am unsure about atomize, today it refers to a different type of operation, namely the production of an "atomic version" of a file from a linear/expanded version. Please weigh in.
- irrespective of the names chosen for these verbs, I'd like a pair of format converter operations (atomize and linearize/expand) and a pair of verbs for moving between drafts/ and workbench/, (<something> and canonicalize). Give me a few suggestions.

Risks
- if the user doesn't delete a workbench file there is risk of parallel edits/editing an older version of the file.
- name changing of files or editing of drafts files could cause weirdness if this isn't properly designed. The assumption is that records are created during atomize and canonize events, and those are the static points in history. Should never assume that draft1.tex is stable for instance.
