# 0.18 — the command line

## Context

The CLI study of 2026-10-02 (`docs/reports/cli-study.md`, 788 transcripts) measured every loom command against the terminal principles (book 1.10). Its findings:
- **Output.** It fails the principles nearly everywhere except the refusals. Verdicts come last. Lines reach 322–1,397 columns. Output is full of storage paths and hashes. No command reports progress, and there were silences of up to 955 s.
- **Defects.** Twelve defects lose data or report a failure as success, among them `sync init`'s defaults publishing over the quilt's own branch, `refs build --force` deleting verified results, and `refs scan` appending a duplicate entry on every run.
- **Speed.** One function, `records/dependencies.py:display_span`, causes most of the slowness: it re-tokenises a whole file once per key.
- **Shape.** The command surface grew by accretion: 96 names for 91 commands, `refs` with 27 subcommands, and flags whose meaning changes from command to command.

An agent's audit of the same day, `docs/issue-reports/refs-audit-critique-from-agent-2026-10-02.md`, adds four things for the cited-works layer:
- result states that tell an extraction from an author's check;
- one work holding several documents;
- ranked search;
- digest diagnostics kept out of the author's lint.

It also finds one more bug: a sibling entry without an identifier loses its PDF.

The author decided on 2026-10-02:
- an umbrella with sequential sub-plans, each a section of this file;
- the principle revisions written into Chapter 1 first, so every sub-plan is measured against them;
- the library redesign takes the CLI of the study's part six plus the critique's core, while lazy digests get a study and a later plan;
- the group is named `library`, the viewer's word.

The outcome: a command line where the defects are fixed, everyday commands answer in seconds on a real quilt, every report reads by T1–T8, the commands obey K1–K7, and the cited works are reached through one `library` group, about ten commands a person needs plus the agent's tools and upkeep, instead of 29.

## 0.18.1 · Defects that lose data or report a failure as success

### Context

Part two of the CLI study (`docs/reports/cli-study.md`) lists twelve defects that lose the author's data or report a failure as success. A thirteenth comes from the agent critique `docs/issue-reports/refs-audit-critique-from-agent-2026-10-02.md` §3.

The author decided on 2026-10-02 how agent guards should work: under an agent marker, an author-only act refuses whatever name the caller declares. That reverses DR-203's "a declared identity wins" for those acts.

The outcome:
- every defect below is fixed;
- each has a test that reproduced it first;
- the book says what the code now does.

### The fixes

#### 1. `sync init` publishing over the quilt's own branch

**The defect.** `--remote` defaults to `origin` and `--branch` to `main` (`cli/sync.py:47-48`). With no flags, `sync publish --push` replaced the quilt's own branch with the source-only projection.

**The fix.**
- Both options become required, with help text.
- `configure` (`sync.py:229-247`) refuses a pair that is the current branch's upstream. It compares `git rev-parse --abbrev-ref --symbolic-full-name @{upstream}` with `remote/branch`; a branch with no upstream counts as safe. The refusal names the pairing chapter 4.6 shows: `--remote overleaf --branch master`.

**Test.** In `tests/unit/test_sync.py`, a quilt whose branch tracks `origin/main` is refused. The existing `_paired` setup has no upstream, so it still passes.

#### 2. `sync incorporated` verifying nothing

**The defect.** `mark_incorporated` (`sync.py:698-706`) checks only that the selected sources are clean. After `--yes`, the next push reverted a coauthor's edit.

**The fix.**
- The command and `mark_incorporated` are removed. `sync finish` is the checked path, and the viewer's Incorporate already uses it: `sync-incorporate` → `incorporate_pull` → `finish_incorporation`.
- Book 4.6's sentence about renames (`04-the-quilt.md:208`) and 12.2 are rewritten.
- The agent permission files are regenerated (`scripts/gen_quilts.py`).

**Test.** `sync incorporated` is an unknown command.

#### 3. `refs build --force` deleting verified results

**The defect.** `_extract_step` (`refs/build.py:395-420`) overwrites `digests/CITEKEY.tex`.

**The fix.** After the write, every result in `load_results` whose `state` is `verified` and whose class is not `mechanical`, and whose label is no longer in the new text, is appended back with `append_to_digest` (`refs/proposals.py:308`). A mechanical result the author edited (an `edited` act in its origin) gets its edit back with `rewrite_in_digest` (`proposals.py:320`). The build's report names each result it restored. A restored result that the new extraction contradicts (an extracted node of the same label with a different statement) is listed for the author.

**Test.** In `tests/unit/test_refs_layer.py`, verify a proposal into the demo's `Calloway14` (whose store has `src/`), run `refs build --force Calloway14`, and the node is still in the digest.

#### 4. `refs scan` adopting the same document on every run

**The causes,** in `adopt_orphans` (`refs/scan.py:402-481`):
- `claimed` reads only `primary(entry).path` and ignores `loom-file`;
- `came in sources` compares the ledger's raw path with `parse_bib`'s whitespace-collapsed `loom-source`;
- a nested seed file is recorded as `refs/x.pdf` but ledgered as `refs/sub/x.pdf`.

**The fix.**
- `claimed` includes every entry's `loom-file` directory.
- The comparison is by the ledger's `"to"` (the store directory), with the paths whitespace-normalised on both sides.
- `copy_documents` writes the relative seed path that it ledgers.

**Also fixed alongside.**
- `refs build` runs its argument checks (`--only`, citekeys) before the scan (`cli/refs.py:364-379`).
- `--dry-run` writes nothing: no copy, no map, no ledger line (`copy_documents` with `write=False`, `scan.py:526-533`).
- The dry run's lines are marked `(dry run)`.
- `--json` builds still scan, as they must, but are refused like any other build when their arguments are bad.

**Existing duplicates.**
- `refs scan` reports once that two or more entries name the same stored document, listing the keys and the fix: keep one, delete the others from `digests/bibliography.bib`. That file is append-only for loom, but the author may edit it (8.15).
- For the author's quilt (`~/Desktop/relloc`), the commands are handed to the author.

**Tests.**
- In `tests/unit/refs/test_scan.py`: a seed file with two spaces in its name, and one in a subdirectory, each adopted at most once over three runs.
- A dry run leaves the store and ledger byte-identical.
- A refused build writes nothing.

#### 5. `revert` recording reverts that never happened

Nothing reads a revert line to learn a key's text: that is found from content (`versions.matching_version`).

**Book.** The book's ledger table drops the `revert` row (17.6, `17-the-workbench.md:89`).

**Test.** `test_revert_prints_a_patch_and_records_it` (`tests/unit/history/test_commands.py:137`) becomes "prints a patch and records nothing".

## 0.18.2 · Speed, and a rebuild proportional to the change

### Context

On 2026-10-02 the author could not open a session in the viewer on `~/Desktop/relloc`, which holds 64 results of their own and 3,204 from cited papers. The cause: every write waited for a full rebuild. Two caches added that day took a cached build from about 55 s to 14 s.

Exploration for this plan found more:
- **Every API write builds twice.** `LoomHandler.do_POST` (`render/serve.py:193-235`) builds before answering. Then the watcher, whose `rebaseline()` (`render/watch.py:67`) nothing calls, sees the same files on its next poll and builds again.
- **Nothing is reused except fragment rendering.** `build()` (`render/build.py:333`) re-scans and recomputes everything on every rebuild:
  - acceptance states, twice (`store.py:721`, `review_compare.py:80`);
  - every review preview, even though each one's path is already content-addressed;
  - spans for every cited work;
  - annotation payloads;
  - every session's transcript pages.
- **Review previews are rendered for cited papers' machine-made results**, which nobody reviews. Their digest nodes have no acceptance row, so every build previews all of them (`review_compare.py:90-94`).
- **A cold build of relloc took 880 s**, nearly all of it `latex d.tex` runs, one at a time:
  - **One process per figure.** `compile_svg` (`render/fallback.py:83-170`) caches by content in `build/cache/svg/` (sha1 of preamble, border and body). But each figure inside a fragment compiles in turn, and the whole document is one fragment.
  - **Previews miss the fragments' cache.** Review, incoming and adoption previews pass the closure's raw text as the preamble, not the fragments' prepared one, so they compile every figure again. They may also fail under `-halt-on-error`, because the macros get defined twice (`fragments.py:175`); this is to be confirmed.

**Decided with the author on 2026-10-03:**
- **The manifest stays current when a write answers.** That is the rule in `test_the_manifest_is_current_when_a_write_answers` (`tests/unit/render/test_write_api.py:77`). The publication becomes fast instead of being skipped.
- **The on-disk per-file scan cache is built only if the benchmark shows a one-shot command still over its target.** On the relloc copy, `status` and `lint` already take about 2 s.

**The outcome:** every change rebuilds only what it feeds, a write in the viewer answers in under a second, and a cold build compiles each figure once, in parallel.

### The work

#### 1. A benchmark, first

`scripts/bench` follows the shape of `scripts/verify`: argparse and a printed table. It runs on the demo quilt, and also on a copy of a quilt when a path is given. It never writes the original.

It measures:
- a cold build, with `build/` removed;
- a cached build;
- an edit to one result's `.tex`, until it is republished;
- `status`, `lint`, `deps`, `ai orient` and `accept KEY`;
- in a `serve`: `session-new`, `annotate` and `message`, each until it answers;
- `serve`'s first build of an already built quilt.

The baseline on the relloc copy is recorded before any change.

#### 2. Figures: compiled once, in parallel, and shared

- **Parallel.** The converter's fallback (`ctx.fallback`, called from `convert.py:567, 610, 657, 1203, 1365, 1377`) returns a placeholder and registers the compile. The renderer then compiles every placeholder of the fragment at once and substitutes the results. This happens in `FragmentRenderer` (`render/fragments.py:182-244`) and in every preview's `_render`.
- **One shared pool.** Compiles run on a module-level pool in `render/fallback.py`, sized to the core count. In-flight compiles are deduplicated by the existing cache key, so a figure that appears in a node, a document, a landmark and a preview is compiled once. The fragment pool (`build.py:427-440`) is unchanged; its threads wait on figure futures from the separate pool.
- **Previews use the fragments' preamble.**
  - A preview of current text (review, incoming, adoption) compiles through the same fallback as the fragments (`FragmentRenderer._fallback(master, file, key)`), so it hits their cached SVGs.
  - A preview of an accepted text keeps the preamble recorded with it, since that is what it shows.
- **The cache stays content-keyed** in `build/cache/svg/`, keyed on preamble, border and body as now. Failures stay cached as `.failed`, and `build --force` clears them.

**Tests:**
- two fragments containing one figure compile it once (count compiles through a fake `latex`);
- a fragment's three figures run concurrently (a fake `latex` that sleeps, with more than one running at a time);
- a review preview of a node with a diagram reuses the fragment's SVG and compiles nothing.

#### 3. Every derived step is keyed by its inputs

A build takes an optional `BuildMemo` from the previous build in the same process (`serve` keeps one) and reuses each step's output while its inputs are unchanged:

| step | key |
|---|---|
| the scan | reused when no changed path is source (`.tex .sty .cls .bib`, `config.toml`) |
| `key_states` (and per-author states in `Records.apply`) | the scan's identity, and the ledger's stamp (`(mtime, size)`, as `load_history` already uses) |
| review previews (`review_compare.py`, `incoming.py`, `prose_changes.py`) | the content-addressed path the preview already has; a path in the previous publication is not rendered again |
| spans of a cited work (`_attach_spans`, `build.py:96-169`) | the work's `results.json` bytes, its map's hash, and the annotations on it; kept in `build/cache/spans.json` so a one-shot build reuses them too |
| annotation payloads (`attach_payloads`) | the payload text |
| transcripts (`_write_transcripts`) | each session inbox's stamp |

- **No previews for machine-made results.** A digest node whose result is `mechanical` (`load_results(root, n.digest)[n.id].cls`) gets no review preview. Nobody reviews it; 0.18.5 makes that state explicit.
- **`key_states` is computed once per build.** `attach_comparisons` stops computing it a second time.

**Tests:**
- one per step: with unchanged inputs, a second build does not recompute (the step's function is patched to count calls);
- a changed input does recompute.

#### 4. The write path and the watcher

- **Writes are classified.** Each API endpoint (`render/api.py`) writes one of these kinds:
  - **records**: sessions, the annotation log, messages, citation notes, adoption decisions, reviewer settings;
  - **source**: `sync-incorporate`, `adopt-finish`, `digest-verify` (which writes the digest file);
  - **ledger**: `review-finish`.
  
  The handler passes the kind to `rebuild`. A records write reuses the scan, and with step 3 it publishes in well under a second. The manifest is still current when the write answers.
- **The watcher does not repeat an API publication.** After the API's publication, `ServeSession` calls `watcher.rebaseline()` under the publication lock.
- **The watcher folds a burst into one publication.** On a change it waits for one quiet poll and then rebuilds once with the union of changed paths. A change that arrives during a rebuild queues one more rebuild, not one per change.
- **Heartbeats publish nothing.** Check that `.loom/sessions/*/attached.json` stays outside the watched set (DR-265-ikmartin), and add a test if not.
- **`_compile_default`** (`serve.py:440`) reuses the serve's scan instead of scanning again.

**Tests**, in `test_serve.py` and `test_write_api.py`:
- a session, annotation or message write answers with the manifest current, runs no scan (the scan is patched to count), and is followed by no watcher rebuild;
- three edits within one poll produce one rebuild;
- `test_the_manifest_is_current_when_a_write_answers` still passes.

#### 5. Commands that need no scan don't run one

**Decided with the author on 2026-10-03:**
- **JSON is one envelope that keeps each command's data.** Every `--json` is an object carrying `verdict`, `ok`, `exit`, `groups` and `notes`, beside the command's own data under its existing keys: `status` keeps `keys`, and `lint`'s bare list becomes `diagnostics`.

**The outcome:** every command reports through one layer, so T1–T8 hold by construction, and a check in the test suite keeps them holding.

### The work

#### 1. `loom/src/loom/cli/report.py`

```python
Item(text, key=None, command=None)     # key: an identifier, placed last and never cut
Group(heading, items, count=None, limit=12, next=None, problem=False)
Report(verdict, ok=True, exit=0, groups=[], notes=[], data={})
Report.render(width=100) -> str        # the text
Report.to_json() -> dict               # the envelope
Report.emit(as_json) -> int            # prints, returns the exit code
```

**The text:**
- the verdict line comes first;
- each group is `heading (count)` with its items indented two spaces under it, sorted as given;
- a list longer than `limit` is cut, with `… and N more; <next>`;
- an item's `key` goes last on its line, and a line over `width` wraps at a space with a hanging indent, never inside an identifier;
- `notes` go to stderr;
- a dry run's verdict reads `dry run: …`.

**The JSON envelope** is `{verdict, ok, exit, groups: [{heading, count, items, next}], notes, …data}`. The items are never cut, and each item is `{text, key?, command?}`. `emit` writes it with `emit_json` (sorted keys), and stdout holds only that, on failure as on success.

`Report` replaces `doctor.Report.render` (its ok/warn/fail model is kept, as items with a status), `ScanReport.lines` and the refs `BuildReport.lines`, each of which gains `report() -> Report`.

#### 2. `Progress`, in the same module

- **Usage:** `with Progress("extract", total=18) as p: p.item(name)`.
- **On stderr only:** stage, item, `n/total` and elapsed time.
- **Silent for the first 2 s,** so a fast command prints nothing; T6 is about what is slow.
- **On a long item:** it adds "still working, 40 s" after 15 s on one item, from a timer thread.
- **Terminal or not:** on a terminal it is one line that rewrites itself; otherwise one plain line per item.
- **Where it is used:**
  - `build`, `check` and `compile`;
  - `serve`'s first build (its "building the quilt ..." line becomes a `Progress`);

#### 3. One diagnostics formatter

- one group per code, headed `code (count)`;

#### 1. One session resolver

- **Tests:** ambiguous refused with both names; deleted not found for writes and found for `session use --deleted` and readers.

#### 2. Flags (K2), outside `refs`

- **`--as NAME` is who acts**, replacing `--author` on:

- **`--name` names something new:**

- **`--to FILE` is always an option, with one path rule.** A helper `_common.destination(quilt, path, writes_drafting=False)`:
  - refuses a path among the quilt's sources or drafting directories, unless the command writes a drafting document;

  `atomize`'s positional `DEST` goes (the study's G6 precedence bug), and the rule applies to `id`, `deloom`, `linearize`, `history restore`, `adopt --to` and `sync status --patch --to`.

## 0.18.5 · The library

### Context

The CLI study (Part six) and the agent's refs audit (`docs/issue-reports/refs-audit-critique-from-agent-2026-10-02.md`) found the reference layer is where loom's command line is worst:
- **Too many commands.** 29 commands (27 `refs`, 2 `digest`), and none lists what waits for the person.
- **Flags broken against K2.** Flags mean different things on different commands: `--author` and `--as` on one option, `--reason` beside `--why`, `--fetch` and `--resolve` as consent.
- **Search.** It is unranked, truncates ids, and `grep` is case-sensitive.
- **Dishonest states.** A mechanically extracted result is stored `verified`, even from a preprint the bibliography does not cite.
- **Duplicate works.** The author's own PDF of a paper loom already fetched becomes an unrelated sibling with a second digest, and a sibling with no identifier loses its PDF.
- **Ingest on weak signals.** It filed a wrong PDF on two weak signals and does not say what it skipped.
- **Lint swamped.** About 129 of the author's 139 lint errors are inside machine-made digests nothing cites.
- **Stale paths.** Chapter 8 and the orientation give store paths the code stopped using.

**Decided with the author on 2026-10-03:**
- **Two landings.** 0.18.5a is the command surface. 0.18.5b is the data model: states, versions, and lint by citation.
- **States.** `extracted` and `verified` now. `checked` (numbering confirmed against the cited version) waits for WQ-39, which keeps its trigger.
- **States are derived on read.** A result is `verified` only when a person verified it. A mechanical result without that reads `extracted`. No file is rewritten: the author's live quilt and its 3,140 results stay as they are.
- **Write API.** It takes library names, and `reason` becomes `why`. Only arras calls these endpoints, so Luisa is not consulted.

- **`add`** takes files and folders.

    - an identifier found in the document's text equals the entry's; or
    - the full normalised title matches and the entry's first author leads the byline.
  - Anything weaker is skipped, with its reason. A document matching another entry more strongly is refused, naming that entry.

  - ties go by citekey.

- **`ignore`** acts by what the work has:
  - a stored document is set aside, as `forget` did;
  - no document is declared unreadable;
  - two versions are refused, naming them.

  `--undo` withdraws whichever applies.
