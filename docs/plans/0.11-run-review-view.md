# 0.11 — Reviewing a run in arras: the split view, the report pane, and the write API

**Status: built**, 2026-09-18, in six gated commits across the three repositories; decision records DR-156 to DR-163. Written 2026-09-18, superseding the reminder of 2026-09-17 and the design sessions of 2026-09-17 and 2026-09-18. [0.10](0.10-annotations-and-review.md) is built and tested, so the annotation log, severity, payloads, run names and `loom ai findings` are available. This is where WQ-23 and WQ-26 land, both closed into it, and it carries R2b of [0.9.5](0.9.5-arras-refactor-interjection.md).

## Context

0.10 gave the agent a record worth reading and gave loom the commands to write it. Nothing reads it. Four facts, which together fix everything below.

**An agent's report cannot be read at all.** Every mode writes `<mode>-<target>.notes.md` into its run, and `/thread/[id]` — 42 lines, `src/routes/thread/[id]/+page.svelte` — lists attachments by filename. You can see that `referee-dm-0003.notes.md` exists; you cannot see what it says. The terminal cannot help, because no agent CLI typesets mathematics, so a report written in LaTeX against the quilt's macros is read as source in a chat window that then disappears. The files already contain real mathematics. Nothing renders it.

**Annotations have nowhere to be answered.** 0.10 made every finding an event in `annotations/log.jsonl` with a severity, a payload and an anchor, and made `loom comment --reply/--resolve/--edit` the way to work one. All of that is CLI-only. The author reviews in a browser and answers in a terminal, which means the review surface and the reply surface are two applications.

**The viewer is read-only by construction and this is the plan that changes it.** WQ-26's stated reason for deferral was that arras has no write API; `docs/specs/write-api.md` is 37 lines of `[decided]` specification with nothing behind it, and its §4 still routes a model's reply through the runner that was declined as WQ-15. Arras stops being read-only here, in the same change that makes it worth writing into.

**Arras is not yet host-neutral, and the view set is about to grow.** R2b of 0.9.5 is assigned to this plan and the reminder omitted it. Two `PENDING_R2B` lists carry the debt explicitly — `tests/unit/host-neutrality.spec.ts:66` for the URL scheme and `tests/e2e-minimal/minimal.e2e.ts:48` for the vocabulary — and this plan adds four views, so the derived view list is cheaper to build now than to retrofit. **Host neutrality is worth having on its own terms and not as preparation for a component API**: it is what lets arras render a corpus loom did not write, and what lets one bundle be themed into two sites. The component API itself was re-argued on 2026-09-18 and is not being built — see [0.9.5](0.9.5-arras-refactor-interjection.md) §8, which keeps it as a declined design.

What unifies them: the record 0.10 built has no reader, and the one surface that could read it cannot be written to, cannot render mathematics, and does not yet know that it is one host among several.

## Scope

**In.** The split view at `/thread/[id]`; the report pane and the block parsing that feeds it; the Journal tab; the verbatim toggle and `build/source/`; the two closure panels and local-graph navigation; the notation panel; the four annotation surfaces of WQ-26; the write API, specified and built; all three parts of R2b.

**Out.** Applying a suggestion ([WQ-27](../work-queue/WQ-27-applying-a-suggestion.md)). The proposed document ([WQ-33](../work-queue/WQ-33-the-proposed-document.md)), deferred 2026-09-18 pending the parallel-quilt reframing. Writing through the editor clients ([WQ-34](../work-queue/WQ-34-write-surfaces.md)). The component API, re-argued and declined on 2026-09-18 ([0.9.5](0.9.5-arras-refactor-interjection.md) §8); the token *scoping* it would have needed is in Part I, because it pays for itself as theming. The pipeline picker, which stays secondary to the chat. The citation-verification view, superseded by reference notes.

`interface_version` stays 1: every manifest change here is additive.

**One standing rule across every part.** Display logic is written as a **core derivation** in `src/lib/` — model facts in, display facts out — rather than as code inside a route. `badges.ts`, `graph/layout.ts`, `contents.ts` and `reached.ts` are the existing shape and the new work follows it. This is not preparation for extracting a package, which is declined; it is what keeps a view testable without a browser, keeps the routes thin enough to re-theme, and keeps the same derivation usable from two places — the report pane and the node page both want the closure, and only one of them should compute it.

## Part A — What the publisher must emit

Four additions to loom's build, all of them data the publisher already has and none of them a new source of truth.

### The pipeline on the thread object

The right pane cycles through runs, and a run's modes and their order are what it cycles through. 0.10 settled that a run's modes are **derived** from the `<mode>-<target>.notes.md` files it wrote rather than declared in `run.toml` — record intent, derive fact — and `render/threads.py` already holds those filenames in `_attachment_kind`. So the thread object gains `pipeline: [{mode, target, report}]` in file order, where `report` is the attachment path.

**The viewer must never parse `referee-` out of a filename.** That is a publisher's vocabulary compiled into the core, and it is exactly the leak R2b exists to remove; a corpus published by the sitegen or by weft has no modes and emits an empty pipeline, which renders as no picker rather than as a broken one.

While in this file: `KINDS` at `render/threads.py:15` still maps `"bundle-"` to attachment kind `bundle`, which nothing has written since DR-148 deleted the command in 0.10, and which `specs/manifest.md:286` does not list among the kinds. Remove it.

### Report blocks, parsed at build time

`ai/rules.md` already mandates *"Write each block under a heading with its name in brackets"*, every finding already ends with its annotation id — `(a-2026-09-17-0001)` — and every annotation already carries a quote selector with prefix and suffix. The structure was always written down; nothing was reading it. So loom parses the bracketed headings into blocks at build time and links each trailing id to its annotation, which anchors into the draft.

A new `render/reports.py`: `parse_report(text) -> list[Block]`, each `{name, title, html, findings: [{id, html}]}`. An unparseable file degrades to one unnamed block holding the whole rendered document — a report is never worth failing a build over.

Two alternatives were considered and rejected, and the reasons belong here because both will be proposed again. *Rendering the file whole* is nearly free — `records/store.py:449`'s `render_markdown` already serves annotation bodies — but it gives a document you can read rather than one you can use: "show in report" has nothing to scroll to, because bracketed names are then text that merely looks like structure. *Blocks emitted through a CLI* (`loom report block referee-review …`) would make the completeness check mechanical, but it is eight heredocs where there was one file, agents author markdown well and author through a CLI badly, and it invents a format that must then be versioned.

**The one piece of real work is math.** `render_markdown` is markdown-it in commonmark mode with `html: False` and emits `$…$` as literal text; the dialect wants `<span class="math inline">\(…\)</span>`. A math pass over the token stream makes the rendered report dialect-conformant, at which point `validate-dialect.py` checks it like any other fragment and the quilt's macros resolve. The same pass serves every other caller of `render_markdown`, all of which have the defect and none of which have shown it: annotation bodies (`records/store.py:394`) and thread messages (`render/threads.py:38,50,115`). It matters less there only because those texts are shorter.

### `build/source/<key>.tex`

The verbatim toggle needs a key's own text before macro expansion, and the manifest was measured at 772 KB on relloc when 0.10 was written and would nearly double with source inline. So the publisher writes one file per key under `build/source/`, fetched lazily by the viewer. `lib/paths.ts` has `dataUrl()` for build-directory files and needs no change; `specs/manifest.md` gains the directory, because a second publisher must know to write it and a viewer must know it may be absent.

### Nothing for whole-document annotations

They already work end to end and have since 0.6: `loom comment` takes *"a key, an equation's qualified key, or a master path"*, the annotation's `target.key` is then the master's `path`, and `m.masters` carries `path`. Arras has simply never called `commentsOn` with anything but a node key. This is arras-side only.

## Part B — The report pane

The right pane of the split view, and the reason the split view is worth building.

**Two tabs: Report and Journal.** The reminder called the second one Transcript, which was a word with nothing behind it — loom cannot see a chat and should not transcribe one. `thread.md` is a journal and orientation §6 says so plainly: *"after each significant exchange, append a dated entry… a later session, yours or another agent's, resumes from it."* It is an agent-to-agent handoff doing its job, and it is shown under its real name. `threads.py:_messages` already renders it as dated messages; the Journal tab is that list, which the current route already draws.

The Report tab renders Part A's parsed blocks in order, with:

- **Whole-document findings first, in a section of their own**, before the blocks. They are about the thing the left pane is showing as a whole, where every other finding is about one node inside it.
- **Each finding an addressable object** with an id, so "show in report" scrolls the right pane to it and selecting it scrolls the left pane to its anchor. This is what makes the pane an index into the draft rather than a document beside it.
- **Findings ranked by severity** from the log, with `[R1]…` display numbers taken from the report itself.

**The manifest grows no severity counts.** `Reviews.open` stays kind-keyed, because an open question is not an open objection and that is the distinction a reader scans for when deciding whether to look. Severity is on every annotation and arras already walks `manifest.annotations`, so it aggregates where it needs to. A second aggregation beside the first is a field every publisher must fill and that can fall out of step with the one next to it.

## Part C — The split view

**This is `/thread/[id]`, not a new route.** That page already shows a run — its messages, its attachments, its log — and the split view is that page done properly. It renders the split view when the thread's `kind` is `run`, and keeps today's simpler shape when it is `comments`, which has no report and no draft to split against. One route, two renderings. `/review` stays the ledger table; a run review is a different thing wearing the same word.

The draft on the left, the run on the right. The panes scroll independently and the strip stays fixed. The right pane cycles through runs — a pipeline, an earlier run, your comments, all runs — and the draft's highlights follow the selected run. Reached from the agent's closing line in the chat (`localhost:8791/thread/<run>`; `DEFAULT_PORT = 8791` in `render/serve.py:25`), from a run in the threads index, and from any finding on a node page.

**The version line.** The left pane is a versioned text and the run was made against a specific version, so the pane says which — "run against `rl-0012@4`, now @5" — from the annotation's `against` hash and the ledger. This is the split view's honest answer when highlights no longer line up, it is cheap now because 0.9's ledger and 0.10's anchors are both built, and it is expensive later because by then someone will have decided that highlights silently not matching is normal.

**"Node and evidence"** is what the split view gives when a finding is clicked, with 0.7's `loom:` links into a paper as the evidence. It needs no view of its own.

## Part D — Closure panels on the node page

`loom bundle` went in 0.10: the agent reads a closure from a command that prints, and what a *person* wants is a view. Both panels are built from data arras already has and neither writes a file.

- **The local graph already exists.** What it lacks is navigation: you cannot move to the nodes within it. That is the whole change, and `graph/LocalGraphPanel.svelte:14,20` already takes `hrefFor` — an injected URL policy — so the seam it needs is the one already there.
- **A stacked closure panel**: the closure in dependency order with the node last, at depth 1 or depth 2, the depth a control on the panel. This is the bundle's own shape, as a page, for reading an argument through.

**Both are panels on the node page, and neither is a route.** A closure is a way of looking at a node, not a place to go. The graph answers "what would this disturb" and the stack answers "what does this rest on", so they belong beside each other. A finding does not choose between them: clicking one gives node and evidence, and the reader picks at the node.

## Part E — The verbatim toggle

Planned as Part G of 0.10 and not built there — what 0.10's arras commit delivered was the manifest's new fields, the `record` → `run` repair, the severity chip and the payload preview. It needs Part A's source-fetch path, and it reads beside the report pane rather than ahead of it.

Per node and per payload, in the box's upper right, revealed on hover and focus with a preference to always show; flips the body between rendered and source, paired with **copy** and **copy for chat** (the key in the author's tag syntax plus the text). "Source" is the node's own text before macro expansion; for a payload, the payload; for a digest node, the digest's statement. Needs no write API.

**The `placement` collision is already resolved and needs nothing here.** 0.10 did it: `fragments/mount.ts:22` documents the viewer's layout decision as a *slot* — *"Named `slot` rather than `placement` because an annotation now carries a `placement` of its own, which is a different thing"* — so the annotation's `replace` / `after` / `before` and the viewer's gutter / inline / count no longer share a word. Recorded so it is not raised again.

## Part F — The notation panel

Settled with the author on 2026-09-16. Notation belongs to agent prose only — reports, explanations, messages — never `nodes/` or `drafting/`, because a symbol an agent introduced to explain something is not a symbol the paper uses.

The agent declares a `[notation]` block once per run. Arras marks each declared symbol by TeX token inside that run's math, lists them in an expandable panel on the run pane, previews the definition on hover, and flags a second meaning for one symbol within a run. The block is parsed by Part A like any other; the marking is a core derivation over the run's rendered math.

## Part G — The write API

`docs/specs/write-api.md` is 37 lines, entirely `[decided]`, and two of its sections are invalid before a line of it is built.

**§4 is rewritten first.** It routes a model's reply through "the bridge… a separate, optional component that watches threads and invokes the runner (`runner.md`)" — the runner declined as WQ-15. Loom cannot wake an agent and should not: it would mean holding credentials and tracking vendor flags that churn. The agent pulls open comments through `loom status` and answers with `loom comment --reply`. `POST /_api/message` stays and means what its own first sentence says: *"a thread with no bridge is a place people write to each other."*

**§2 has two rows invalidated by 0.10.** `/_api/thread` is described "as `loom ai start`", which no longer launches anything; and `/_api/discard` takes `{record}`, a file path, which the annotation log abolished — discarding is by run, and by annotation id for a finding an agent withdraws.

**What is built.** `render/serve.py`'s `LoomHandler` extends `SimpleHTTPRequestHandler` with `do_GET` and `do_HEAD` only, so this is a `do_POST` on the same handler and a `GET /_api` for discovery. `ThreadingHTTPServer` is already bound to `127.0.0.1`, which is what §3's "no authentication in version 1" rests on, and the binding is worth an explicit test rather than an assumption. Every endpoint wraps a CLI function that 0.10 already shaped as a library call; every successful write triggers a republish and the viewer sees the change through the manifest as usual.

The endpoints this plan needs: `comment`, `reply`, `resolve`, `edit`, `discard`, `refs-note` (accept and reject). `accept`, `thread` and `message` are specified and may be built here or left 404 — a viewer that receives 404 shows no affordance, which is the discovery mechanism working as designed.

**`--json` on write commands is not in this plan.** It is WQ-34's first item and the editor clients are its consumer; the write API calls the library functions directly and needs no text to parse.

## Part H — The four annotation surfaces

WQ-26, absorbed 2026-09-17. All four share the write path and the log, and the author confirmed on 2026-09-18 that all four stay in: splitting them back out would partly undo the absorption.

- **Writing an annotation.** Select text, write, choose kind and severity; appended with `author` the person and `kind: human`. The quote is computed from the selection as `write-api.md` §5 specifies — mapped back through the block's `data-src` to source text, falling back to the whitespace-normalised match and then to a whole-block comment.
- **Payloads inline.** A suggestion's text rendered in red beneath its anchor, placed by its `placement` hint, with the verbatim toggle and copy beside it. Preview and copy only; applying is WQ-27.
- **Reference notes.** `reference-notes.jsonl` read and shown per node — the suggested works, who accepted them, from which run — with accept and reject as actions, each taking an optional reason. 0.10 ships these as `loom refs note` only; this is where they become buttons.
- **Whole-document annotations.** Shown at the top of the document in the read view, and first in the run's report. Needs no interface change (Part A).

**One arras-side defect blocks these, and its fix is Part I's rule wearing different clothes.** Annotation kind is an open string used as a CSS class — `fragments/mount.ts:86` (`'k-' + first.kind`) and `:136` — and every rule that styles it enumerates exactly four kinds: `AnnotationBox.svelte:71-92`, and `theme.css:588-591`, `:599-602`, `:633-636` for the margin mark, the block edge and the count button. So 0.10's `citation` renders unstyled in all three. **A fixed palette of four is a publisher's vocabulary written in CSS**, which is the same fault R2b is removing from the copy, and the fix is a default style that any kind falls back to rather than a fifth rule.

The filter beside it is already right and is the model: `AnnotationPanel.svelte`'s kind list is `$derived` from the annotations actually present, with the reason in a comment — *"a publisher may use kinds this viewer has never heard of, and one it cannot offer is one nobody can filter by"*. What the write surface still needs is a kind **chooser**, which is a different control from a filter: it offers what a person may create, where the filter offers what is there.

## Part I — R2b of the arras refactor

0.9.5's weave puts R2b in this plan. All three parts land here, and the first has a mechanical finish line.

**The vocabulary leaks of §4(b).** "not yet compiled" renders on every node of a corpus that compiles nothing (`routes/node/[...key]/+page.svelte:87`, and again at `routes/+page.svelte:52` and `routes/master/[stem]/+page.svelte:109`), "loose: no document reaches this node" on every node of a corpus with no documents (`routes/node/[...key]/+page.svelte:143`, and bare "loose" at `:177`); `worklink.ts:15` compiles `const PREFIX = 'loom:'` into the core (corrected 2026-09-18: this was not a leak — `loom:` was the *interface's* scheme, so arras naming it was arras implementing the format. The real fault was that the interface named its own URI scheme after one of its publishers, and the scheme is now `cited:`, DR-166); `loader.ts:32` emits the diagnostic code `loom:interface-version`, which is arras talking about itself in a publisher's namespace. `PdfViewer.svelte` is on the exemption list for a doc comment naming the scheme, so emptying the list includes rewording that comment.

**This plan is done when both `PENDING_R2B` lists are empty.** That is a mechanical check on a design question, and it is why the lists were written as lists rather than as a note.

**The `publishes` capability block** of 0.9.5 §9: what a corpus has, never what to draw. The scheme name moves into `manifest.publisher`.

**The host's own root, and the token scope.** `theme.css` opens with a global `*` box-sizing reset and declares every token on `:root`, so arras styles a page it does not own. `tests/unit/host-neutrality.spec.ts` already states the rule it should meet — *"tokens go on a class the host applies"* — and carries `OWNS_TOKENS = 'src/lib/theme.css'` as its one exemption. The tokens move to arras's own scope and the reset scopes with them, so a host restyles with an ordinary stylesheet at ordinary specificity: one bundle, two looks, which is most of what 0.9.5 §2 meant by *"a personal site must not look like `loom serve`"*. **Done when `OWNS_TOKENS` leaves that file.** The guard's other exemption is not debt and stops describing itself as debt: `prefs.svelte.ts` writes preferences onto `documentElement` and its comment says *"until seam 2 it is the app's own root"* — with seam 2 declined, the app **is** the host and owning its root is simply correct.

**The derived view list.** `shell/views.ts:14-24` returns the same six views for every corpus and `INDEXES` is a module-level constant evaluated at import; `routes/taxa/+page.svelte:11` has no `{:else}`, so an empty `taxa` yields a heading over nothing. This plan adds views anyway, so deriving the list while the file is open costs almost nothing and doing it afterwards means editing the same file twice.

## Sequencing and gates

Larger than 0.10 and it should land in six commits, each green on its own. The author asked for explicit internal gates rather than one push.

1. **Part I (R2b).** No new surface; it changes what every existing one says. Doing it first means the four views this plan adds are written neutral rather than corrected afterwards. **Gate: both `PENDING_R2B` lists and `OWNS_TOKENS` gone from the guards, not emptied; the minimal suite green with `FORBIDDEN` unexempted.**
2. **Part A (the publisher).** Pipeline, report parsing with the math pass, `build/source/`, the stale `bundle` kind. No arras change. **Gate: loom's tiers green; a parsed report round-trips through `validate-dialect.py`; fixtures regenerated.**
3. **Parts B and C (report pane and split view).** The plan's centre. **Gate: an e2e test that clicks a finding in the report and asserts the left pane scrolled to its anchor, and the reverse.**
4. **Parts D, E and F (closure panels, verbatim toggle, notation).** Reading surfaces, no write path. **Gate: source fetched lazily, and an absent `build/source/` degrading to rendered-only rather than to an error.**
5. **Part G (the write API).** **Gate: `GET /_api` discovery; every endpoint tested against a scratch quilt; a test asserting the socket is bound to `127.0.0.1` and not `0.0.0.0`.**
6. **Part H (the four surfaces).** The write API's first consumer. **Gate: a comment written in the browser appears in `annotations/log.jsonl` with `kind: human`, and a reference note accepted in the browser appears in `reference-notes.jsonl`.**

Then the book, the specs, the records and the queue as one documentation commit against what was built.

## Risks

- **This plan is large.** Six parts touch arras and three touch loom, and the write API is a new surface area with its own security story. The gates above are the mitigation and they are not optional; a part that lands ungated will be the one that is wrong.
- **The math pass is the only genuinely new machinery.** Everything else is a derivation over data that exists. Its failure mode is quiet: a report renders with `$x$` as literal text and looks merely ugly rather than broken, which is how it would survive review. The dialect validator run over a parsed report is what makes it loud.
- **The write API is the first thing in this system that accepts input.** §3's "no authentication in version 1" rests entirely on the socket being bound to localhost. That is true today and is an assumption, not a test, until Part G writes one.
- **R2b first will feel like the wrong order.** It delivers nothing visible and it is the commit most likely to be deferred under pressure. It is first precisely because every later part writes text that the lists forbid, and correcting four new views is more work than writing them neutral.
- **`interface_version` stays 1 and every change here is additive** — but `pipeline` on the thread object is the kind of field a viewer starts to assume is present. It is optional, a corpus without modes emits an empty list, and the minimal fixture must exercise exactly that.
