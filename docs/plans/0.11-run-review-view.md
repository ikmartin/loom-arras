# 0.11 — Reviewing a run in arras: the split view and the notation panel

**Status: reminder**, written 2026-09-17; becomes the plan once [0.10](0.10-annotations-and-review.md) is built and tested. This is where [WQ-23](../work-queue/WQ-23-agent-review.md) graduates: its trigger is "the author resumes the design", and 2026-09-17 was that.

## What exists and what does not

Of the WQ-23 prototype's five views (published at <https://claude.ai/artifact/DNKQMbKsdXCLLVgDn4TXvT>, source in `docs/work-queue/WQ-23-agent-review/`), only the highlights are built — comments as colour-coded marks that expand on selection, from plan 0.6. Checked against arras on 2026-09-17: no run review route (`/thread/<id>` lists a run's annotations, unsplit), no run selection, no highlights following a run, no annotation severity (the only `severity` in the types is the diagnostics'), no notation handling.

## The split view

The draft on the left, a run on the right with **Report and Journal** tabs (this plan renamed the second: there is no transcript, and `thread.md` is a journal — see the report pane below); the right pane cycles through runs — a pipeline, an earlier run, your comments, all runs — and the draft's highlights follow the selected run. The panes scroll independently and the strip stays fixed; "show in report" scrolls only the right pane, selecting a finding in a report scrolls only the left. Launched from the agent's closing line in the chat (`localhost:8791/review/<run>`), from a run in the threads index, and from any finding on a node page. Findings ranked by severity from 0.10's log; `[R1]…` display numbers from the report. The author: "nearly exactly what I want".

**One addition the workbench makes possible and that is cheap now and expensive later:** the left pane is a versioned text and a run was made against a specific version, so the pane says which — "run against `rl-0012@4`, now @5" — from the annotation's `against` hash and the ledger. That is the split view's honest answer when highlights no longer line up.

"Node and evidence" is what the split view gives when a finding is clicked, with 0.7's `loom:` links into a paper as the evidence; it needs no view of its own.

## The report pane: markdown authored, blocks parsed

Settled with the author on 2026-09-18, with three designs demoed side by side.

**The problem.** Nothing renders an agent's report. `/thread/<id>` lists attachments by filename, so you can see that `referee-dm-0003.notes.md` exists and not what it says — and the terminal cannot help, because no agent CLI typesets mathematics, so everything read in chat is LaTeX source. The notes files already contain real LaTeX against the quilt's macros; they are simply never rendered.

**And `thread.md` is not this.** Orientation §6 says it plainly: *"after each significant exchange, append a dated entry… a later session (yours or another agent's) resumes from it."* It is an agent-to-agent handoff, and it is doing its job. The Transcript tab named in this plan's split view was a word with nothing behind it — loom cannot see a chat and should not transcribe one. **The tab is the Report, and the second tab is the Journal**, which is `thread.md` under its real name.

**The design: parse the brackets.** The agent keeps writing one markdown file, exactly as now. `blocks.md` already mandates *"Write each block under a heading with its name in brackets"*, and every finding already ends with its annotation id — `(a-2026-09-17-0001)` — and every annotation already carries a quote selector with prefix and suffix. So loom parses the bracketed headings into blocks at build time and links each finding's trailing id to its annotation, which anchors into the draft. No new format, no change to how agents write, nothing to version, and an unparseable file degrades to one block.

Two alternatives were considered and rejected. *Rendering the file whole* is nearly free — `render_markdown` exists at `records/store.py:443` and already serves annotation bodies — but it gives a document you can read rather than one you can use: "show in report" has nothing to scroll to, because the bracketed names are text that merely looks like structure. *Blocks emitted through a CLI* (`loom report block referee-review …`) makes the completeness check mechanical, but it is eight heredocs where there was one file, agents author markdown well and author through a CLI badly, and it invents a format that must then be versioned. Parsing gets the structure for free because the structure was always written down; nothing was reading it.

**Why this plan and not 0.10.** The Report pane is not a document viewer, it is a navigable index into the draft, and this plan is what needs that: *"'show in report' scrolls only the right pane, selecting a finding in a report scrolls only the left."* Both require a finding to be an addressable object with an anchor. 0.10's only obligation is to keep the bracketed headings mandated in `blocks.md`, which are now load-bearing.

**The one piece of real work** is math. `render_markdown` is markdown-it/commonmark and emits `$…$` as literal text; the dialect wants `<span class="math inline">\(…\)</span>`. A math pass makes the rendered report dialect-conformant, at which point `validate-dialect.py` checks it like any other fragment and the quilt's macros resolve.

## The verbatim toggle (moved from 0.10)

Planned as Part G of [0.10](0.10-annotations-and-review.md) and not built there: what 0.10's arras commit actually delivered was the manifest's new fields, the `record` → `run` repair, the severity chip and the payload preview. The toggle needs a source-fetch path arras does not have, and it reads beside the report pane rather than ahead of it.

Per node and per payload, in the box's upper right, revealed on hover and focus with a preference to always show; flips the body between rendered and source, paired with **copy** and **copy for chat** (the key in the author's tag syntax plus the text). "Source" is the node's own text before macro expansion; for a payload, the payload; for a digest node, the digest's statement.

It comes from `build/source/<key>.tex` fetched lazily — the manifest is already 772 KB on relloc and would nearly double with source inline. `lib/paths.ts` has `dataUrl()` for build-directory files, but there is no source-fetch path and no `build/source/` in the interface, so the publisher's output and `specs/manifest.md` both gain it. Needs no write API.

## Closure views on the node page

`loom bundle` is deleted in 0.10 — the agent reads a closure from a command that prints, and what a *person* wants is a view. Both of these are built from data arras already has, and neither writes a file.

- **The local graph already exists.** What it lacks is navigation: you cannot move to the nodes within it. That is the whole change.
- **A stacked closure view**, as a view on the node's own page: the closure in dependency order with the node last, at **depth 1 or depth 2**, the depth being the reader's choice. This is the bundle's own shape, as a page, for reading an argument through.

## The notation panel

Notation belongs to agent prose only — reports, explanations, transcript messages — never `nodes/` or `drafting/`. The agent declares a `[notation]` block once per run; arras marks each declared symbol by TeX token inside the run's math, lists them in an expandable panel on the run pane, previews the definition on hover, and flags a second meaning for one symbol within a run. Settled with the author on 2026-09-16.

## Annotation surfaces (WQ-26, absorbed 2026-09-17)

WQ-26 graduates into this plan rather than trailing it, at the author's decision. Four surfaces, which share the write path and the annotation log:

- **Writing an annotation in arras**: select text, write, choose kind and severity; into `annotations/log.jsonl` with `author` the person and `kind: human`.
- **Payloads inline**: a suggestion's text rendered in red beneath its anchor, placed by its `placement` hint, with the verbatim toggle and copy beside it. Preview and copy only; applying is WQ-27.
- **Reference notes**: `reference-notes.jsonl` read and shown per node — the suggested works, who accepted them, from which run — with accept and reject as actions, each taking an optional reason. 0.10 ships these as `loom refs note` only; this is where they become buttons.
- **Whole-document annotations**: an annotation whose target is a document rather than a key. Loom has written these since 0.6 (`loom comment` takes "a key, an equation's qualified key, or a master path") and arras has never shown one: `src/routes/master/[stem]/+page.svelte`'s `commentsOn(key)` is only ever called with node keys taken from the rendered fragment, and `master.path` is never passed to it. Shown at the top of the document in the read view, and in the run's report. **The manifest already expresses it** — the annotation's `target.key` is the master's `path` and `m.masters` carries `path` — so this is arras-side only, needs no interface change, and is a core derivation that R3 relocates rather than rewrites.

**This pulls the write API into this plan.** WQ-26's own reason for deferral was that arras has no write API and this is the item that needs one, so `docs/specs/write-api.md` is built here, with §4 rewritten first: it still routes a model's reply through the runner declined as WQ-15. Loom cannot wake an agent and should not; the agent pulls open comments through `loom status` and answers with `loom comment --reply`. If that proves too large beside the split view, the honest split is display before input — whole-document annotations, payloads and reference notes *read* need no write API, and only the first surface does.
