# 0.21 — MCP: how agents attach to loom

## Context

Agents work in a quilt today through loom's command line. Loom writes a permission file listing which `loom` shell commands an agent may run, and a prose orientation tells the agent what they do. Relloc's session of 2026-10-12 to 10-26 showed what that costs: permission rules that matched nothing (DR-275-ikmartin, DR-343-ikmartin), LaTeX mangled by shell quoting (an agent wrote `y^\prime` to get past it), and an orientation of about 48 KB. This plan makes MCP the way agents attach. It was discussed by the author with the Quilt review session and loom-arras on 2026-10-26; the design is `docs/design/agents.md`, and principles are cited by name from `docs/design/principles.md`.

The author decided on 2026-10-26, in his words where quoted:

- **MCP is the intended way for agents to attach.** It "should be the intended way for agents to 'attach' or 'interact' with loom", and "agents attaching to loom should have the full capabilities provided by the MCP".
- **No vendor is assumed.** "Chat GPT, Claude Code, Gemini and local agents should all be able to use loom."
- **Shell permissions for agents are generated on request,** for an agent without MCP such as Aider. Loom keeps both settings variants, and `loom doctor` checks whichever applies.
- **Two bridge tools replace the chat composer** as the way the person points an agent at something:
  - *where the person is looking*, down to the selected words or the PDF page and region, from the viewer tab touched last;
  - *what the person did since this agent last looked*: their annotations and replies, and their acceptances (including keys gone stale), with one marker per agent name.
- **Code execution is out of scope.**
- **Order:** the viewer plan (0.20) comes first, and this plan follows it. 0.20.1 deletes the launcher, the `--settings` preset and `ai-config.toml`, and leaves `session next`, `session watch` and the inbox to this plan.

What this plan is not: loom calls no model and holds no key (P9); the MCP server is a client of loom like the language server, and no command requires it (P8); and nothing about the author's own command line changes.

## How this plan is carried out

One master document, as 0.20 is. Each phase starts in plan mode: the code is explored, the concrete changes are proposed and the author approves them. When a phase is built and `scripts/verify full` passes, what was built is appended to **Implementation** at the bottom, with anything that departed from the phase as written. A phase that changes what loom generates for an agent client is also tried against the real client (the `client` test tier from branch `review-findings`) before its commit. Nothing is committed until the author says so.

## 0.21.1 · The agent contract cut

The orientation becomes the MCP server's instructions, so it is cut before the server is built. In `loom/src/loom/assets/ai/`:

- **`orientation.md` becomes pointers:** what a quilt is, the boundary (what only the author does), and where everything else lives (`loom status`, the tools, `loom --help`). It stops restating the command tree.
- **`rules.md` keeps what protects trust:**
  - the boundary;
  - `--as` on every write;
  - page-checked quotations;
  - agent documents kept apart from the author's;
  - findings as annotations.
- **`rules.md` drops what only adds friction (P14):**
  - the per-mode check scripts of rule 7;
  - the epistemic label on every chat claim (it stays on durable claims);
  - `[summary]` and a ticked checklist on every notes file (kept only where a report is read later);
  - modes as the default framing.
- **Transcripts.** Add the instruction from the design: write the transcript so that someone coming back later sees the main points, what was decided or found, what is open, and links to what came of it.
- **Bugs to fix:** `--kind conf` is advertised and refused (`full_kind`); "the session's directory is your scratch directory" contradicts `build/SESSION/`; "you may remove what you created" contradicts the rule that nothing is deleted from a session; and two different rules are both called rule 7.
- **The mode files** stay as tools a person or agent reaches for, with their output contracts trimmed to what a reader uses.
- **Commands the modes want,** carried from WQ-32's reverse pass (closed into this plan): every key whose proof cites a given hypothesis; what changed in a key since an annotation was written; a document's results in order with their states; a section of a document as a selector (`section 2 of drafting/main.tex`); and a key's text at the version under review. Plan mode decides for each whether it is a flag, a command, or something the agent composes itself, and says which.

## 0.21.2 · The server

`loom mcp` runs a stdio MCP server for the quilt it is started in, found the way every command finds one. The `mcp` package is an optional extra (`loomtex[mcp]`), so a quilt without agents installs nothing new.

- **Tools.**
  - One tool per entry in `AGENT_COMMANDS`, generated from the click command tree and named by its path (`loom_status`, `loom_library_propose`), so each tool keeps its command's name (K7).
  - Left out: `serve`, and `session next` and `session watch` (0.21.5).
  - The schema is derived from the click parameters. Rules between options stay refusals at run time (K3), so `annotate` gets a flat schema.
  - The author's acts are not tools at all.
- **Results.**
  - Text by default, as T1–T5 shape it for this reader, with a `json` flag on each tool that prints JSON.
  - Exit 0 and 1 are results, and 1 carries a flag, since lint and check exit 1 with a complete report. Exit 2 is an error carrying the refusal's text.
  - A result over a size threshold (to be set from measurement, below every client's own limit) is written to a file under `build/SESSION/`, and the tool returns its path, so the agent's own file tools can search it.
  - Every result, and `run.log`, carries the equivalent `loom …` command, so a person can rerun it.
- **Read-only.** Read-only tools carry `readOnlyHint`, from the same table, so a client can skip approval prompts for them.
- **Identity.**
  - The server is started with the agent's declared name (`--as`) and sets `AI_AGENT` for every command it runs, so K5's guard sees an agent.
  - It refuses to start under a name that does not say it is an agent.
  - `--as` is then no longer a parameter of any tool.
- **Instructions.** The server's instructions are 0.21.1's orientation, so an agent attached over MCP is oriented without a shell.
- **Tests:**
  - the tool list equals `AGENT_COMMANDS` minus the exclusions;
  - no author command is reachable;
  - the exit-code mapping;
  - a schema snapshot, so a changed flag shows as a diff;
  - identity is refused for a non-agent name;
  - a large result goes to a file.

## 0.21.3 · Configuration

`loom ai init` (and `loom upgrade`) generate what each client needs, from the same table, and never a file someone else committed.

- **Project-level config, written and gitignored:**
  - `.mcp.json` for Claude Code;
  - `.gemini/settings.json` for Gemini's CLI, if it still reads project settings when this phase is explored.

  Each names `loom mcp --as "<Client> Agent"`, so each client has its own agent name. A clone carries none of them, so cloning someone's quilt never runs their command.
- **User-level config is printed, never written.** For a client whose MCP config lives in the user's home (Codex's `~/.codex/config.toml`, Cursor, VS Code, LM Studio and others), `loom ai init --client NAME` prints the snippet. Loom writes nothing outside the quilt.
- **Permission files have two variants:**
  - **The MCP variant** (default): allow `mcp__loom__*` and the agent's write directories; deny `Bash(loom *)` as a guard against mistakes. It is never described as the boundary, which stays the orientation's statement of the author's acts plus K5.
  - **The shell variant**, on request (`--shell`): today's allow list of `Bash(loom …)` rules, for an agent without MCP.

  `loom doctor` works out which variant a quilt uses and checks that one.
- **Vendor pointer files.** `CLAUDE.md`, `AGENTS.md`, and `GEMINI.md` (new) keep one line of loom's: use the loom tools, or `loom ai orient` from a shell.
- **The `client` tier** (opt-in, `LOOM_CLIENT_TESTS=1`, never in CI) gains a test per configured client: the real client starts the server, calls a read tool and a write tool, and is refused an author command.

## 0.21.4 · Prompts and resources

- **Modes as MCP prompts.** Each mode file is offered as a prompt (`/loom:review` in Claude Code), taking a key where the mode does. A prompt is something a person reaches for; nothing makes it the default framing.
- **Resources,** read-only, at the addresses `loom link` already prints (`quilt:KEY`):
  - a key's own text;
  - its closure;
  - a document, flattened;
  - a page of a cited work's text.

  An agent can then `@`-mention a result instead of asking for it. A client that does not read resources loses nothing, because the same reads are tools.

## 0.21.5 · The bridge

The bridge is two new commands. They are commands rather than MCP-only tools, so that the server generates them like the rest, a person can run them, and their results carry a command (K1, P8). Their names are proposed here and settled in the phase.

- **`loom here`: where the person is looking.**
  - The viewer reports the reader's place to `loom serve` through a new write-API action, debounced, on every change of focus, scroll or selection: the focused pane's active item (`workspace.current`), the block at the top of the pane, the selected words or PDF page and region, and the selected session (plan 0.20, "For plan 0.21").
  - `loom serve` keeps it in memory and never writes it to disk: it is where the person is, not a record (P2).
  - The tab touched last wins. A selection in Review is reported as the block under review, not as a reading place.
  - `loom here` reads it back over the local API with the token in `.loom/serve.json`. With no viewer open, it says so and points to `loom serve`.
- **`loom since`: what the person did since this agent last looked.**
  - It reports annotations and replies written by people, with their quotes and proposed text, and acceptances, including keys that went stale, since the agent's marker.
  - The marker is kept per agent name in a cursor file loom owns and does not commit, as the inbox's cursors are today, and moves forward when the report is read.
  - "By a person" means a declared name that does not say it is an agent.
- **`session next` and `session watch` are retired.** With the composer gone, only agents write to a session's inbox, so there is nothing to wait for, and `loom since` answers the question `next` used to. `loom session say` stays: it is how an agent writes the transcript. The inbox stays as the transcript's store.
- **The design.** `docs/design/agents.md` loses its two open questions on these points; the transcript instruction from 0.21.1 is already in place.

## Out of scope

- **An HTTP transport,** for front ends that cannot start a stdio server such as Open WebUI, until someone needs one.
- **Claude Code's channels** (a research preview), which could later push a viewer message into a running session.
- **Cloud agents,** which would need loom installed where they run.
- **A notes tool,** which arrives with the notes plan; this plan leaves room for it.
- **Code integration,** which is deferred.

## Behaviour that must survive

- The author's acts refuse an agent in any shell, whatever name it declares (`refuse_under_agent`, K5).
- Every command runs from a terminal with no server (P8).
- `loom session say` and the transcript.
- Annotations land in the selected session.
- One allow table, from which every permission file and every tool list is generated.
- Generated agent configuration is never tracked and never one someone else wrote.
- An agent's writes stay within its session's directory, `build/SESSION/` and `drafting-ai/`.

## Verification

`scripts/verify`: `fast` while working, `full` before each phase's commit. The `client` tier by hand for every phase that changes what loom generates for a client (0.21.3 onward), with the client versions recorded in **Implementation**.
