# Implementation plan: readable node names and explanatory graph interaction

Status: implemented in the working checkout on 26 September 2026. All fast checks pass; full verification has the environment limits recorded in Section 13. Existing user changes were preserved. The baseline analysis and task breakdown below describe the agreed scope; Section 13 records delivery.

## 1. Outcome and scope

A reader should be able to identify a result, read its statement, and understand its immediate and downstream relationships without memorizing Loom IDs or leaving the graph. Keep IDs as stable addresses and retain existing document membership marks, scope controls, graph modes, review state, and navigation.

The graph work has four connected parts:

1. An optional author-controlled node name, with a common display policy across Dots, Boxes, local graphs, previews, and Review.
2. Selective, collision-aware labels in Dots, with additional labels on hover, keyboard focus, selection, and zoom.
3. A persistent statement preview and relationship explanation for the selected node, including direct versus transitive dependencies and directional paths.
4. Drawing choices that follow Scope: Dots and Box for Whole quilt; Dots, Box, Sections, and Reading Order for one document.

This plan does not implement AI adoption, automatically generate names, add a source editor, change default graph scope, introduce semantic clustering, or infer dependencies from mathematical prose. Names authored in AI drafts can eventually travel with those drafts through incorporation; that workflow is independent of this work.

Example box:

```text
Uniform energy bound
Lemma 3.2 · A priori estimates
zk-0001
```

The dependency lists and highlighted paths show recorded relationships, not assertions about mathematical importance or completeness.

An additional user-requested task records and ships the Codex integration files needed to select Codex during quilt initialization; see Section 11. It can be implemented independently of the graph phases.

## 3. Node-name source contract

### 3.1 Syntax and ownership

Introduce the optional single-line directive inside a node's own source region:

```tex
\begin{lemma}\label{zk-0001}
% !LOOM name: Uniform energy bound
...
\end{lemma}
```

The name is plain Unicode text. Trim outer whitespace; preserve case, punctuation, and meaningful internal text. Do not parse it as HTML, Markdown, or executable TeX. Long names remain intact in source and metadata; individual surfaces may visually truncate them. Names need not be unique and are never targets for `\ref`, `\uses`, URLs, ledger keys, or allocation.

Support environment nodes, sections, and explicitly identified proof nodes. An ordinary attached proof without a separate node identity is displayed as “Proof of <owner name>”, with its existing proof key retained. Do not attach one name to a parent and child simultaneously: ownership follows existing own-text ranges.

`name` is node-local. Exclude it from file-level inheritance alongside the existing treatment of `basis`. A directive outside any eligible node produces a location-bearing warning and supplies no name. An empty value warns and falls back to the existing title. Multiple name directives in one node warn; use the last value consistently with current directive assignment, with an empty last value producing fallback. Register diagnostic codes and severities through the existing diagnostic mechanism.

Never rewrite author source automatically to populate names. Existing untitled nodes remain valid.

### 3.2 Identity, history, and acceptance

Names change display, not identity. Renaming preserves links, references, graph selection keys, comments' target keys, and node allocation. Existing duplicate-ID conflict handling remains authoritative; do not choose a name from one conflicting definition and hide the conflict.

**Revised requirement: changing only a display name must not stale mathematical acceptance or invalidate a pending mathematical OK.** The earlier draft preserved directive hashing at the cost of surprising the user; documentation would not make that behavior intuitive.

Implement this narrowly. First map the existing own-text, acceptance, snapshot, annotation, and history hash call sites. Preserve complete source, including names, in content-addressed snapshots and history. At the mathematical freshness boundary, compare text with recognized node-local `name` directives excluded; all other directives retain their current meaning. Use the same comparison for dependency freshness and pending review decisions. Never strip names from the shared snapshot/hash normalizer, and do not reuse a mathematical fingerprint as the address of raw historical text.

Existing acceptance records must remain readable. If their stored hash cannot be compared directly under this rule, derive the comparison from the saved snapshot without rewriting the ledger. Missing snapshots must retain the existing conservative behavior rather than being declared fresh. Specify the exact fields and comparison sites after inspecting those call paths, before coding; avoid a general-purpose new versioning framework. Annotation anchoring and full source diffs retain the source version they were written against.

This is a small but substantive cross-cutting requirement, not a label-only change. Tests must prove that a name-only edit preserves acceptance and pending OK, a mathematical or basis edit still invalidates them, and historical names remain retrievable. Conversion checks must show that names travel with their owning nodes through atomize and inline without appearing in the typeset paper.

### 3.3 Manifest contract

Publish `nodes[id].name` as an optional nonempty string when a valid name exists. Keep `title` as the existing source title. Absence means use the normal fallback. This is an additive interface-version-1 field, subject to the existing loader's compatibility tests. Update the TypeScript Node type, manifest specification, fixture examples, and publisher tests together.

Search should discover the explicit name as well as the ID, existing title, and aliases. Inspect the current search producer and consumer before choosing an additive search field or composing searchable text; preserve all existing search terms. The name must not become a reference alias merely to make it searchable.

## 4. One shared display policy

Add a pure shared formatter, provisionally `arras/src/lib/nodes/display.ts`, accepting the manifest, a node or proof key, and optional master context. Return structured identity data rather than an HTML string: primary name, type/number, section context, ID, and accessible label.

Primary-name precedence:

1. Explicit `name`.
2. Existing nonempty title.
3. Type plus number in the selected document.
4. Stable ID.

Avoid repetition: when “Lemma 3.2” is already the primary label, do not repeat it on the context line. Keep the ID visible in Boxes and the inspector, but avoid printing it twice for an unnamed fallback. Titles use the current publisher's text conversion; explicit names render as escaped plain text.

Document numbering and section parentage are contextual. Within a document scope, use that master's `numbers` and `parent` entries. In Whole quilt, show type without a document number or section subtitle rather than treating the default document’s number as globally valid. The existing document scope selector supplies that context when wanted. This avoids a second numbering mode and the opaque “Multiple document contexts” label. A missing compile number is an ordinary fallback, not an error.

Apply the formatter to main Dots and Boxes, local dots and boxes, section/reading result rows, node previews, and review links including dependent-block links. Keep graph/layout and presentation-specific shortening outside the formatter. Proof rows must remain distinguishable from statement rows and from one another: use the existing proof number or identity when several proofs belong to one named statement.

## 5. Box layout

Use a consistent larger box with three text lines: name, type/number/section, and ID. Start with one shared size of approximately 220 × 72 diagram units, then tune it by visual inspection. Pass this same size to ELK and rendering so edges meet the correct boundaries. Keep membership marks in a reserved area.

Use one line per text role and truncate names or section context with an ellipsis when needed. Keep the full name in the selected preview and accessible label. Measure only as needed to truncate accurately; do not add content-dependent box dimensions, wrapping, font-load relayout, or a second sizing cache. Boxes remain fully labeled. If real documents demonstrate that truncation prevents recognition, revisit variable sizing with that evidence.

Named sections follow the shared identity policy. Reference-paper nodes retain their existing work-title behavior. Small local Boxes can retain their compact layout while using the same name formatter; they need not grow into three-line cards.

## 6. Selective Dots labels

### 6.1 Placement and density

Create a pure placement helper, provisionally `graph/labels.ts`, operating on projected screen coordinates, measured text bounds, viewport bounds, and an ordered set of candidate labels. Use screen coordinates so overlap tests remain correct under zoom, SVG letterboxing, responsive size, and node dragging.

At overview scale, prioritize the selected node, hovered/focused node, their immediate neighbors, then other nodes in a stable ID order. Do not rank ordinary labels by connectivity; that adds an unexplained preference for heavily linked results. Exclude offscreen ordinary labels. Try below the dot, then above it; reject placements that collide with accepted labels, other dots, or membership marks. Begin with a straightforward greedy placement pass. Add a spatial index only if measured interaction cost requires it.

Zoom reveals more labels because dots separate in screen space. Keep text within a readable CSS-pixel size range instead of allowing it to shrink or grow without bound. Rerun placement at most once per animation frame for pan, zoom, resize, and drag; these interactions must not rerun force simulation. Use deterministic priority and candidate positions so unchanged inputs do not flicker. Add placement-history caching only if visual testing shows objectionable movement; do not make it an initial requirement.

### 6.2 Interaction contract and dense neighborhoods

Hover or keyboard focus gives the active node and its immediate neighbors label priority in both directions. Click pins selection and opens the inspector. Existing selected labels remain high priority while hovering another node. Hovering does not replace the pinned preview or permanently change selection. Dragging a node must not accidentally trigger selection; retain a movement threshold.

A dense hub can have more neighbors than can physically fit. Do not satisfy “reveal neighbors” by overlapping them. Always show the hovered or focused node’s full label in an anchored callout if it cannot fit as a normal diagram label, then place as many neighbor labels as fit. Keep the inspector pinned to the selected node; its list must not pretend to describe a different hovered node. Clicking or pressing Enter pins that node and makes its complete named neighborhood available in the inspector’s current direction. The other direction remains one selector change away. Reuse the existing depth control to focus the view; add no new neighborhood action. Keyboard focus exposes a node’s full label, and every dot retains an accessible name.

Main Dots owns the complete selective-label interaction in this release. All local graphs reuse the name formatter. Reuse collision handling in expanded local Dots if it fits the existing component boundary; do not make a redesign of the small floating graph a delivery requirement. Keep Boxes fully labeled.

## 7. Explain selected relationships

### 7.1 Shared graph model and relationship lists

Reuse existing traversal code where possible, extracting a small shared helper only where lists and highlights would otherwise duplicate it. Compute adjacency once per manifest revision. Normalize proof endpoints to their owner as current result graphs do and remove self-links produced by that normalization. Retain original edges, edge kinds, and citation locations for rendering and explanations. Do not treat inclusion membership or `see` relations as dependencies.

For a selected result compute direct dependencies, direct dependents, transitive dependencies, and transitive dependents using cycle-safe traversal. A node reached both directly and through a longer path belongs in the direct group. Exclude the selected node itself from its relationship lists even inside a cycle. Multiple citations or statement/proof edges to the same result produce one list entry. Section and document endpoints remain navigable graph context and appear with their type in the same list rather than in a separate panel.

Compute relationship lists and paths from the active Scope graph (Whole quilt or the selected document), before taxon/tag/state/depth display restrictions. Label the list “Relationships in <scope>”. Traverse that graph without inventing paths through nodes outside it. Display restrictions can hide items: when they do, show one concise “Some related nodes are hidden by the current filters” notice and mark those entries in the list. Preserve filter behavior and do not silently clear filters. Keep document membership marks, the legend, and navigation to document locations.

### 7.2 Highlight and arrow contract

Keep the two existing controls: “what it rests on” and “what rests on it”. Distinguish the selected node, its direct neighbors in the chosen direction, more distant related nodes, and unrelated nodes with emphasis and edge weight. Preserve solid/dashed/dotted edge-kind patterns and document membership colors; do not reuse those channels for a second meaning. Avoid color-only distinctions.

Highlight the actual traversed edges for the chosen direction, rather than every edge whose endpoints happen to be highlighted. The edge set must preserve the path connecting the selection to each highlighted result. If an intermediate node is filtered out, do not invent a shortcut edge; report hidden context in the inspector.

Arrows mean **uses → depends on** everywhere. Dots shows arrowheads on selected relationship paths. Before selection, hover may reveal incident arrows; while a selection is pinned, hover does not add an unrelated arrow set. This keeps the preview, relationship list, and directed highlight describing the same selected result. Clip paths to node boundaries so arrows do not disappear under dots. Boxes retains its upstream-above layout but orient routed paths/markers to the same semantic direction; test this explicitly because current ELK paths run dependency-to-dependent. Arrowheads stay legible at different zoom levels. Use the short legend “Arrow points to the dependency.” Keep the explanation that Dots position is not directional in help text.

### 7.3 Inspector and rendered statement

Extend the existing inspector rather than adding a second selection panel. Keep the initial view compact: common identity header and state badge, rendered statement, one relationship list, and Open in document. The existing direction selector determines whether that list shows dependencies or dependents. Within it, distinguish “Direct” and “Indirect”; show direct items first and keep indirect items collapsed. Keep the existing source link and provide navigation to the existing node-context view for full document locations and other metadata. Do not recreate that view in an expandable Details area. Do not add four parallel lists, another direction control, a second preview panel, or a hover-driven replacement of the selected statement.

Extract or adapt the existing NodePreview rendering path for persistent use. Accept explicit master context instead of always using the default document. Reuse fragment fetching, math macros, and link wiring. Hide attached proofs in the statement preview, but offer navigation to them. A section gets a bounded summary and open action rather than loading an entire section into the rail. A missing fragment shows an explanatory fallback while identity and relationships remain usable.

Key asynchronous work by selected ID, master context, and manifest hash. Cancel or ignore stale fetch/typesetting completions on selection changes or unmount; clear old content immediately so a new heading never displays the previous node's statement. Live rebuilds refresh changed names and previews. On narrow screens, place the inspector below the graph or use the existing responsive panel behavior, preserving selection.

### 7.4 Drawing choices follow Scope

Offer only drawings that apply to the selected scope:

| Scope | Available drawings |
|---|---|
| Whole quilt | Dots, Box |
| One document | Dots, Box, Sections, Reading Order |

When the user changes Scope from a document to Whole quilt while Sections or Reading Order is selected, select Dots automatically. If Dots or Box is already selected, keep it. Switching from Whole quilt to a document keeps the current drawing and makes Sections and Reading Order available; do not automatically restore a previously selected document-only drawing. Switching between documents keeps any of the four selected drawings.

Hide the document-only drawing choices in Whole quilt rather than leaving disabled controls. Preserve the existing selection and filters under their normal validity rules; the mode fallback itself must not clear them. Keep document membership marks and the clickable document legend in both whole-quilt drawings, Dots and Box.

Implement availability and fallback together in the graph route so the selected drawing is always valid for Scope. Apply that rule to restored state or any URL-driven state as well as interactive scope changes, where those mechanisms exist. Invalidate outstanding layout requests when scope or drawing changes: an old Sections result must not replace Dots after switching to Whole quilt. Update the graph help and book wording to describe two quilt-wide drawings and four document drawings.

### 12.3 Supporting work is not a separate product feature

The additive manifest field, common formatter, traversal reuse, compatibility handling, async stale-response guards, packaging checks, and regression tests support the use cases above. They should not create extra UI or new configuration concepts. Keep each at the smallest boundary that prevents inconsistent names, incorrect relationship lists, stale previews, lost history, or missing installed assets.

Use one shared graph fixture for the chain, diamond, duplicate edges, cycle, document membership, and filter cases. Unit tests establish exact semantics; a small number of end-to-end workflows establish that the controls connect correctly. Real visual inspection checks crowding and readability. The real Codex smoke test checks CLI compatibility that mocks cannot establish. Those checks cover different failure modes and are not redundant implementations of the same feature.

### 12.4 Redundancies removed or bounded

- The graph inspector no longer grows an expandable copy of the node-context page. Full metadata remains one navigation away in the existing context view.
- Local graphs share names, but compact local views are not required to acquire full-page cards, panels, or label-placement controls.
- The existing direction selector owns one relationship list; there are no four parallel lists, extra direction selector, or new neighborhood button.
- Existing search and membership controls are extended or preserved, not duplicated.
- Automatic box sizing, font-driven relayout, connectivity ranking, speculative spatial indexing, and label-position caches remain outside the initial implementation.
- Hover and selection have separate jobs: hover identifies a candidate; selection owns the statement and relationship list. A hovered candidate cannot silently redefine the inspector.
- Stages can ship independently where their semantics are complete. Custom naming does not delay readable existing titles, and Codex setup does not delay graph work.

The requested tasks are useful as a group. The features with the clearest immediate return are shared readable labels, scope-valid drawings, and the statement preview. Custom-name freshness deserves the most engineering scrutiny because it crosses records and history; its complexity is justified only as the narrow guarantee that a cosmetic edit does not undo mathematical review.
