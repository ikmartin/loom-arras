## The one idea

Mathematicians write single documents; loom's value is in atomic structure. The workbench separates the two states a paper is in — *being worked on* and *fixed as a landmark* — and makes the passage between them the thing that leaves a trail: every canonization records what every node was at that moment, so changes between landmarks can be seen, addressed and reasoned about, per lemma, without git and without the author changing how they write.

The principle that governs every check below, to be added to Chapter 1 as a principle: **loom verifies what it can, reports what diverges, repairs nothing, and never blocks work.** The head is always the files on disk; the history is a log of what loom was told, not a claim about the filesystem.

## Vocabulary, settled

- **atomic** format: a document as a spine of inclusions over `nodes/`. **linear** format: a document with its environments inline. Verbs **atomize** and **linearize**. "Expanded" and "assembled" were rejected: "expanded" collides with TeX's macro expansion and loom's own `expansions`; "assembled" makes a reader ask "assembled from what?".
- **`drafting/`**: the directory of working documents; every `.tex` in it is live. Replaces `drafts/` as the masters directory. Chosen over `drafts/` because "drafts" reads as *versions of my paper*, which is what the canon is, and a drafting table is where work happens. Alphabetically beside `canon/`.
- **`canon/`**: canonized documents. Always flat and self-contained — compiles with plain LaTeX, no `loom.sty`, no `nodes/`, forever — because a landmark is what goes to a coauthor or arXiv, and history must never need loom to be readable. **Not scanned**: a canon document defines no nodes and is history, not source. Shown in arras all the same (below).
- **`.loom/history/`**: the record. Hidden because nobody should edit it; if someone does, loom reports that the record is corrupt and stops claiming otherwise. Loom is not a backup service; git is.
- Verbs: **`draft`** (canon → drafting), **`canonize`** (drafting → canon), **`stamp`** (a minor landmark), **`fork`**, **`revert`**, **`live`**. `work` was rejected because a *work* is a cited paper throughout loom (`refs/work/`, the work graph). `bench` was rejected as a noun in a verb's coat. `revise` was the runner-up.
- **Aliases** `canonicalize` and `canonise` are accepted and print one line, `canonicalize → canonize`, never silently.
- A **key** is what a version is a version of: a statement, named by its id, or a proof, named `<id>/proof` (or by its own id when labelled). Ids never contain `/` or `#`; keys can. Versions are per key because acceptance, hashing and review already use the key as their unit.

## Configuration

`config.toml` gains, written by `loom init` into every quilt: `[quilt] name` (the project's name, shown in arras as the project name instead of any document's title), `drafting = "drafting"`, `canon = "canon"`. The history directory is a constant with an override key that exists and is documented but is never written by init. User config (`~/.config/loom/config.toml`) may set any of the three; the quilt's config overrides it. Everything loom prints names the configured directory, never the literal. An existing quilt keeps working with `drafting = "drafts"`; nothing is moved.

## Layout

```
canon/
  paper-v1.tex                  flat, compiles alone, forever; not scanned
  paper-v2.tex
drafting/
  paper.tex                     live; linear defines its nodes, atomic includes nodes/
  talk.tex                      a second live document is fine; see the identity rule
nodes/                          definitions, where the format is atomic
.loom/
  state.toml                    the acceptance ledger, unchanged, still written only by loom accept
  history/
    ledger.jsonl                one line per event, append-only
    0001-paper-v1/              a step: import or canonize, named for the document produced
      paper-v1.tex              the spine as frozen (flat)
      preamble.tex              the preamble as of this step
      rl-0001.tex               versions of every key whose text moved
      rl-0001.proof.tex
      annotations.json          a cut of the annotation log (0.10)
    0002-stamp-referee-points/  a stamp: changed keys only, no document
    texts/
      <sha256>.tex              content-addressed texts: the old snapshots, and anchors (0.10)
```

`refs/`, `ai/`, `build/` are unchanged. `.loom/snapshots/` moves into `.loom/history/texts/`; its files are already named by sha256, so every reference in `state.toml` still resolves. `loom upgrade` performs the move — one recorded deviation from 4.8.2, since the directory is loom's own and nothing but loom writes it. `loom accept` and staleness keep working against the pool, untouched; the review system is rebuilt later on top of this plan, not in it.

## The history model

**Three tiers.** *Steps* are import and canonize: named landmarks of the document, one directory each. *Stamps* are declared minor landmarks: `loom stamp -m "…"`, one directory each, holding only the keys whose text moved since the last directory-creating event. *Anchors* (0.10) are texts kept only because an annotation points at them, content-addressed, never on the timeline. Nothing is ever triggered by saving a file. In linear format git cannot tell a lemma's history — it sees one file changing — which is what stamps are for.

**Numbering is quilt-wide**, `0001`, `0002`, …, over every directory-creating event. A per-node counter (`rl-0001-01`, `-02`) was the author's first sketch and was rejected because two nodes' "-02" would be different moments and the time axis would not line up. The step is carried by the *path*, never by a suffix on the id.

**Addresses.** `rl-0001@3` is canonical (the step number); `rl-0001@paper-v2` is an alias for the step that produced `canon/paper-v2.tex`, resolved through the ledger; arras shows the alias. A proof: `rl-0001/proof@3`. Version files: `history/0003-paper-v2/rl-0001.tex`, `rl-0001.proof.tex`. Gaps are meaningful: a key with versions at @1 and @4 was unchanged at 2 and 3.

**Canonize is document-scoped; the step is quilt-scoped.** `loom canonize drafting/paper.tex --to canon/paper-v3.tex -m "…"` (message required) linearizes the document into the canon file, and the step's directory records every key in the *quilt* whose text moved, including keys of other live documents. The ledger entry carries `document:` (what was canonized) and `froze:` (every key recorded), and which keys the document reaches, so a reader can tell A's canon from B's incidental state. Canonizing a file that is not live is allowed, warned about, and recorded as such.

**Stamp is quilt-wide.** `loom stamp -m "…"` freezes every key whose text moved anywhere in the quilt; `--in drafting/A.tex` narrows it to what one document reaches. Example: two papers in `drafting/`, `rl-0003` edited in A and `rl-0040` in B; a bare stamp freezes both under one message.

**A proof version records the statement version it was written against**: `of: rl-0001@3`, one hash. So an old proof is displayed beside the claim it argued, and "the statement moved under this proof" (proof@7 of @3, statement now @9) is a detectable fact rather than a guess. Cases that decided per-key versioning: statement unchanged and proof rewritten (node-level would say "changed", statement-level would say nothing); statement strengthened and proof untouched (per-key shows the uncomfortable pair); a proof split into a lemma and a shorter argument (add plus fork plus a proof whose `of:` moved).

**The preamble is stored per step**, since a lemma is nothing without its macros; for a stamp, only when it changed.

**Editing a canon file in place is a deviation, and a cheap one**: the step directory holds its own frozen copy of the spine, so `@3` means what was recorded regardless of what later happens to `canon/paper-v3.tex`. Loom reports `loom:canon-edited` naming the step and offers the resolution — canonize the edited file into a new document, making the edit a declared landmark. No step is ever created automatically.

**Ids are never reused.** Deletion is absence from every live document; a deleted node's history stays addressable and forkable. An id in history and in no live document is *retired*. The allocator (`next_local` in `scan/labels.py`) consults live ids **and** the ledger's retired ids from the day the ledger exists — derived on every call, never cached, because a stored maximum goes stale the moment someone writes a label by hand and then collides silently. Writing a node under a retired id is told apart by content: text hashing to one of that id's recorded versions is a **recovery** (`loom:node-recovered`, info; the timeline shows the gap); anything else is a **reuse** (`loom:id-reused`, error; fixes: fork under a new id, or `revert` to the recorded version). `loom revert rl-0012@4` is the recovery case by construction.

**The ledger entry**, one JSON line: `step` (for directory-creating events), `when`, `actor`, `action` (`import`, `canonize`, `stamp`, `draft`, `atomize`, `linearize`, `fork`, `revert`, `live`), `message`, `from` and `to` (paths with hashes), `document` and `froze` and `reaches` (canonize), `changed` / `removed` (ids), `parent` with how it was known (`declared`, or `inferred: 0003 (30/32 keys matched)` — inference is per key by hash, so a hand-copied and edited draft still gets a measured parent; only a file sharing nothing gets `unknown`), `ancestry` (fork: `new`, `from: id@N`, `in`), `superseded` (a conversion's input). Runs are referenced by their directory name, which is their id.

## The node identity rule and its failure mode

**The rule**, for Chapter 5: *a node is defined once and included many times.* A linear document defines the nodes it holds inline; an atomic spine includes nodes defined in `nodes/`. Every live document defines the ids it contains; no id may be defined by two live documents; anything not live defines nothing. Two papers in one quilt are unremarkable (the allocator makes their ids disjoint). **A node two documents need must live in `nodes/`** — sharing forces atomization of exactly what is shared, which is what `atomize --key` does. Spines including the same node files are unrestricted, as today.

**Liveness.** Everything in `drafting/` is live. The only file loom ever marks inert on its own is one a conversion superseded — `atomize` and `linearize` know with certainty that their output replaced their input, and record it. `loom live FILE` flips a superseded file back. No live-file list, no config key.

**Conflicts are conflicted, never resolved.** A second live definition of an id gives the id **no text**: it shows as conflicted everywhere it appears — its page, its box in every graph drawing, its row in every table — naming both files, with severity error, repeated on every rebuild while it stands (a single line scrolls away in a serve log). The rest of the quilt builds normally. Resolution by walk order was rejected as the one outcome nobody can debug.

**What breaks under two definitions, written out for the book**: the manifest wants one fragment per key and would pick by filename; a bundle would inline the closure from the other document and compile a paper corresponding to nothing on disk; hashes, staleness and acceptance ask for "the node's text" and there are two; an agent told to revise the node edits one copy while the other silently disagrees, invisibly. That last one is why the rule is structural, not a warning.

**The `--keep-shared` drift**, anticipated: `linearize --keep-shared` leaves `\input{nodes/rl-0001.tex}` for a node another live document includes, and writes the reason beside it — `% !LOOM shared: also included by drafting/A.tex -- \`loom fork rl-0001 --in drafting/B.tex\` to split` — since loom is the one writing that line. When the author later inlines it anyway, detection is specific: "`rl-0001` was shared with A and is now also defined inline in B; the inline text is `rl-0001@3` with two lines changed", with the three resolutions named.

`% !LOOM ignore` stays as the author's manual mechanism.

## Diagnostics

New codes, all produced by the scan or by the record checks, carried in the manifest, printed by `loom lint`, listed in arras's error panel:

- `duplicate-id` (error) — one id defined by two live documents; names both.
- `loom:superseded-file` (info) — a file a conversion replaced still holds definitions; it is inert. Exists to answer "why did editing this file change nothing?" One line per file, not per node.
- `loom:undefined-node`, `loom:orphan-node` — referenced and defined nowhere; defined and reached by no live document.
- `loom:history-edited`, `loom:canon-edited`, `loom:history-missing`, `loom:dangling-ancestry` — the record diverging from the files.
- `loom:id-reused` (error), `loom:node-recovered` (info).
- "This node's text equals @2" is **not** a diagnostic — nothing is wrong — but a badge from derived manifest metadata.

The word "definition" is never used in a code name: it is a taxon (`\begin{definition}`).

Two changes to the diagnostics model: a structured `fixes` list on every diagnostic (label plus the exact command), so the error panel can offer "fork it", "restore the inclusion", "rename the id" as three actions that copy three commands; and a second subject class, *the record*, grouped apart from *the source* in the panel because their fixes differ in kind. `/problems` is the error panel (loom's faults, bugfixing); `/review` is the drafting panel (decisions about the mathematics); they stay distinct.

**When checks run.** Node conflicts: in the scan, every build and every serve rebuild, at no extra cost. Canon-file hashes: on every command that reads the quilt (a handful of files). The walk over `.loom/history/`: only in `loom lint` and `loom history verify`. `loom lint --nodes` gives the hygiene report on demand; `linearize`, `atomize` and `canonize` run the subset that applies to them as a precondition and name the full command on failure.

## Commands

- **`loom draft canon/X.tex --to drafting/Y.tex`** — copy a canon document to the drafting table; ledger line; the copy is live by position. `loom draft` with a canon file that has moved since it was written notices (hash) and says so.
- **`loom canonize drafting/Y.tex --to canon/Z.tex -m "…"`** — as above. Never touches acceptance: a landmark is not a review, and a node whose text moved simply reads stale against its last acceptance through the existing hashes.
- **`loom stamp -m "…" [--in DOC]`** — as above.
- **`loom atomize`** — the existing conversion (nodes out to `nodes/`, inclusions left in a new spine), now one act: it converts, records that its output superseded its input, and prints the cleanup instruction. `--retire` moves the input to a `retired/` directory the scan skips, an opt-in move the author asked for in that command. Never in place; loom writes copies. The `--key` form is unchanged.
- **`loom linearize SPINE --to DOC [--fork | --keep-shared]`** — flattens `\input`, `\include` and `\nest` (loom's own macro: an `\input` whose sections arrive one level down, so flattening rewrites the sectioning levels; this is what `assemble` did beyond inlining and is why the flat file needs no `loom.sty`). Refuses by default when a node another live document includes would be defined twice, naming the nodes and both continuations; `--fork` forks every such node and prints the mapping table, recorded in the ledger; `--keep-shared` leaves those as inclusions with the marker comment. `loom assemble` is **dropped** — nothing else lived there.
- **`loom fork ID --in DOC [--from @N] [--as ID]`** — allocates a new id (or takes the one named); writes the text as a new node file when DOC is atomic, inline when linear — as a printed patch in either case, since loom never edits an author's file; rewrites `\ref`, `\cref`, `\uses` and postnotes **inside DOC only**, printing the patch; appends `{fork, new, from: id@N, in, when, who}` to the ledger; copies no annotations (they belong to the original's history; ancestry is enough). Built in 0.9 because `linearize --fork` needs it.
- **`loom revert ID@N`** — prints the patch that puts that version's text into the head. Materializes, never points: git's answer (`git checkout <commit> -- file` writes content; the working tree is never a pointer). After applying it, the head's hash equals @N's, so loom can say "text of @N" with no pointer anywhere.
- **`loom live FILE`** — un-supersedes a file, ledger line.
- **`loom history verify`** — the full walk; `loom history gc` is WQ-30.
- **`loom lint --nodes`** — the hygiene report.
- **`loom import PAPER`** — copies the paper into `canon/` verbatim and records step 0001 as `imported`. **`loom init --from PAPER`** is exactly `init` followed by that. Work begins with `draft`, then `atomize` if atoms are wanted. Today's `import` (Chapter 6: atomization, anchoring fixes, the report) is reachable as `import → draft → atomize`; Chapter 6 is rewritten around that sequence. `loom init` no longer records anything from a draft.
- **`loom ai promote`** keeps only its digest case; the node case retires in favour of preview-and-copy (the author's choice: more intentional, simpler). The clerical step it absorbed has homes: `loom id FILE` prints the patch inserting fresh ids, `loom id --next` prints the next free one.
- **`loom build --force`** already exists (2026-09-17): re-renders every fragment, ignoring the cache; the cache also fingerprints loom's own code in a `dev` version (DR-131).
