This owns no milestone and no build of its own: it specifies what must be inserted into [0.10](0.10-annotations-and-review.md) and [0.11](0.11-run-review-view.md) when each is written, one rule that starts with the next commit to arras, and one queue item. ## Why this exists

Three facts, which together fix the shape of everything below.

1. **The interface is specified publisher-neutral and a second publisher is coming.** `specs/README.md` names publishers plural, Chapter 9.10 names the second one, and Chapter 10.8 forbids arras from knowing what wrote a corpus. An audit on 2026-09-17 found that arras is neutral in its *structure* — open types, data-driven states, taxa and diagnostics, no write path, no publisher API — and not neutral in its *vocabulary*: six places assume a corpus has documents, an acceptance ledger, digests and proofs, and the app crashes at boot if a manifest omits a section rather than leaving it empty. Section 4 is the list.
2. **The author requires host-neutrality, and requires it to be usable by hand.** The same corpus, rendered by two hosts, must be able to look like two different sites: a personal site must not look like `loom serve`. The author intends to build sites with arras personally, writing HTML and CSS, without an agent's help and without adopting a framework — so seam 2 is not merely an API, it is an API a web developer already knows how to use (section 8). Nothing in arras supports either half today, and every plan that lands adds a little more that works against both.
3. **0.9 is being implemented now.** There is no slot for a refactor of its own, so the work weaves into the two plans that follow, and the parts that cannot wait are expressed as a rule rather than as a rewrite.

## 1. What arras is

Arras is a **renderer for a published artifact**. The artifact is a build directory: `manifest.json`, the only index, and HTML fragments in the dialect. Anything that writes a conforming build directory gets the same viewer, and the viewer learns nothing about what wrote it.

The system is a pipeline with three boundaries, of which two matter here:

```
  source          front end        IR                 core                     host
  ────────        ─────────        ───────────────    ───────────────────      ─────────────
  source files →  publisher     →  build directory →  arras core           →   a host
                  (parses the       manifest.json      wires fragments,         routes, chrome,
                   source            + fragments       typesets, derives        tokens, layout,
                   language)                           badges / layout /        which widgets,
                                                       contents / previews      the front door

                  ╰── seam 1: a FILE FORMAT ──╯       ╰── seam 2: an API ───╯
                      versioned, validated,               components, tokens,
                      publisher-neutral                   derivations; host-neutral
```

The compiler analogy is exact enough to be useful: the publisher is a front end, the build directory is an intermediate representation, and arras is the back end. Fragments are the text section; the manifest is the symbol table and the relocation information. Three rules that already govern this repository fall out of it — a back end never re-derives what the front end knew (viewer obligation 2), an additive IR change does not break a back end (the versioning rule), and a second front end is the only way to find out whether what you built is an IR or your own compiler's internals serialized.

In the vocabulary of model–view–presenter:

- **Model:** the build directory. Owned by the publisher, serialized, crossing a process boundary as bytes. This is why there is a written specification, an `interface_version` and a validator, and why Chapter 10.8 is enforceable rather than aspirational.
- **Presenter:** arras's derivations — `badges.ts`, `graph/layout.ts`, `contents.ts`, `reached.ts`. Model facts in, display facts out.
- **View:** the widgets and the shells.
- **Controller:** absent by design. Arras writes nothing; the write API, when it lands, is served by the publisher and arras is its client.

**The two neutralities.** Seam 1 is publisher-neutral and exists today: a versioned format with a validator and a fixture. Seam 2 is host-neutral and does not exist yet: a component API and a token contract, so that the core is shared and the presentation is not. R3 builds it; this document's job is to stop the debt against it from growing in the meantime.

The local precedent is `loom-lsp`: the semantics are computed once and `loom-nvim` and `loom-vscode` draw them however their editor draws things. Seam 2 is that same split, moved to display. `loom serve`'s app becomes one host rather than the only one.

## 2. What arras is and is not

| Arras is | Arras is not |
|---|---|
| A renderer of a build directory | A processor of any source language — parsing belongs to publishers |
| The engine: loading, wiring, typesetting, deriving display facts | The site: identity, brand, chrome and layout belong to the host |
| A reference viewer shipped with loom | *The* viewer. The app served by `loom serve` is one host |
| A reader of the manifest as the only index | A deriver of structure from fragment text beyond what the dialect marks up |
| Stateless about the corpus | An owner of corpus state. Records belong to the publisher; only viewer preferences are arras's |
| Pull-driven by one trigger, the manifest's hash | A client of any publisher API, save the write API when it lands |
| Ignorant of which publisher wrote the corpus | A host of two known publishers. Serving exactly two clients is the same failure as serving one |
| Usable by a person with an editor, plain HTML, CSS and a script tag | A framework with its own idioms, navigable only by a tool that has read this repository |

## 3. The three questions

Apply these to any change, in review or while writing it. The first two are the operational form of sections 1 and 2; the third is the operational form of section 8. A change that fails any of them is in the wrong place, not merely in the wrong style.

**Q1 — publisher neutrality: would this still be true of a corpus that is not a loom quilt?** If no, it does not belong in arras's code. It belongs in the manifest as data, or in a capability the publisher declares.

**Q2 — host neutrality: would two different sites want this identically?** If no, it does not belong in the core. It belongs to the host, as tokens, chrome, routes or page composition.

**Q3 — platform familiarity: would a web developer who has never read this repository recognise this?** If no, prefer the platform's own version of it: an element, an attribute, a class, a custom property, an anchor, an event. A bespoke mechanism needs a reason that the platform's mechanism cannot meet, and the reason goes in a decision record.

**Tie-breaker — is this semantic work a site author would otherwise have to redo?** Yes, it is semantics: core. No, it is identity or arrangement: host.

Worked examples, because the questions are only as good as their application:

| Thing | Q1 | Q2 | Where it belongs |
|---|---|---|---|
| How a state maps to a coloured pill | yes | yes | Core (`badges.ts`) |
| The colour values themselves | yes | no | Host tokens |
| "not yet compiled" beside every node | **no** | — | Neither: a fact about one publisher's workflow. A capability decides whether numbering is expected at all |
| The graph layout algorithm | yes | yes | Core |
| Which views appear, and in what order | yes | no | Host, reading the capabilities |
| Whether a review view is meaningful at all | **no** | — | The publisher declares it |
| The `loom:` URL scheme name | **no** | — | From the manifest's `publisher`, never a constant in `src/` |
| ⌘K palette behaviour | yes | yes | Core widget; the host decides where it lives |
| What the front door says | no | no | The host, entirely |
| Expanding an inclusion in place | yes | yes | Core |
| A note embedded in a hand-written page | yes | yes | Core, reached as a custom element |
| Restyling a badge | yes | no | Host, in ordinary CSS against documented class names |
| Whether the rail sits left or the strip sits right | yes | no | Host |

A fourth question, when the first three leave it open: **does the answer already arrive in the manifest?** If it does, derive it rather than hard-coding it — and if it does not, the fix is usually a capability on the publisher's side, not a branch in arras.

Measured 2026-09-17 against `980d477` plus the uncommitted graph work in the tree. Five groups.

**(b) Vocabulary leaks.** Each fails Q1.

- Acceptance, staleness and digests throughout `/review`, `/references` and `/digest`: correct for a corpus that has them, furniture for one that does not.

**(c) The origin root is assumed.** Six sites hard-code `/build/` — `src/lib/fragments/fetch.ts:13`, `src/lib/manifest/client.svelte.ts:13`, `src/lib/manifest/loader.ts:64`, `src/lib/fragments/mount.ts:70`, `src/lib/components/DiffView.svelte:44`, `src/routes/master/[stem]/+page.svelte:105` — and the seven functions in `src/lib/nav.ts` build absolute routes. There is no `kit.paths.base`.

**(d) The host is assumed.** `src/lib/theme.css:12` defines tokens on `:root` and the file opens with a global `*` box-sizing reset; `src/lib/prefs.svelte.ts:101` writes attributes onto `documentElement`; the manifest store is a module singleton (its `url` is at least settable). Each fails Q2.

## 5. The three pieces

**R1 — the URL seam** (done 2026-09-17, DR-143). `kit.paths.base`, build-time configurable and defaulting to `/`; `nav.ts` prepending it; the six `/build/` sites reading from one place. It is *not* a deployment, not a second host, and it changes nothing a reader sees.

**R2 — absence tolerance and capabilities.** Every section optional at boot; the leaks of 4(b) removed; the view list derived from what the corpus declares. It is *not* the host split: the shells stay arras's, and their arrangement does not change.

**R3 — the host split. Declined 2026-09-18** and closed as WQ-31 without being built; section 8 keeps the design, the seven answers and the reasons. What survives it is the half that pays for itself as theming — tokens off `:root` onto arras's own scope — which [0.11](0.11-run-review-view.md) Part I builds, and the standing habit of writing display logic as a core derivation rather than as route code, which is what kept the extraction cheap to consider and keeps the routes thin to re-theme.

## 7. The host-neutrality rule, and its test

Seam 2 cannot be built before 0.11. The debt against it can be stopped now, and that is the single highest-value insertion in this document, because R3's cost is proportional to the number of violations standing when it starts, and three plans stand between here and there.

**The rule.** In `src/lib/` — the core — none of the following is added:

- a write to `:root` or to `document.documentElement`; tokens are defined on a class the host applies, and preferences are set on a root the host owns.
- an origin-absolute URL or route literal; every path is composed from the configured base, and every URL a widget emits comes from an injected policy, as `LocalGraphPanel`'s `hrefFor` already does.
- a new module-level singleton holding corpus state; one corpus per page is a host's choice, not the core's.
- a publisher's name, scheme or command, in code or in copy; those arrive in the manifest.

**The test**, `tests/unit/host-neutrality.spec.ts`, in the spirit of `tests/unit/forbidden-words.spec.ts` (Chapter 10.8) and beside it: walk `src/lib/`, fail on `:root` outside the token file's own declaration block, on `documentElement`, on string literals matching `/build/` or `^/[a-z]` in a URL position, and on `loom:` outside a manifest-supplied value. Like the forbidden-words guard it is a boundary test, not a style test: it exists so that a boundary already decided is not eroded one plan at a time.

## 8. Seam 2 follows the web platform

> **Declined 2026-09-18.** This section specified the requirements for a component API that is not being built; see the status note above. It is kept because its constraints are the right ones *if* the question reopens, and because the reason a design was declined is the part nothing else records. Nothing below is a commitment.

The requirement, stated so that it constrains R3 before R3 is designed: **a person must be able to build a site with arras by hand.** Not by reading this repository, not by asking an agent, and not by adopting a framework — by writing HTML and CSS in an editor, the way sites have been built for thirty years. An API that only its authors and their tools can navigate is a bespoke system whatever else it is, and it fails for the same reason a publisher-shaped interface fails: it is built around its first consumer.

What that means concretely, each item being the platform's answer rather than one of ours:

- **Custom elements, not a framework API.** `<arras-note key="…">` in a plain HTML file. Svelte 5 compiles components as custom elements and supports `shadow: 'none'`, which keeps the host's own CSS applying and keeps one MathJax font cache per page rather than one per shadow root.
- **No build step required.** A `<script type="module">` and an element are enough. A bundler is an option for someone who already has one, never a precondition for someone who does not.
- **Ordinary CSS.** Tokens as custom properties, class names documented as a contract, normal specificity, no shadow-DOM prison and no styles in JavaScript. Restyling is a stylesheet the author writes, not a plugin they register.
- **Real URLs and real links.** Anchors with `href`s that survive a middle click, a bookmark and the back button; fragment anchors that land. Navigation that exists only as in-memory state is not navigation.
- **Progressive enhancement.** Fragments are already semantic HTML: a host that includes one server-side gets readable text, and the widgets enhance what is there rather than replacing it.
- **Standard packaging.** An npm package with an `exports` map and a version that means something. The vendored bundle stays for loom, but it stops being the only way in.
- **Documentation for a person.** The first example on the page is a short HTML file someone can paste into an editor, open, and see a node.

Chapter 10.1's existing distribution story — one build, vendored into loom, copied into the pip wrapper — is unchanged by this. What changes is that it is no longer the whole story, because neither of those paths is one a person can use to build a site of their own.


### The acceptance check it would have had

Recorded because it is the part that would otherwise have been quietly dropped, and because it is the honest test of whether a component API is finished: **a single hand-written HTML file — a script tag, a stylesheet of the author's own, and one element — renders a node from a build directory on a static server, with no build step, no framework and nothing generated.** If that file needs anything this repository has to explain, seam 2 is not done. Nothing weaker than this proves the requirement, because every weaker version is satisfiable by an API only its authors can navigate.

### The design answers reached before it was declined (2026-09-18)

Seven questions were put to the author and answered in full, in the session that then declined the direction. They are kept so that reopening the question does not mean redoing the design.

1. **What ships.** Arras becomes the core; the app's source belongs to loom, which uses the core the way weft and the sitegen would — no privileged consumer. This framing is the author's, and it is what prompted the re-argument below.
2. **The elements.** A provider plus content elements, each named for what it is: `<arras-corpus>`, `<arras-note>`, `<arras-contents>`, `<arras-graph>`, `<arras-closure>`, `<arras-report>`, `<arras-annotations>`. Not one parameterised `<arras-view name="…">`, whose `name` is a registry only this repository knows; not elements down to the badge, which would freeze the internal component tree as public API.
3. **Finding the corpus.** `<arras-corpus src="…">` as a provider, children walking up the DOM as `<source>` finds `<picture>`; a bare `src` on an element overrides, one manifest fetch is cached per resolved root, and two providers on a page mean two corpora with no extra mechanism.
4. **URLs.** An injected `hrefFor`, as `graph/LocalGraphPanel.svelte` already takes — set as a property on the provider, with `src` staying an attribute, which is the platform's own division of strings in markup from functions in script. The core must still ship a default policy, or a page that injects nothing emits broken links.
5. **CSS.** Tokens on arras's own elements, the reset scoped with them, class names a documented contract. Not `:root`, which declares on a page arras does not own; not shadow DOM, which §8 above rules out because the host's CSS could then only reach `::part()` and MathJax would build one font cache per root. **This answer was kept**: it is the cheap half of R3 and [0.11](0.11-run-review-view.md) Part I builds it, because it pays for itself as theming without any of the packaging.
6. **The bundle.** A light default entry, with MathJax loading on first typeset and the graph's `elkjs` and `d3-force` only when an `<arras-graph>` upgrades — imported from the package's own files, never a CDN, so Chapter 10.1's offline guarantee holds.
7. **Scope.** All of it in one item with internal gates, the app rewritten against the public API as its first host, since a seam the app does not use is a seam nothing checks.

### Why it was declined

**Seam 1 already delivers the reuse; seam 2 buys chrome.** The build directory is a specified, versioned, publisher-neutral format with a validator and a conformance fixture, and `setDataRoot` exists so a host may point the viewer at *"a different path, a different origin, a corpus that is not beside the viewer at all"* (`src/lib/paths.ts`). Weft and the sitegen can therefore render their corpora with the shipped bundle today. What a component API adds is not that they can use arras — it is that they can make it look like a different site, and that a person can compose pages by hand. Both are real wants. Neither is reuse, and calling them reuse is what made the cost look already justified.

**The costs are specific to the boundary, not general.** Svelte's `setContext`/`getContext` does not cross a custom element, so answer 3's provider and its DOM walk are new machinery replacing what the framework gives free. Chapter 10.1's optimizations are global invariants of one application — *"All typesetting shares one queue (DR-120)"*, fragments cached under the manifest's hash and emptied when it changes, and the 160-formula batching that typesets everything above the reader before the reveal so nothing above them shifts — and across independently mounted elements each becomes a hand-maintained singleton. SvelteKit splits per route and tree-shakes across the app automatically; a library of registered elements gets that only where the laziness is hand-written, which is what answer 6 is. `build:prerender` writes one `index.html` per route, which a page composed of custom elements makes harder — and if the app keeps importing the components directly to preserve it, the app is not a host and the seam is unproven anyway. Finally, every exported name, attribute and class name becomes a contract, a permanent tax on the fastest-moving part of the project: 0.11 alone adds four views.

**The project had already decided this question once, the other way.** The loom↔weft seam was settled deliberately: weft copies loom's code — crawl, identity, bib, postnote, extract — rather than depending on it, with the digest contract written down first so drift is a failing test. Share the contract, not the code. It is hard to argue that crawl and identity should be copied while display must be packaged.

**If it reopens**, the trigger is not a plan but an observation: weft or the sitegen has tried the build-directory route and hit a wall that can be named. Designing for two consumers that do not exist is the same failure as designing for the one that does, in the other direction.

## 9. `publishes`: what a corpus has, not what to draw

The view list is a constant today, so a corpus with no documents and no ledger still offers `read`, `review` and `references`, and gets empty furniture. Two ways to fix it, and the difference matters.

**Deriving it from the data** — hide `read` when `masters` is empty — cannot distinguish *empty because not yet* from *empty because never*. A quilt with no runs yet would lose a view and get it back later, and the manifest is re-polled every second, so the furniture would move while someone worked.

**Declaring it** as a capability block fixes that, and it is the shape this interface already uses on the write side: `GET /_api` answers with the capabilities it has, and a viewer that gets a 404 shows no editing affordances (`specs/write-api.md` §1). The read side gains the same idea:

```json
"publishes": {
  "documents": true,
  "review": true,
  "bibliography": true,
  "discussions": true
}
```

The rule that keeps it honest, and the reason it does not violate 15.1: **a capability says what exists, never what to draw.** `"documents": false` says this corpus is not assembled into documents; it does not say "hide the read tab". Arras decides what that means, and a host may decide differently.

Additive, so `interface_version` is unchanged. A manifest that declares nothing keeps working, falling back to deriving from the data, which is what v1 manifests get. Key names, and whether the fallback is permanent, are settled when 0.10 is written; the shape is settled here.

## 10. `fixture-minimal`

**Built on 2026-09-17** at `docs/specs/fixture-minimal/`, vendored into `arras/tests/fixture-minimal/`, with `arras/tests/e2e-minimal/` running against it in CI (`specs/fixture.md` §5, DR-146). One refinement to what follows: the "deliberately empty" sections are omitted outright rather than written as `{}`, since absence is what the floor permits and `{}` would have passed before R2a.

A fixture is a committed sample build directory used as test input, so each tool can be tested without running the other. `specs/fixture/` is one: a synthetic quilt, generated by loom, vendored by both tools (`specs/fixture.md`).

One fixture from one publisher cannot show that the interface is publisher-neutral, and a second fixture from a second publisher would only show that arras serves two known clients, which is the same failure in a larger disguise. What is needed is a fixture of **the interface's floor**, belonging to the specification and generated by nobody's publisher:

- present: `interface_version`, `publisher`, `corpus`, nodes, edges, tags, taxa, search, macros, states.
- deliberately empty: `masters`, `keys`, `regions`, `inclusion`, `annotations`, `threads`, `references`, `diagnostics`.
- deliberately strange: a state label no viewer knows, a diagnostic code no viewer knows, a relation kind no viewer knows, and a node whose taxon appears nowhere else.

What its test asserts: every route renders or is absent by capability; nothing crashes; no empty furniture stands with a heading over it; and no phrase belonging to one publisher's workflow appears anywhere on any page. It is the guard that keeps 0.10, 0.11 and everything after them from re-deriving the assumptions of section 4(a) and 4(b), which they otherwise will, because each of those plans is about the workbench.

## 11. Acceptance checks

Observable, and all but the last two runnable in CI.

1. Arras boots and every route renders against `fixture-minimal`.
2. No page rendered from `fixture-minimal` contains "not yet compiled", "loose", or a publisher's name.
3. A corpus declaring `"documents": false` offers no read view, and its rail carries no document picker.
4. `tests/unit/host-neutrality.spec.ts` passes, and fails when a `:root` write or an absolute `/build/` literal is added to `src/lib/`.
5. A build with `base` set to a non-empty path serves correctly under that path, and `build:prerender` writes routes under it.
6. `loom serve` against the existing fixture is unchanged to the eye, and the shots suite agrees. This is the regression guard: everything above is meant to be invisible to the corpus that has all the structures.
7.
