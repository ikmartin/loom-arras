# 0.27 — Boxes you can tick, and pages that read the quilt

One phase, built start to finish. What was built is in the **Implementation** section at the bottom. "Page" in this plan means an HTML file of the quilt; the documents it changes say "an HTML file", since a page is already what `loom write` writes (K7).

## Context

A `- [ ]` in Markdown reaches the viewer as a literal `[ ]`, because the publisher has no task-list rule, so changing one means opening a text editor. The author also wants to see what is open across a quilt, but a flat list isn't meaningful yet: quant's 518 boxes hold the same material at up to three levels, and they mix self-assessments with tasks.

So loom does two small things. It draws boxes the person can tick in place, and it makes a quilt's own HTML pages a stated capability, so that a quilt can build whatever list or tracker it wants. Loom gets no todo view and no object system, and org isn't part of this.

## Decisions, approved with this plan

1. **A tick is the `[ ]` in the file.** It is author data (P2), visible in any editor and to agents, and it travels with the text when a file is revised.
2. **Only a Markdown file's boxes are live.** A notebook's boxes are drawn read-only, and so is every box where no publisher can write. Chat messages, annotations and pages keep today's literal text.
3. **A tick is the person's act, and P7 gains it by name.** The old text goes into the history first, and an agent posting to the endpoint is refused. Agents can still edit the file as they edit any file, so the orientation asks them to keep each `[x]` when rewriting and to tick only when the author asks. That rule is advice, since an edit to the file can't be told apart from anyone else's.
4. **A tick doesn't appear in Your Changes.** The person just made it, so the same change goes into their look. Any other edit to that file stays listed. A tick on a line already inside a pending edit stays listed as part of that edit.
5. **A tick is recorded, not versioned.** Each writes one history line (who, when, file, line, state), so "what did I do this week" can be answered later. It keeps no named version. It appears in The Record's Everything recorded, not in its Versions timeline.
6. **Agents hear about ticks.** `loom since` reports each box's final state in the window, with the line's words.
7. **No `loom tick` command.** The command line already has the file, as with `settings-save`.
8. **Pages stay read-only.** A page can't write and never reaches the viewer's token (invariant of 2026-11-02). This plan doesn't loosen that.
9. **Pages get one addition: a listing of shown files.** Without it, a page has to hard-code file names and silently misses new ones. Loom's records and durable page state stay out, as a queue item with a trigger.

## What gets built

### The publisher

- **Finding boxes:** a new `loom/src/loom/tasks.py` has `items(text)`, which returns each task item's true source line, state and a short hash of the line without its box. Fenced code is excluded by using the parser, not a regex.
- **True line numbers:** `token.map` is wrong after math is lifted (measured: source lines 9 and 10 came back as 6 and 7). So `items` parses a second form of the text in `records/store.py`, where each math span keeps its line count. The rendered output doesn't change, and the second parse runs only when a file has a box.
- **Drawing:** the token pass in `files.py` marks `<li class="task" data-done="false" data-task="LINE:HASH">` and removes the `[ ] ` from the text. `render_file_markdown` gets a `tasks` flag, true only for Markdown files, so notebook cells carry no `data-task`. The markup goes on the token, so the raw-HTML allowlist never sees it.
- **The tick:** `tasks.tick(quilt, who, path, task, done)` checks the file is shown and Markdown, and that the line is still a task with the same hash. It then stores the old text (`write_raw`), flips one character, writes atomically and preserves every other byte, CRLF included. Asking for the state already there is a success and writes nothing.
- **The look:** a new `looks.take_line` applies the same change to the look when that line is unchanged since the look, mapped through the same `SequenceMatcher` that `changes()` uses.
- **The endpoint:** `POST /_api/file-tick {path, task, done, author?}`. It follows `_changes` in `render/api.py` for `is_agent` refusal and goes in `CAPABILITIES` and `RECORD_WRITES`, so a tick republishes from the last scan. Refusals are `stale` (409), `not-a-task` (409), `no-such-file` (404) and `author-only` (403). No reviewer name is required, and with no name there is simply no look to update.
- **The record:** a `tick` line through `append_entry`, with `line` and `done` carried in `_acts` (`render/manifest.py`) and `HistoryAct`.
- **`loom since`:** a `ticks` field in `since.py`, with the matching text block and JSON (T8).

### The viewer

- **The box:** in `FileItem.svelte`, an effect after the body is drawn adds a real `<input type="checkbox">` to each `li.task`, as the frames effect there already does for frames. It is disabled unless the item has `data-task` and `can('file-tick')`.
- **Clicking:** one delegated handler flips the box at once, posts, and on refusal flips it back and says why, using the existing `refused` state.
- **No redraw on a tick:** when a new body differs from the drawn one only in `data-done`, the body string stays put and only the boxes update. MathJax doesn't re-run and the scroll position holds.
- **Rapid ticks:** a pending map holds each box's asked state until a publication agrees, so an older publication can't briefly untick a newer click.
- **The Record:** `actWords` in `review/timeline.ts` gets a `tick` case, "Ticked a box in lesson.md", and `tick` stays out of the Versions timeline.
- **Style:** `li.task` in `FileItem.svelte`'s style block: no bullet, box aligned to the first line, no strikethrough.

### Pages

- **The listing:** `GET /.loom/files.json` on the frames origin (`FramesHandler`, `render/serve.py`) answers `{"files": [...]}` from `Shown.walk()`. `.loom` is never a shown path, so it can't collide with a project file. It keeps the same Host check.
- **The stated capability:** a page may rely on reading shown files, the listing, and `quilt:`, `cited:` and `app:` links through the bridge. It can't write, and its browser storage is lost when `loom serve` restarts, because the port changes. A page can also send what it reads to the network, and the docs say so plainly.

## Implementation

**2026-11-04.** Built as planned, in one commit. What differs from the plan:

- **Line numbers come from one parse, not two.** `records/store.py`'s `source_line` maps the renderer's own lifted lines back to the file, so what counts as a task is exactly what the page's parse says, and a tick re-reads the file through that same parse.
- **Refusals.** Any line that no longer reads as the page drew it is `stale`, however it changed; `not-a-task` is for a file that is not Markdown or not UTF-8.
- **The ledger line also keeps the item's words,** so `loom since` can report them after the line has moved.
- **The documents say "an HTML file",** not "page", since a page is what `loom write` writes (K7). The queue item is `WQ-64-html-file-reach.md`.
- **The queue's count was stale.** Its README said twenty-five active items where twenty-two existed; with WQ-64 it now says twenty-three.
- **`FileItem` keeps its drawn body across publications,** the same change the Markdown-HTML session has in hand, because a tick must not blank the page.

By hand, on a scratch copy of quant with HOME and XDG isolated: on the 205-box outline the box flips at once and the file differs from the original by that box alone. The scroll position and the drawn nodes hold, and the write answers in about 0.4–0.7 s, publication included.

Two things found about running the tests: the write suites copy only tracked files, so a regenerated quilt's new texts need `git add -N` before they run; and at a load of 150–230, with other sessions' suites running, six write tests missed their time limits, all of which passed at a load of about 30. The last full run passed everything but `patch.e2e.ts`'s local 1.5 s budget, which a parallel run misses and which passed six times of six alone.
