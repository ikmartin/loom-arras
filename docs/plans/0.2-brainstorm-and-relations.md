# Plan 0.2: brainstorming and relations

For the implementing agent, to be read after the v0.1 milestones M1 through M6 (book, Chapter 13) have landed and the relative localization quilt exists. This plan adds four things the v0.1 book does not have. Three are documentation and templates; one, the `see:` relation, is a small change to the scanner, the manifest, and arras. Nothing here adds a macro, a directory, a stored state, or a dependency kind, and no change alters a compiled PDF.

Markers as in the book: **[decided]**, **[assumed]**, **[deferred]**. Everything below was decided in design conversation on 2026-09-16 unless marked otherwise; see DR-89 at the end (numbered DR-39 when this plan was written, before DR-39 to DR-88 existed).

## 0. Prerequisites

Before starting, confirm on the relloc quilt:

- `loom lint` clean, `loom build` publishes, `loom serve` renders every page kind in arras.
- Node-level directives (`tags:`, `author:`) are parsed and appear in the manifest.
- Multiple masters work: a second master in `drafts/` gets its own numbering and reachability.
- Multiple proofs of one statement are listed on the statement's node page whatever master reaches them.

If any of these is missing, finish v0.1 first; this plan assumes them.

## 1. Use cases

### 1.1 A brainstorm about the residue map

The author runs `loom ai start brainstorm-residue` and, in the agent, applies the `brainstorm` mode. The agent orients, reads `loom status --json`, `loom search residue --json`, the bundles of the two definitions the topic touches, and the overview sections of the digests that matter. The author says what they are after. The agent restates it as a precise candidate statement, asks which hypotheses are intended, writes `draft-cand-residue-indep.tex` (a `conjecture` environment with `\incomplete{Not yet attempted.}`), computes the $\mathbb{P}^2$ degree-two case in `brainstorm-residue.check.py`, reports that `Man12-thm-4.1` gives the statement under a hypothesis the author did not state, and records two discarded approaches with reasons. Its notes file has `[summary]`, `[candidates]`, `[dead-ends]`, `[known-results]`, `[open-questions]`.

The author promotes the surviving candidate (`loom ai promote` gives it `rl-0051`), adds `\input{nodes/rl-0051}` to `drafts/outline.tex`, and in arras reads the outline view with the candidate in place, badged draft, hanging in the graph from the definitions it uses. Weeks later a `draft` run turns it into a lemma; referee runs follow; it is accepted; the `\input` line moves to `main.tex`. Its id never changes.

### 1.2 The plan as a master

`drafts/outline.tex` is an ordinary master: sections, strategy prose, `\input` lines for candidates and for the settled definitions they build on. `status --master drafts/outline.tex` reports its reach; candidates are not loose while it reaches them; `loom assemble drafts/outline.tex --to $LOOM_RUN/outline.tex` hands an agent the whole plan. A refuted candidate keeps its node, gains a sentence naming the run and the counterexample, and loses its `\input` line, becoming loose.

### 1.3 A thorough version beside a paper version

The paper master reaches `nodes/rl-0004.tex`, a lemma with a compact adjacent proof. A notes master reaches `nodes/rl-0071.tex`, a differently stated, much longer version broken into steps (`rl-0072`, `rl-0073`) that the compact proof does not cite. `rl-0071.tex` carries `% !LOOM see: rl-0004`. On `rl-0004`'s page arras shows "See also: rl-0071 (Residue independent of embedding, detailed) in notes.tex"; on `rl-0071`'s page the reverse. Neither the PDF nor the dependency graph changes; the compact acceptance does not go stale when the notes change; audit does not report an unused dependency. When the two versions share a statement, the author uses a second labelled proof instead (5.6.2) and needs no directive.

## 2. Feature: the `see:` relation

### 2.1 Specification

**[decided]**

1. A node-level key-value directive `% !LOOM see: ID, ID, ...`. Scope as `tags:` (5.11.2): inside a node's own text it applies to that node; in a file's first twenty lines before any node it applies to every node the file defines (**[assumed]**; rarely useful, kept for uniformity).
2. Each item resolves like a reference: an id, an alias, or a digest node id. An unresolved item is `dangling-link` (error) with the directive's file and line.
3. A relation is undirected for display: arras shows it on both nodes. It is stored once, on the node that declared it, with `from` and `to` recorded so the declaring side is known.
4. A relation is never a dependency: it enters no closure, no bundle, no acceptance row, no `deps` closure, and no staleness computation. `\uses` remains the only way to declare a dependency the text does not name.
5. Self-relations and duplicates are `loom:see-redundant` (info).

### 2.2 Scanner

- `scan/directives.py`: add `see` to the inventory with list-value parsing (5.11.1); attach to the enclosing node like `tags`.
- A resolution pass after ids and aliases are known (the same pass that resolves `\ref`): map each item to a node key; emit `dangling-link` for failures with locations.
- Store relations in the scan result as a list of `{from, to, via: "see", src}`, separate from `edges`.
- `loom deps KEY` prints a final section "See also" listing relations of the key, marked not-a-dependency; `--json` gains `relations: [...]` beside `statement`, `proof`, `closure`. `loom unravel` does not list relations (it reports consequences, and a relation has none).

### 2.3 Manifest

Add a top-level `relations` list (specs/manifest.md §16, new):

```json
"relations": [
  {"from": "rl-0071", "to": "rl-0004", "kind": "see",
   "src": {"file": "nodes/rl-0071.tex", "line": 1}}
]
```

Kinds: `see` only. Adding a kind is a decision-record event. Nodes gain no new field; arras derives per-node lists from this list.

### 2.4 Arras

- Node page header: a "See also" list, both directions, each entry the node's taxon, title, and the masters that reach it, linking to its page. Rendered from `relations`; arras knows only that relations are links with a kind label.
- No graph change in this plan (**[deferred]**: a toggle to draw relations dotted, after the MVP).
- Unknown relation kinds render generically as a labelled link list.

### 2.5 Diagnostics

- `dangling-link` (reserved) covers unresolved targets; the message names the directive.
- `loom:see-redundant` (info) added to specs/diagnostics.md.
- No `expands-statement-differs`; decided against.

## 3. Feature: the `brainstorm` mode

### 3.1 Specification

**[decided]** An eighth mode file, `ai/modes/brainstorm.md`, written by `loom ai init`, refreshed by `loom upgrade` under the edited-modes guard, with a skill stub and no slash command (it takes no single target). Four new blocks in `blocks.md`.

### 3.2 Text of the four blocks (append to `blocks.md` §Blocks)

```markdown
- [candidates] One entry per candidate statement produced in this run:
  its draft file name, its taxon, a one-line statement, the hypotheses
  the author must still decide, and what it would depend on (ids).
- [dead-ends] One entry per approach tried and abandoned: what it was,
  why it fails (a computation, a counterexample, a known obstruction with
  a digest node id), and whether anything was salvaged.
- [known-results] What the digests already say about the topic: digest
  node ids with locators, each with one line on how it bears on the
  candidates (gives it, contradicts it, gives it under other hypotheses).
- [open-questions] What could not be decided in this run and what would
  decide it (a computation to run, a paper to digest, a definition to
  fix).
```

### 3.3 Text of `ai/modes/brainstorm.md`

```markdown
# Mode: brainstorm

## Before you begin
- Write only under `$LOOM_RUN`. Never edit source. Never run `loom accept`
  or `loom ai promote`; the author promotes.
- Read `ai/modes/blocks.md` once this session.

## Purpose
Help the author explore a topic before anything is proved. Your job is
to make the author's ideas precise and testable quickly, not to supply
strategy: restate what they want as a candidate statement with explicit
hypotheses before evaluating it; compute the small cases before opining;
search the digests before claiming anything is new or known; record what
was tried and why it failed. If you have an idea of your own, offer it in
one sentence under [open-questions] and do not pursue it unless asked.

## Input
- `loom status --json`; `loom search TOPIC --json` for the ids involved.
- `loom bundle ID --run $LOOM_RUN` for each definition or result the
  topic touches.
- The overview sections of the relevant digests (`refs/CITEKEY.tex`,
  which are designed to be read whole); `loom search --kind digest`.
- If the author has an outline master, `loom assemble drafts/outline.tex
  --to $LOOM_RUN/outline.tex` for the plan as it stands.

## Procedure
1. Ask what the author is after and restate it precisely. Stop until
   they confirm.
2. For each candidate: write it as `draft-cand-SLUG.tex`, a complete
   node in the quilt's conventions (taxon `conjecture` or `question`,
   `\incomplete{Not yet attempted.}` in place of a proof, `\ref`s to the
   definitions it uses, `% !LOOM tags:` as the author prefers).
3. Compute: small cases, examples, degenerate cases; save every trial
   per standing rule 7.
4. Search: what the digests give, contradict, or give under other
   hypotheses; cite digest node ids.
5. Record every approach abandoned during the conversation under
   [dead-ends] with its reason at the time it is abandoned, not at the
   end.

## Output
1. `brainstorm-SLUG.notes.md`: [summary], [candidates], [dead-ends],
   [known-results], [open-questions].
2. `draft-cand-*.tex` per candidate.
3. `brainstorm-SLUG.check.py` with outputs.
4. An entry in `thread.md` after each significant exchange.
No annotations unless an existing key was found wanting (then as audit
would record it).

## Checklist
- [ ] Every candidate is a draft file with explicit hypotheses.
- [ ] Every dead end has a reason.
- [ ] Every "known" or "new" claim cites a digest node or says
      "no digest; memory-grade".
- [ ] Nothing was written outside `$LOOM_RUN`.
```

## 4. Feature: default candidate taxa

**[decided]** The minimal master written by `loom init` (4.7) declares, in addition to the standard set:

```tex
\theoremstyle{plain}
\newtheorem{conjecture}[theorem]{Conjecture}
\theoremstyle{remark}
\newtheorem{question}[theorem]{Question}
```

A conjecture owes a proof and appears on the blockers page as a gap until proved or refuted; a question owes nothing. No `sketch`. `--from` keeps the author's own preamble untouched. The demo quilt gains `drafts/outline.tex` (a second master) with one conjecture and one question reached only by it, so `loom init --demo` demonstrates the outline pattern and the fixture description (specs/fixture.md §1, demo paragraph) is updated accordingly. Test: `test_init_minimal_master_declares_candidate_taxa`, `test_demo_has_outline_master`.

## 5. Documentation-only items

- 4.4, new final paragraph: "Multiple masters are views. The paper master reaches what is settled; a talk reaches a selection; an outline master reaches candidates, planned sections, and the settled results they build on, so that candidates are reached rather than loose while they are being considered. The transition from plan to paper is moving `\input` lines. `status --master` reports each view; a node may be reached by several."
- 11.5, one sentence: "An agent that needs a whole master in context uses `loom assemble MASTER --to $LOOM_RUN/<name>.tex`; masters are not keys and `bundle` does not apply to them." The same line in orientation §5.
- 7.9, one sentence after "make the node loose": "A refuted candidate is handled the same way: its `\input` line is removed, its body gains a sentence naming the run and the counterexample, and a tag of the author's choosing may mark it for filtering; no tag has special meaning."

## 6. Order and size

1. Documentation items (§5) and taxa (§4): an hour; no risk.
2. Brainstorm mode and blocks (§3): a few hours; text and one test count.
3. `see:` (§2): scanner directive plus resolution, manifest field, `deps` section, arras header list, fixture, tests. One to two days. It touches both repositories and the fixture, so it is done last and in one change set with the spec patches, per specs/fixture.md §3.
