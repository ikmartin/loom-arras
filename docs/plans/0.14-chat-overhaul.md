# 0.14 — the chat overhaul

Plan for the chat overhaul, settled with the author on 2026-09-23 from the brainstorm in `docs/long-prompts/chat-overhaul`, which stays as the author's working document. Each phase is planned in plan mode, implemented, verified and stopped for review, as in 0.13.3. Phases are recorded under Delivery as they land.

## Purpose

*(verbatim)*

Loom is a shared, durable, addressable medium for mathematical work between a person and an agent. Everything either party produces has a permanent address, a place to live proportional to how far it is trusted, and one explicit act that moves it to the next place.

This document is about expanding and beefing out the ai integration features. It stops short of creating an ai-quilt.

## The visual principles

*(verbatim)*

Reading mode is measured against these. They came out of the work rather than preceding it, and each one has cost something to follow.

**P1 · Open on the thing itself.** The first screenful belongs to what the reader came for. What the application has to say *about* that thing goes to an edge or behind a control.

**P2 · Say it once, in the place that governs it.** Where two surfaces state the same fact, one is deleted rather than restyled, and the survivor is whichever one controls the fact.

**P3 · Claim only what is known.** Where the viewer does not know something it shows nothing rather than something plausible. A marker says the one thing that cannot be inferred and no more.

**P4 · Name the question. One element, one question.** Every element exists because a reader asks something at that moment. If the question cannot be named in one short sentence, the element goes; if two can be named, it is two elements; if two elements answer one question, one goes. Two riders: **a place is not an element** — a rail or a panel groups elements, and the test for a place is whether its elements' questions are asked at the same moment — and **the question is the reader's, not the system's**, which is what condemns a section reporting that a node is "in no document".

**P5 · Following a connection must not cost the thing you followed it from.** The viewer's subject is how texts relate; a relation has two terms; a viewer that holds one term can only show a relation by destroying the other.

**P6 · Show less rather than more by default.** Unless something has a good reason to be shown, don't show it. Corollaries: simpler is better, visual noise is BAD

## The design

Each section is the brainstorm's text, verbatim. Where planning settled more with the author (2026-09-23), it follows under **Settled in planning**.

### The transcript

**A session's transcript is a faithful record of the conversation between the person and the agent, and nothing else.**

**Decided:**
- One log per session, `inbox.jsonl`, kept as one file however long it grows.
- Only the two parties write to it: the person through the chat input or `loom session send`, the agent through a new `loom session say`. Loom never writes to it automatically.
- Annotations are not shown in the transcript. An agent may mention and link the annotations it writes, and is encouraged to.
- The transcript stays out of the manifest. It is served in pages: the chat opens on the latest messages and scrolling up loads older ones.
- `loom serve` reads only what is new: an index of where each message starts replaces parsing the whole file on every poll.
- `thread.md` stops being the transcript. `loom ai orient --session` resumes from the chat's tail instead.

**Settled in planning:**
- **A static viewer still shows the Chat.**
  - The build writes each transcript into `build/transcripts/<session>/<n>.json`, in pages of 100 events. The manifest's existing `seq` says how many pages there are, so no index file is needed.
  - Static and served viewers read the same pages. `loom serve` adds only the live tail, through `/_api/events`.
- **`thread.md` is retired, not demoted.** Loom stops reading it, and the orientation and every mode template stop asking for it. An agent journals by saying so in the chat.

### The Chat view

**The conversation and its input live together in one pane: the session item's Chat view, which replaces the Discussion view.**

**Decided:**
- The Chat view belongs to the one attached session; there is only ever one.
- The rail's cluster for a session reads **Chat | What it did**.
- Top to bottom: the transcript, newest at the bottom and paged upward; the status line; the packet tray; the input, with send and stop.
- The input is as wide as its pane. It is today's composer (`arras/src/lib/sessions/Composer.svelte`), moved into the new layout and widened.
- The status line says whether an agent is attached, what it is doing, and whether it failed to start. None of this is written to the transcript.
- Choosing a session in the picker opens its Chat.
- Annotations made in other panes still collect in the tray, so sending a packet needs the Chat open but not in focus.
- If a reply that lands off screen turns out to be missed, a small marker in the rail is the remedy, not a second input.

### Packets

**The annotations a person makes reach the agent without being retyped as a message.**

**Decided:**
- A new annotation — a mark, a card or a text selection — goes out with the person's next message automatically.
- The message in the transcript carries a summary of the annotations it sent (`4 suggestions, 2 questions, 3 notes`), never the annotations themselves.
- A tray above the input lists what the next packet holds, each row linking to its annotation, with a preview of the exact text that will be sent.
- A packet can be sent without a message.
- Choosing which annotations a packet carries is left for later.

### Launching an agent from the command line

**Loom starts an agent through a command-line program the person configures, and never through an API.**

**Decided:**
- Loom never asks for an API key and calls no model; it runs a local agent command such as the Claude CLI.
- The commands are set in a quilt-specific `ai/ai-config.toml`, which is gitignored by default and overrides the user-level config. Commands are never in `config.toml`.
- They are a `start` and a `resume` argument list, with a few placeholders loom fills in: the session, a conversation id derived from it, and the prompt.
- Loom refuses to launch from an `ai-config.toml` that git tracks. Otherwise a cloned quilt would run its author's command on the cloner's machine.
- `loom init` creates `ai-config.toml` after asking which AI the person uses: `1. Claude/Claude Code 2. ChatGPT/Codex 3. Other 4. No AI`.
  - Any other answer counts as 4.
  - For 1 or 2 the config is written automatically, and the person is pointed to the file if they want to change anything.
  - For 3 they are told how to fill in the file by hand.
- A flag answers the question without the prompt, so `loom init` can run in tests and scripts.
- Whether loom launches agents at all is a setting in `config.toml`, off by default. `loom init --launch-agents` turns it on. It is a yes or no, not a command, so committing it runs nothing.
- `loom init` asks the questions and writes `ai-config.toml` whether launching is on or off. Its printout says plainly whether agents will be launched and where to change that.
- When launching is on, a message lands and no agent is attached, `loom serve` runs the command: one process per turn, with the conversation carried across turns by the agent's own resume.
- The Chat view offers a stop button, and `loom agent check` tests the configuration without spending anything.

**Settled in planning:**
- **Answers 1 and 2 also install the AI layer**: what `loom ai init` does, meaning the orientation, the rules, the modes and, for Claude, the `.claude/settings.json` allow-list. A launched agent therefore has its orientation and permissions from its first message. Answer 4 writes only a commented `ai-config.toml`.
- **`resume` is optional.**
  - With no `resume`, loom runs `start` on every turn, and the agent regains the thread from `loom ai orient --session`, which prints the chat's tail.
  - The Codex preset is `codex exec …` with no `resume`. It is **unverified**: Codex is not installed on this machine, and the plan says so until someone runs it.

### Links

**An agent can link from the chat to anything the viewer can show, and a click takes the reader there.**

**Decided:**
- One link form for everything: nodes, documents at a place, works at a page or a quote, annotations and sessions.
- Only what the viewer can display is linkable; a session's drafts and diffs are not.
- A link with empty text is named by the viewer (`[](loom:node/sh-0009)` reads `Theorem 3.1`); a link with text shows the text as written. The choice is the agent's.
- Links are checked when a message is posted, and a `loom link` helper prints a correct one, so the agent never composes one by hand.
- A click reveals the item where it is open, or opens it at the place named in the pane the reader is not focused on. A link to an annotation opens its target at the mark with the card open.
- Links in the chat get hover previews, as links elsewhere do.

*(verbatim, from the brainstorm's visual-elements list)* Links in messages: an empty link shows the viewer name for the item, a link with text shows text. Clicking the link follows it into the unfocused pane when document not already open, otherwise it puts the relevant document in focus in the pane it is open in and goes to the specified location, showing a little mark initially and then fading. Links get hover previews. This link system is unified across all documents, there is not a separate link system for the transcript and for the drafting documents, its all the same link system so it is predictable and unified and simpler in code.

**Settled in planning:**
- **The form is `quilt:KEY[#PLACE]`** for everything the quilt owns: `[](quilt:sh-0009)`, `[](quilt:drafting/main.tex#sh-0009)`, `[](quilt:a-2026-09-16-0001)` and `[](quilt:s-2026-09-16-0001)`.
  - The key's shape decides the kind: a node id, a document path, an annotation id or a session id.
  - Works keep `cited:SCHEME:VALUE#page=N|#quote=…` (DR-166). This replaces the brainstorm's `loom:node/…` example.
- **Arras may now use loom's vocabulary.** The author is moving away from book 10.8's separation. The word `quilt` leaves `arras/tests/unit/forbidden-words.spec.ts`, and the rest of the guard is untouched in this plan.
- **One rule, no exceptions.**
  - Already open: that item is brought into focus in its pane and moved to the place. A document's links to its own content behave the same way.
  - Not open: the item opens as a new tab in the unfocused pane, with the pane's other tabs kept. In a node | context split, a context link to another node therefore gives that pane two node tabs.
  - The phase-4 context exception (DR-250-ikmartin) is superseded.

### What it did

**A session's What it did view is the plain record of everything the agent did through loom.**

**Decided:**
- A chronological list of everything in `run.log`, to be edited down later.
- It opens at the bottom of its page, so the newest action is at the bottom and is the first thing seen.
- Each row gives a link to the annotation where there is one, the fixed name of what it concerns (`draft1.tex`, `sh-0009`), never a derived one such as `Theorem 3.1`, and its state.
- The annotation state system is to be fixed separately.

### The formatting document

**Agents are told, during orientation, how to write what a person reads in the viewer.**

**Decided:**
- A formatting document beside `orientation.md`, served to the agent by `loom ai orient`; a stub exists at `loom/src/loom/assets/ai/formatting.md`.
- It records the link rules: empty link text is named by the viewer, and only what the viewer can show is linked.
- It tells the agent to write proposed text as a suggestion, which the viewer displays, rather than as a file in its session, which it does not.
- Contains instructions for math formatting to achieve proper rendering in the transcript and in annotations
- Contains relevant information regarding loom's rendering system and conventions so content can be written properly, lists packages and dependencies used (like MathJax) that are relevant.

### Proposed dependency edges

**An agent can propose that one result depends on another, and the author decides.**

**Decided:**
- A proposed edge is a suggestion annotation whose proposed text is `\uses{…}`; no new kind of record is made.
- Loom never writes the edge into the author's source; the author applies the suggestion.

## Decisions I am taking (stated so they can be overruled at review)

1. **One Chat at a time.**
   - Opening a session's Chat, from the picker, a `quilt:s-…` link or a URL, selects that session. Any other session's Chat tab is closed.
   - So the Chat on screen is always the attached session's, and the footer and the Chat never disagree.
   - Choosing a session keeps focus where it was (DR-253-ikmartin).
2. **A packet holds the person's own annotations and replies**, `created` or `replied` since the last message that carried any. Edits, resolutions and discards wait for the state-system work.
   - The inbox event stores each annotation in full, since it is the faithful record of what was sent.
   - The Chat shows only the counts.
3. **Message bodies are rendered by loom** with `render_markdown`, the same function annotation bodies use, so math and links render identically everywhere. `/_api/events` and the transcript pages carry `body_html`.
4. **The status line reports only what loom knows** (P3): whether someone is attached (the heartbeat), the launched process's state, and the agent's latest `run.log` line. It never parses a vendor's output.
5. **`loom serve` stops rebuilding for heartbeats.**
   - `attach()` rewrites `attached.json` only when who is attached changes, or when the last beat is 30 s old (STALE stays 90 s).
   - `inbox.jsonl` no longer triggers a rebuild, because the Chat's live tail comes from `/_api/events`.
6. **What it did's rows get their annotation from the log line itself.** `loom comment` appends ` → <id>` to its `run.log` line, so a row links its annotation without guessing from timestamps. That annotation's key is the fixed name.
7. **An annotation link's hover preview is its card**, read-only, drawn by `AnnotationBox`. Node and work links keep their previews. Documents and sessions get none, as today.
8. **`loom agent check` is a new group**, `loom agent`, as the brainstorm named it. `loom ai check` already means something else: files written outside a session.
9. **The inbox gains a lock.** `post()` takes an `fcntl.flock` on the inbox, so the person and a launched agent cannot draw the same `seq`.

### Phase 5 · Launching

- **`config.toml`**: `[ai] launch = false`, added to `scan/quilt.py` `CONFIG_KEYS` and `QuiltConfig`. The retired `agent` and `runner` keys stay accepted and ignored.
- **`ai/ai-config.toml`**:
  - Keys: `name` (must satisfy `is_agent`), `start`, and an optional `resume`.
  - Placeholders: `{session}`, `{agent_session}` (uuid5 of the quilt and session), `{prompt}` and `{quilt}`.
  - The user-level `~/.config/loom/config.toml` `[agent]` table has the same keys, and the quilt's file overrides it.
  - Claude preset: `start = ["claude","-p","{prompt}","--session-id","{agent_session}"]`, `resume = ["claude","-p","{prompt}","--resume","{agent_session}"]`.
  - Codex preset: `start = ["codex","exec","{prompt}"]`, marked unverified.
- **`loom init`** (`cli/quilt.py:205`):
  - Asks the questionnaire. `--ai claude|codex|other|none` skips it, and without a terminal the answer is `none`.
  - Answers 1 and 2 run `init_layer` (Claude with `permissions=True`).
  - Writes `ai/ai-config.toml` and adds it to `.gitignore`.
  - `--launch-agents` / `--no-launch-agents`.
  - The printout names the file and says whether agents will be launched.
- **New `loom/src/loom/agent.py`** holds the launcher, owned by `ServeSession`.
  - **When it launches**, checked every second: launching is on; the config resolves and is not tracked by git (`git ls-files --error-unmatch`); a person's message is newer than the agent's cursor; nobody is attached live; and no process is running for that session.
  - **How it launches**: `cwd` is the quilt, the environment carries `LOOM_SESSION`, the command runs in its own process group, and stdout and stderr go to `agent.log`.
  - **State**: `agent.json` records `{state: running|done|failed|stopped, pid, started, ended, code, error, turns}`.
  - The first turn uses `start` and later turns use `resume` when it exists.
  - **The prompt is loom's own, vendor-neutral**: a message is waiting in session `{session}`; run `loom ai orient --session {session}` if you have not, then `loom session next --json --as "{name}"`, act, and answer with `loom session say`.

## The study: the implementor as author, a Sonnet agent as the agent

This runs after phase 6, on the whole of 0.14, and follows plan 0.13 §17.

**Setup:**
- A fresh copy of the showcase in the scratchpad, with `git init`.
- `[ai] launch = true`, and the Claude preset in `ai/ai-config.toml` with `"--model", "sonnet"` added to both argument lists. The agent is therefore launched by `loom serve` itself, which tests the launch path.
- `XDG_CONFIG_HOME` points at the scratchpad.
- `loom agent check` passes first.
- The implementor plays the author through Playwright (`arras/scripts/drive.mjs`) at 1440×900, taking a screenshot at each step. The faults log is `scratchpad/study/faults.md`.

**Scenarios, one pass each:**
1. **Cold start.**
   - Choose a session: the Chat opens and focus stays.
   - Make three annotations: an objection on a node, a question on a PDF quote, and a suggestion in a draft. The tray lists them and the preview is right.
   - Send a message: the agent is launched, and the status line shows it working with its activity.
   - The reply arrives with a summary line under the person's message.
2. **Links.**
   - Ask the agent to answer with links: an empty node link, a titled link, a document at a place, an annotation, and a work at a page.
   - Check the naming, and follow each link twice, once with the target open and once with it closed.
   - Check that an annotation link arrives with its card open, and that hover previews work.
3. **Resume.** Send a follow-up that relies on the earlier reply: the second turn uses `resume` and the agent remembers.
4. **Packet only.** Make one annotation and send with no text.
5. **Stop.** Ask for a long task, press stop: the status line says stopped, and the next message launches again.
6. **Failure.** Point `start` at a missing executable: the status line says it failed to start, and `loom agent check` names the fault.
7. **Tracked config.** `git add ai/ai-config.toml`: nothing launches, and the status line and `agent check` say why.
8. **A dependency edge.** Ask the agent to propose one: a `\uses{…}` suggestion appears on the right node.
9. **A long transcript.** Seed 500 messages with a script. The Chat opens at the bottom and scrolling loads older pages. A static build (`loom build`, served with no API) shows the same transcript.
10. **What it did.** Rows are in order, open at the bottom, name fixed keys, link their annotations and show states.
11. **Cold resume.** Stop serve, rebuild loom, serve again and send: the agent resumes from the chat's tail.

**Cost discipline:**
- Sonnet throughout, with short prompts.
- Anything deterministic is checked with Playwright and not with the agent.
- At most three iterations, fixing between them. Stop when an iteration finds no fault worth fixing, and state what the study cannot answer: Codex, and a person other than the implementor.

**Report**: `docs/reports/0.14-chat-overhaul.md`, with scope, a verdict table per scenario, faults found and fixed, and the screenshots under `docs/reports/images/0.14-chat-overhaul/`.

## The principles check

This runs last, after the study, on the screenshots it produced and on fresh ones at 1440×900 and 1100×800. Each element gets one row: its **question**, the reader's, in one short sentence, and a verdict on each principle. A failure is fixed or brought to the author before 0.14 is called done.

| element | question it answers (P4) | P1 | P2 | P3 | P5 | P6 |
|---|---|---|---|---|---|---|
| Chat view | what has been said in this session? | opens on the newest message, not on a header | the session is named once, by its tab | — | — | no heading, no chips |
| status line | is the agent there, and what is it doing? | one line, below the transcript | the only place agent state is said, so the footer and picker must not restate it | only the heartbeat, the process state and the log line | — | empty states say one short thing |
| packet tray | what will my next message carry? | hidden when empty | not repeated in the message itself (summary only) | the preview is the exact text | a row link leaves the Chat in place | preview behind a toggle |
| summary line | what did that message carry? | — | counts only | counts from `changed` | — | drawn only when non-empty |
| send / stop | how do I say something, or halt the agent? | — | — | stop only while running | — | no other controls |
| links | where does this point? | — | the name comes from the viewer, once | an unresolvable link never reaches the transcript | the source stays on screen: one rule, the unfocused pane | the flash fades |
| What it did | what did the agent do, in order? | opens at the newest action | fixed keys, not reader names | only `run.log` lines | a row's link opens beside | no summary, sections or report |
| rail cluster | which reading of this session? | — | two views, not three controls | — | — | no discussion link |

**How each column is checked:**
- **P1**: the first screenful of each view is its subject, measured from the screenshot.
- **P2**: search the whole screen for each fact the element states, such as the session's name, the agent's state or an annotation's kind. Anywhere it appears twice, one copy goes.
- **P3**: for each string the element can show, name where its data comes from, and fail any string that is inferred.
- **P5**: for each link kind, follow it from the Chat and check the Chat is still visible.
- **P6**: list everything drawn in the empty states (no messages, no packet, no agent) and justify each item, or remove it.

The table, with its verdicts, goes into the report.
