# 0.17.2 — adoption: an agent's copy as a second incoming source

Luisa's part of plan 0.17. An agent works in its own copy of a document under `drafting-ai/`; adoption brings the copy's changes back into the person's documents. The design treats the agent as a collaborator and its copy as an incoming revision, so this plan builds adoption on the pipeline a document workspace pull already uses — Incoming, the incorporation contract, review origins, Needs review — rather than beside it.

Read first: [0.17-ai-drafting-and-compare.md](0.17-ai-drafting-and-compare.md) — decisions 9–14, 28 and 29, **the adoption analysis** (why adoption writes where each node lives and never supersedes, over the four examples E1–E4), and **the interface 0.17.1 fixes**; and [ai-drafting-study.md](../reports/ai-drafting-study.md) §5–§8.

## What 0.17.1 hands over

- `drafting-ai/` documents are live, their nodes carry derived ids (`zk-0001-ai`, `NodeRec.derived_of`), and `ScanResult.document_role` says which directory a document is in.
- A copy is written by `loom draft DOC --ai NAME` as a `copy` step: the flat source as its document text, and a base `{key, step, hash}` per derived key. `History.bases(copy)` and `History.copy_of(copy)` read them, already counting the `adopt` and `refresh` lines this plan writes, in the shapes the interface fixes.
- "Changed" is `mathematical_hash` (decision 28), so a display name changed alone (DR-301-luisa) is never a change to review.
- The synthetic quilt carries `drafting-ai/aidoc.tex`, a copy of `drafting/main.tex` with a node unchanged, changed by the agent, changed on both sides since the copy, new, deleted and moved.

## What exists today, and what changes

- **Incoming** (`render/incoming.py:64`) scans a base tree and an incoming tree and pairs nodes by identical key. An adoption's pairing strips the derived suffix and reads the base from `History.bases`, and what it produces is an incoming tree in the same form, so `attach_incoming`'s rendering, word spans and fragments serve it unchanged.
- **The contract** (`sync.py`: `prepare_incorporation` `:321`, `incorporate_pull` `:394`, `_expected_blobs` `:434`, `finish_incorporation` `:450`) pins the exact revision, refuses uncommitted edits in affected paths, stops on a conflict before any file changes, and commits once. An adoption is incorporated under the same contract.
- **Review origins** are written at `sync.py:524` into `SyncState` and read by `review_queue.rows_for` (`:92`), which gives a pulled block the cause `incoming-pull` (`:171`). They move to a store every source shares, since a quilt with no document workspace must still record an adoption's.

## Settled in planning

- **One module plans an adoption**, `loom/src/loom/adopt.py`. It pairs each derived node with its counterpart and classifies the pair from its base: unchanged; changed by the agent (offered); changed by the person only (not offered: refreshing takes it); changed by both (offered, drawn as a conflict); new (`zk-0012-ai`, offered, adopted as `zk-0012`); deleted (offered: taken, it leaves the document and its node file stays); defined outside the source's closure (offered only as a fork, E4, with the reason). The command line and arras both call it.
- **An adoption is an incoming revision.** From the taken keys, `adopt.py` builds the person's tree as it would be after Finish — each taken node's text in its home, inline or in its node file; new nodes where the copy placed them; deleted ones removed from the document; the prose between nodes merged — as a commit on `refs/loom/adopt/<copy>`, never on a branch. Everything after that is the pull's pipeline: the Incoming rendering, the patch, the pins, the contract, the one commit.
- **The prose between nodes is merged by `git merge-file`:** base the copy step's document text, ours the source flattened now, theirs the copy, each with every node's body reduced to one placeholder line naming its key, so only prose and order merge; each placeholder is restored to the node's form in the source. A conflict is shown and stops Finish.
- **Take and keep are node by node, for an adoption only** *(to confirm with the author)*. A document workspace pull stays whole: the workspace must converge on one revision. An adoption's take and keep are pending decisions per reviewer, stored as the review queue stores its own (`review_queue.py:194`); a take-all sets every offered node.
- **Review origins become one store** (`.loom/review-origins.json`), written by every source and read by `rows_for`: per block, its source (`pull:<commit>` or `adopt:<step>`), whether the source changed its text, its baseline fingerprint and whether it was changed locally before. The fields leave `SyncState`; the fixtures and demos are regenerated rather than migrated. A block an adoption changed waits in Needs review with the cause `adopted`, naming the copy, exactly as a pulled one waits with `incoming-pull`.
- **The command line's adoption finishes in a second step** *(to confirm with the author)*, as `sync prepare` and `sync finish` do: `loom adopt DOC [KEY…]` pins and prints the patch (`--to FILE` writes it), and after `git apply`, `loom adopt --finish DOC` checks the tree holds exactly the patched text and records it. A patch that is never applied never moves the bases.
- **The write endpoints** are `adopt-decision` (take or keep one node, or take all) and `adopt-finish` (prepare, show, then incorporate), beside `sync-incorporate` (`render/api.py:38`, `:100`); both carry and check the displayed reviewer (DR-304-luisa), who is the `adopt` step's actor.
- **Open annotations follow the text the person takes**: a new event in the annotation log (`records/log.py:20`), `retargeted`, re-anchors an open annotation on a taken node to its plain key and the source document; kept nodes' annotations and settled ones stay on the copy.
- **`loom ai refresh DOC`** is adoption in the other direction, written to the copy only, so it is an agent command *(to confirm with the author)*: it takes the person's changes to nodes the copy has not changed, merges the preamble and the prose, reports and leaves a node changed on both sides, and writes a `refresh` line with the moved bases.

## Behaviour that must survive

- A document workspace pull is fetched, reviewed, incorporated and queued for review exactly as today.
- Incorporating, from any source, never accepts mathematics.
- Loom writes the person's files only where a change was reviewed, and shows it first.
- An agent cannot adopt.

## Risks

- **The prose merge** is the least tested part: a spine whose nodes the copy both reordered and edited may conflict often. A conflict stops Finish, so the failure is a refusal, never a wrong write.
- **Moving review origins out of `SyncState`** touches every pull test and fixture; the rows `rows_for` produces for a pull must be identical before and after.
