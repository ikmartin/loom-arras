## User workflow

1. Create an AI copy with `loom draft DOC --ai NAME`. Human and agent can edit that copy; only the human can incorporate its changes into working documents.
2. Open Incoming and select the contribution. Show “Incoming from Overleaf” where applicable, or “Incoming from AI draft ‘aidoc’”; use the configured source name for other document workspaces. Commit identifiers belong in details.
3. Compare the proposal with the current working document. Choose **Use proposed version** or **Keep current version** for offered nodes, and explicitly include or leave document-level changes. Explain that unselected proposals remain in the AI draft and will appear again while they differ; this is not permanent rejection. Provide **Use all proposed changes**, without bypassing conflict or dependency checks.
4. Preview the complete resulting change, including prose, preamble, node placement and affected documents. Resolve conflicts and incomplete selections before proceeding. **Incorporate selected changes** applies exactly this preview and records the incorporation.
5. Continue in the existing **Needs review** queue for mathematical review. Show the contribution's readable source there. **Finish review** retains its existing acceptance meaning; incorporation does not accept mathematics.

Overleaf pulls remain whole-revision incorporations because their workspace must converge. AI contributions permit selection. Explain this difference where selection is offered; do not create separate review systems or imply that pulls gain per-node selection.

## Behavior specification

### Identity, comparison and selection

Retain the implemented `-ai` workspace identifiers and `NodeRec.derived_of`. Present the node's human-readable name and “proposed revision of zk-0001,” with the AI draft as context. The suffix is not a separate mathematical identity. Adopted revisions retain the original canonical identity; genuinely new results receive collision-free canonical IDs, with all references rewritten consistently. Recheck allocation when incorporating.

Separate source changes worth incorporating from changes that affect mathematical acceptance. Names, prose and other source edits remain visible and selectable. Use the existing suffix-normalizing `pair_hash` for mathematical comparison between AI and canonical text; name-only changes do not invalidate mathematical acceptance.

One planner pairs nodes against their recorded bases. Distinguish unchanged, proposal-only changes, author-only changes, identical changes on both sides, conflicting changes, new nodes and removals. Identical changes on both sides need no conflict resolution. Author-only changes are preserved. Handle deletion versus editing and moved definitions explicitly; never infer a replacement destination from an obsolete path.

Selections belong to the displayed reviewer and exact comparison, using the existing pending-decision pattern without treating incorporation choices as mathematical judgments. Changed proposal, author text, baseline, reviewer or selection invalidates the final preview. Preserve still-applicable choices only when their fingerprints still match.

Selecting a node does not silently select prose changes. Offer document-level prose, preamble and ordering changes as an explicit group alongside node choices. Preview the complete result even when that group is left unchanged. If the chosen node changes cannot be represented consistently without a document-level change, explain the required selection or edit and stop.

Label a removal **Remove from this document** when the canonical node file remains. Show other documents affected by an update to a shared node. Validate the resulting selection for missing new dependencies, dangling references, duplicate definitions and invalid placements; do not silently incorporate additional proposals. For E4, explain “This result belongs to another document. Incorporate it as a separate result.” Reuse the existing fork machinery for this bounded case, without offering definition relocation or a general node manager.

### Baselines and conflict resolution

Use per-node bases from the prerequisite copy records, plus a document baseline for prose, preamble and structure. Initially this is the copy step's flat source. Record subsequent baseline updates during incorporation and refresh; repeated operations must not always merge against the original copy. Extend the prerequisite record shapes and readers explicitly where needed, preserving compatibility with existing copies.

Merge prose with `git merge-file` using normalized node placeholders, restoring the original inline or included representation afterward. Treat ordering and node selections together when validating the result. A conflict stops before author-file changes. The user can edit the AI draft or working source in their existing editor, save/commit affected author changes as required by the incorporation contract, and refresh the comparison. No new merge editor is required. Outstanding conflicts stay visible with the files and alternatives involved.

Advance only baselines actually reconciled or incorporated. Unselected proposals remain outstanding. A no-op repeat must not create another incorporation or resurrect old prose changes.

### Shared incorporation contract

Use one source-neutral incorporation pipeline for comparison rendering, final patch validation, writing and history. AI-specific code prepares the proposed tree; it does not duplicate the pull machinery. Build each selected node into its current home, inline or in a node file, and preserve unselected working text.

Pin the proposal revision, author revision, baseline, choices, reviewer and final patch with immutable identifiers. A mutable `refs/loom/adopt/<copy>` may locate a prepared contribution but is not sufficient proof of what was inspected. Revalidate immediately before writing. Refuse conflicting or uncommitted changes in affected author paths and stale previews with an actionable explanation.

CLI and Arras both preview first, then explicitly incorporate and record through the same operation. Do not require users to apply a patch and separately record completion. Reuse the existing commit/record contract rather than imposing a different commit count for AI contributions. Define rollback or recoverable failure behavior so a failed record write cannot be reported as successful incorporation. Nothing pushes to a remote.

Move review origins from `SyncState` into shared `.loom/review-origins.json`, preserving source, baseline fingerprints and prior local-change information. Migrate or compatibly read real existing quilts, not just regenerated fixtures. Keep `pull:<commit>` and `adopt:<step>` as internal provenance. Existing acceptances remain historical records; changed mathematics and affected dependents use the existing freshness and review rules, while cosmetic changes do not create mathematical review work.

### CLI and Arras

`loom adopt DOC [KEY…]` prepares and displays the selected result and prompts before incorporation. The normal command applies and records the confirmed result itself. Noninteractive inspection uses `--json` without writing author files; incorporation of a saved preview must supply its immutable token explicitly, proposed as `loom adopt DOC --incorporate TOKEN`. Never treat absence of an interactive terminal as approval. `--to FILE` may export the prepared patch for advanced use, but export does not advance baselines or replace the normal workflow. Do not implement the old manual `git apply` / `--finish` route in this milestone. Adoption is author-only and absent from `AGENT_COMMANDS`.

In Arras, Incoming lists one entry per contribution and reuses the existing pair layout, rendered statements, source diffs and affected-dependency links. Selection controls lead to a final preview, followed by a separate **Incorporate selected changes** action. Internal API names may remain `adopt-decision` and `adopt-finish`, but preparing/showing a preview must never perform incorporation. Both mutation endpoints validate the displayed reviewer and applicable pins. Extend `IncomingReview` to carry source, selections and preview identity without creating a second review page.

Keep annotations accessible on the original contribution and link back to that context after incorporation. Do not silently drop, settle or move comments. Automatic retargeting is outside this milestone; later transfer must preserve history and leave unresolved anchors visible rather than guessing where a comment belongs.

### Updating the AI copy

Retain `loom ai refresh DOC`, described as **Update AI draft from the working document**. It uses the same pairing and merge primitives, writes only the AI copy, brings in author changes where safe, preserves outstanding proposals and reports conflicts. It may be an agent command because it does not incorporate into author files or accept mathematics. Update applicable node and document baselines; unresolved differences remain visible, and a partially refreshed copy must not be reported as fully fresh. This is copy maintenance, not another review queue or “reverse adoption.”

## Scope boundary

This milestone incorporates into an existing working document. Creating an independent talk or alternate paper through `loom adopt --as` is removed from its implementation phases. E3 becomes a documented unsupported case with a clear message, not an implicit fallback to revising the original. Before scheduling a separate-document feature, specify and preview which results remain shared and which receive independent identities; users should not have to infer that from inline versus node-file storage. General annotation transfer is likewise outside this delivery. Track either as a work-queue item with an observable trigger if separately scheduled; neither blocks core incorporation.

## Implementation phases

1. **Shared provenance:** extract the review-origin store with compatibility for existing quilts. Preserve pull review behavior and expose readable source labels.
2. **Planner and preview:** implement `loom/src/loom/adopt.py`, normalized comparisons, selection validation, document merging, evolving baselines and immutable previews according to the behavior specification. Reuse existing Incoming rendering and fork primitives.
3. **CLI incorporation:** implement inspection, confirmation and the shared apply/record operation, adoption history and verification, author-only enforcement, and contribution-context links. No manual apply/finish requirement.
4. **Arras Incoming:** add source entries, clear choices, document-level selection, conflict explanations, result preview and the explicit incorporation action. Update the manifest and write API together.
5. **Copy refresh:** implement copy-only synchronization with the planner's common merge primitives and baseline handling. Update the agent orientation to name this command.
6. **Documentation and delivery:** reconcile the umbrella plan; update book chapters 7, 10, 11, 12 and 15 and the manifest specification to the implemented behavior. Record decisions/deviations for changed `[decided]` requirements. Regenerate fixtures and demos, rebuild and re-vendor Arras, verify, and merge into `main` when delivery is complete.
