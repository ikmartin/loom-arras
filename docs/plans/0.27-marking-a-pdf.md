# 0.27 — Marking a PDF

## Context

The author asked for what Preview and Skim give a reader: highlight or comment on a PDF, come back later and find it there, and something resembling a full PDF editor inside loom. Reading the code and testing saves on scratch copies gave this picture of where things stood:

| PDF | What a person could do | What they saw later |
|---|---|---|
| A cited work's page | `annotate`, through the composer | a drawn mark |
| A cited work's page | `quote` | a line in the notes fold, nothing on the page |
| A project file | `quote` only | a line in the notes fold, nothing on the page, and "its words are gone" straight away, since `notes.detached` searched the PDF's raw bytes for the words |
| A compiled document | nothing on the PDF; annotations go on the rendered text | nothing on the PDF |
| One already marked up in Preview | nothing | highlights painted, but nothing to click and no comment to read |

What the tests on scratch copies found:

- pdf.js's `saveDocument`, already in the bundle, appends real Highlight, FreeText and Ink annotations, with comments, after the original bytes, and Apple's PDFKit reads and draws them. It writes these from plain data, with none of pdf.js's editor interface.
- PDFKit's own save, the engine under Preview and Skim, rewrites the whole file: it re-embeds fonts, turned one `ℓ` into `"` in `pdftotext`'s reading, moved word boxes by up to 0.02 pt, and dropped the annotations' `/NM`. Nothing identifies an annotation across such a save.
- `digests.md` §10 says "the document an anchor was checked against must never change", and `refs/check.py` reports `version_mismatch` on a changed `paper.pdf`. A library PDF cannot hold its reader's marks. Nor can a compiled PDF, which the build replaces.

## Decisions

The author approved the first; the others follow from it and from the principles, and are recorded here so each can be questioned.

1. **Loom's log is the record, and a PDF is what it is exported to and imported from** (P2, P4, P7). A mark is an event in `.loom/annotations/notes.jsonl`. It reaches coauthors with the rest of the log, an agent reads it with `loom since`, and no PDF's bytes change. There is no live sync with a file, because nothing identifies an annotation across a Preview save.
2. **A mark is a note, with a `mark` saying how it is drawn.** Annotations stay the record of review, with kinds, severity and threads. A note already reaches work pages and project files and holds `quote`, `page`, `rects` and an optional body. It gains `mark`, `strokes`, `artifact` (the file's hash when it was written) and `origin` (where an import came from), and events to change, erase and restore it.
3. **A mark is one gesture and asks for no session** (P14). The viewer sends none; the record's `session` stays empty unless an agent's command names one. It is drawn whatever session view is selected (V7), and it stays out of transcripts.
4. **A mark does not fade.** Fading suits a passing thought (P14), and a highlight that vanished after two weeks would be a surprise. A quote keeps fading as before.
5. **A mark is drawn in the annotation neutral** (A4: hue is the kind, and a mark has no kind). A colour an import brought is kept on the record and written back on export, not drawn. Whether marks should take colours is left **Open.** in `model.md`.
6. **Geometry is recorded for a mark and pinned to the bytes it was drawn on** (A3). When the file's hash changes, a mark with words is found again on its page and drawn there; one that cannot be found, or that has no words, is detached: listed and not drawn.
7. **Import is an explicit act from a chosen PDF, or from the PDF being read.** It matches by page, position and comment, so taking in the same PDF twice adds nothing. Annotations taken in from the file being read are hidden on the canvas, so the record governs them and nothing is drawn twice. Skim keeps its notes outside the PDF by default, so a person exports from Skim first.
8. **Export runs in the viewer**, so Python gains no PDF dependency and a static build can do it too. It opens the PDF separately, because `document_()` shares one document between panes. pdf.js writes Highlight, FreeText and Ink; underline, strike-out and a pin are written as Highlights with their own appearance and renamed in place to `Underline`, `StrikeOut` and `Text`, a same-length rewrite of the appended bytes. Boxes, ovals and arrows are written as Ink, which every reader draws.
9. **Page edits always write a new file** (P7), from the same interface: rotate, delete, reorder, insert from another PDF, extract. `pdf-save` refuses to overwrite, and a library work or compiled PDF is never written. pdf.js has no rotation, so a page's `/Rotate` is rewritten in place at the same length after extraction.
10. **Editing a page's own text and redaction are left to a dedicated application**, reached by "Open in its application", which PDFs now take.

Compiled documents get no marks: their annotations live on the rendered text, and a PDF of those is [WQ-28](../work-queue/WQ-28-annotated-export.md).

## The phase, by checkpoint

All one phase, built without stopping unless a decision is the author's. Each checkpoint ends in `scripts/verify` for the lanes it touched and a commit on the branch.

**A. Show what is there.** Fix `detached` for a PDF. Rectangles use one convention, `[x0, y0, x1, y1]`, everywhere, including `loom note --box` and an image's region. A note with a place is drawn on a work's page and a project PDF. A PDF's own annotations can be clicked and their comments read.

**B. The highlighter.** Record, events, API and command: `mark`, `artifact`, `note-change`, `note-erase`, `note-restore`, `loom note --mark`, `--edit`, `--erase`, `--restore`. Viewer: highlight on the selection chip, a markup bar with highlight, underline, strike and pin as tools that stay armed, a card to comment and erase, undo and redo, and drawing at once rather than after the next publication.

**C. Export and import.** "Save a copy with annotations", from notes and from annotations on a work's pages; "Take in annotations" from a chosen PDF and from this one, through `notes-take`; hiding what was taken in.

**D. Ink, free text and shapes.** `strokes`, drawing, moving and resizing, in the markup bar.

**E. Page edits.** The pages editor, `pdf-save`, "Open in its application".

**F. Close.** Specs, design, fixture, command reference and vendored bundle; `scripts/verify full`; this file's Implementation section.

## Verification

- loom unit tests: replay of the new events, fading, detachment across a changed file, every endpoint and refusal, `pdf-save` never overwriting (C4).
- arras vitest: rectangle merging, stroke simplification, moving and scaling, an export read back by pdf.js with its bytes as a prefix, an import's mapping of every subtype, page edits.
- arras Playwright, against a real `loom serve`: highlight, comment, erase and undo on a project PDF and a work's page, each surviving a reload; ink, text and shapes; a download read back; an import taken twice; the pages editor writing a new file; no tools on a static build, marks still drawn.
- By hand: a look at the marks in the browser, and an exported PDF opened through PDFKit.
