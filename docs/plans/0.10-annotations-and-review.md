The verbatim toggle of Part G moved to [0.11](0.11-run-review-view.md), which is where it reads. Written 2026-09-18, superseding the reminder of 2026-09-17. ## Context

Three things are wrong at once, and they are one thing.

**Annotations cannot be edited.** A review record is a JSON file rewritten whole (`records/annotations.py:76`), and book 7.4.3 says resolution is "the one field loom rewrites in place". So a re-check that finds the same fault still standing can only *reply*, and after three passes a finding wears three restatements of itself. The fix is an append-only event log where `edited` supersedes a body and only the current body renders.

**The agent's report cannot be read.** Everything a mode produces lands in `ai/runs/<run>/*.notes.md`, and the one place built for reading — arras — lists those files by name. Terminals do not typeset mathematics, so today a report is read as LaTeX source in a chat window that then disappears.

**The AI layer's entry points are shaped around a launcher that should not exist.** `loom ai start` runs your agent as a subprocess of loom, owning its argv convention and putting loom in the process tree for a whole session — the runner declined as WQ-15, in miniature, and redundant besides, because `loom ai init` already writes a `CLAUDE.md` whose one sentence is the same instruction.

What unifies them: loom records what an agent did, and the recording is per-file, unqueryable, and wrapped in a process it should not own. This plan makes the record a log, makes it answerable, and gets loom out of the way of the agent.

## Scope

## Part A — The annotation log

`annotations/log.jsonl` at the quilt root replaces `comments/<author-slug>/<date>.json` and `ai/runs/<run>/annotations.json`. One append-only, event-sourced table; current state by replay.

**Events** `created`, `replied`, `edited`, `resolved`, `discarded`. **Columns** `id`, `event`, `when`, `author`, `kind` (`human` | `agent`), `run`, `target`, `against`, `anchor`, `annotation_kind` (`suggestion`, `objection`, `question`, `ok`, `citation`), `severity`, `body`, `payload`, `placement`, `status`, `reply_to`. (Corrected 2026-09-18: this line said `annotation-kind` and `reply-to` with hyphens, which the code has never written or read. Chapter 7 now carries the list, and a line spelling them the hyphenated way is reported rather than silently misread.) JSONL because quotes hold newlines, and because two people appending in parallel merge as two lines.

**Severity** is Major / Moderate / Minor and grades the *fault*, not the enthusiasm: mandatory in review mode, optional elsewhere. **Payload** is suggested text carried in the record; **placement** is `replace` / `after` / `before` as a hint for where a viewer shows it. Everything is preview-and-copy; applying is WQ-27.

**Payload and placement.** A suggestion may carry text — a proof, a paragraph, a rewritten passage — as `payload`, a string in the record, with `placement` one of `replace` / `after` / `before` relative to the anchor, as a *hint* for where a viewer shows it. Everything is preview-and-copy: the author flips the verbatim toggle, copies, and pastes where they decide. A suggested proof is the same object, not a promotion. Applying anything is [[WQ-27]].

**Kind and run are separate columns**, not encoded into the author (`"AI-Claude"` was rejected): three columns make "everything from this run" and "everything any agent said about `rl-0002`" filters rather than string parsing.

**`[R1]`, `[R2]`…** are per-report display numbers in report order, for talking about points in chat; annotation ids are never shown to readers (WQ-23, settled).

### What this replaces, concretely

`src/loom/records/annotations.py` is the module (not `store.py`, which only imports from it). Its `Annotation` is 11 flat fields with `author.{kind,id}` and `target.{key,hash}` nested on the wire; `Record` is one file with `schema`, `discarded`, `annotations`. **The two storage globs are duplicated in four places** — `annotations.py:89`, `render/threads.py:152`, `scan/alloc.py:28`, and `cli/ai.py` via `record_paths` — and every one must end up reading the log instead.

`next_id` is already quilt-wide max+1 over all records, so ids survive the move unchanged. `Record.write()`'s atomic tmp-then-replace becomes an append; `load_record`'s error-string convention (it returns a string rather than raising) is what feeds `loom:foreign-annotations`, and the log needs an equivalent: a malformed line is reported, not fatal.

**Per-run cuts go.** The author decided (2026-09-18): the log is the only store. `ai/runs/<run>/annotations.json` stops being written, and an agent reads its own findings with `loom ai findings` (Part C) — the file existed because nothing could be queried, and the query now exists. Two consequences: `loom ai check` no longer sees a file loom itself wrote inside the run, and `scripts/gen_quilts.py:292`'s `_annotation_ids`, which reads ids back out of that file to drive `--reply`/`--resolve`, must read them from the log or from `loom comment`'s own stdout.

**The canonize cut stays** and is new work: `.loom/history/<step>/annotations.json`, the records that stood against the versions the step replaced, so a step explains itself alone and survives a run being discarded. `write_step` (`history/steps.py:125`) writes version files, `preamble.tex` and the document copy today and nothing else.

### Two bugs to fix while here

**`loom comment --run R --resolve <id-in-R>` silently loses the resolution.** In `_one_comment`'s resolve branch (`cli/review.py:198-221`), when the parent lives in the same file as the record being written, `prec` and `rec` are two in-memory objects over one path: `prec.write()` writes the status flip, then `rec.write()` at `:220` overwrites it. The existing test resolves a *run* annotation while writing as a *person*, which is the case that works. An append-only log cannot express this bug, so the fix is structural — but the **test** must be written, because it is the case an agent hits every re-check.

**`Records` is constructed without `history_dir` almost everywhere** — `render/build.py:144`, `cli/review.py:82,194,452`, `cli/ai.py:126`; only `cli/lint_cmd.py:54` passes it. A quilt with a non-default `[quilt] history` therefore reads its stale-cause diffs from the wrong directory in every command but `lint`. One-line fixes, but they need a test with a non-default history path.

## Part B — Anchors, and the cache that does not exist

An annotation records `against`: the sha256 of the text it was written against. When a scan sees a key's hash move and annotations point at the old hash, the old text is frozen into `.loom/history/texts/<sha256>.tex`. An annotation against text never touched again costs nothing; a text loom never saw — two edits between scans — leaves the annotation **unanchored**, "written against a text loom never recorded", rather than pretending.

**The storage exists; the trigger does not, and this is the plan's one piece of genuinely new machinery.** `write_snapshot`/`read_snapshot` (`records/snapshots.py`) already do exactly what is wanted: content-addressed, write-once, `.loom/history/texts/<hex>.tex`. But their only caller is `loom accept`, nothing on the scan path writes them, and **there is no last-seen-text cache anywhere in the tree** — nothing stores the previous scan's per-key hashes, so "a key's hash moved since the last scan" has nothing to compare against. `plan_freeze` compares against the history ledger's last recorded version, which only moves when `canonize` or `stamp` runs.

So the plan adds a bounded last-seen cache: one copy of the quilt's per-key hashes, rewritten in place on every scan, under `.loom/`. It also gives `loom serve` "what changed since the last scan" for free, which is worth having.

The wording throughout is *stood against the version you changed*, never *caused the change*: the author may ignore every suggestion, and causation is an explicit act.

## Part C — The AI layer's entry points

### The launcher goes

**Deleted:** `launch_agent` and `launch_prompt` (`ai/runs.py:37-56`), `[ai] agent` (`scan/quilt.py:57,105` and the `config.toml` template), `--no-launch`, and `test_run_launch_agent_if_configured`. `loom ai start` keeps only what it should always have been: allocate a directory, write `run.toml`, print the path — and it is a command the *agent* runs when you say "start a run for this".

The bootstrap already works without it: `loom ai init` writes `CLAUDE.md` and `AGENTS.md` from `assets/ai/vendor/root.md`, whose one sentence is *"Before doing anything, run `loom ai orient` and follow it"* — the same instruction `launch_prompt` passed, minus the run pointer. **DR-72 is retired**; DR-111 (the withdrawal of `[ai] runner`) is the precedent for how.

### `run.toml` records only what nothing can derive

```toml
created = 2026-09-18T09:14:02Z
name = "Referee of rl-0012"
discarded = false
```

`name` is authored, has spaces, and is **mutable** (`loom ai name "better title"`). `slug` goes; the directory is the timestamp plus the name slugified and truncated to **48 characters**. `read_run_toml` (`ai/runs.py:59`) is a hand-rolled flat parser that already strips surrounding quotes, so a quoted `name` needs no parser change — but `created` and `discarded` are written unquoted today and `session` is named in its docstring and written by nothing, so both should be tidied in passing.

A `target`/`about` field was designed and dropped: it is not scope, and as "what the split view opens on" it is derivable. **Record intent, derive fact, with no exception.** The pipeline is derived too — every mode writes `<mode>-<something>.notes.md` without exception, so the modes a run used and their order come from the directory's own filenames, which works retroactively on runs already on disk.

### Addressing a run by name

**`resolve_run`, beside `resolve_key` in `cli/_quilt.py:33`** and following its shape. Accepts, in order: nothing → the most recent undiscarded run; a name, case-insensitively; a prefix, if it matches exactly one; the directory name or relative path, so `LOOM_RUN` keeps working. An ambiguous prefix prints the matches and exits 2 — the `refs resolve` precedent, and a real case, since `referee` already matches two runs in the synthetic quilt. `open_runs` (`ai/orient.py:20`) already does the listing.

Behind **every** `--run`, not just attach: `loom comment sy-0004 "…" --run localization` is what an agent types repeatedly. Note `cli/review.py:159-179` currently duplicates `resolve_run` from `cli/_common.py:47` rather than calling it; that duplication goes.

### The commands

- **`loom ai runs [--all]`** — undiscarded by default, one indented line each as `YYYY-MM-DD: <name>`; `--all` adds discarded ones, marked. Without `--all` a run discarded by a bulk `--before` is invisible and cannot be found to undo.
- **`loom ai start "Name"`** — allocate and print.
- **`loom ai name "New name"`** — rename; the directory does not move.
- **`loom ai orient [--run NAME]`** — orient, and **attach**. There is no `loom ai attach` and no current-run pointer: `orient --run` already prints the orientation, the live state and the run's `thread.md` and `run.log`, which *is* reattaching, and its own output already tells the agent to pass `--run` from then on.
- **`loom ai findings --run RUN [--json]`** — every annotation this run made: id, target, kind, severity, status, quote. A filter over the log's `run` column, not new storage; `orient --run` summarises it. It exists because the real review run contains `.referee-ids` and `.audit-ids`, dotfiles in which the agent cached its own annotation ids for want of a query.

`loom ai` divides on trust and should say so in the orientation and Chapter 11: **yours** are `init`, `check`, `discard`, `promote`; **the agent's** are `orient`, `start`, `findings`, `name`; `runs` is both. `promote` is already in the agent's deny list, which is the proof the division is real.

### `CLAUDE.md` is yours, with one line of loom's

`upgrade_layer` (`layout.py:159-166`) **overwrites `CLAUDE.md` and `AGENTS.md` whenever their content differs from the shipped asset**, so project-specific instructions added to a quilt's `CLAUDE.md` are silently clobbered on the next upgrade. Loom ships three kinds of file into a quilt the author may also own, with three policies — `.gitignore` gets one line appended and is never rewritten; `ai/modes/*.md` are hash-tracked so an edit is kept and the new version written as `.new` beside it; and the file with the strongest claim to being the author's gets the crudest.

Give it the `.gitignore` treatment: **ensure loom's line is present, replace a known earlier version of it, never touch the rest.** `assets/ai/vendor/root.md` then becomes `CLAUDE_LINE`, a constant beside `GITIGNORE_LINE` (`layout.py:27`) — and being a constant rather than a markdown file is what keeps the one-line constraint visible, since the check stops being idempotent the moment someone adds a second paragraph.

## Part D — Bundle: the command goes, the engine stays

**This is smaller than the design session assumed, and better.** `build_bundle` + `write_bundle` are the engine behind two other things: `loom compile KEY` already builds, writes and compiles a bundle when the target is not a master (`cli/build_cmds.py:128-129`), and `loom check --bundles all` does the same for every environment key and raises `loom:bundle-failed` (`:192-193`). `render/fragments.py:23` also imports `_macro_block` from `tex/bundle.py`. So `tex/bundle.py` survives nearly intact as an internal module.

**What goes:** the `loom bundle` command (`build_cmds.py:46-107`), its registration, `write_bundle`'s run-copy branch (`:39-42`), and `GITIGNORE_LINE = "ai/runs/*/bundle-*.tex"` with the `.gitignore` lines it wrote.

**What replaces it:**
- **`loom source KEY --closure`** prints `build_bundle(result, key).text` to stdout. Nothing to clean up, nothing to gitignore, and no stale file to hold — the hole where an agent reasons from a bundle written before the author's edit dissolves rather than being fixed.
- **`loom compile KEY --with FILE`** and **`--draft FILE`** — one option each on a command that already bundles and compiles, reusing `substituted_region` and `draft_bundle` unchanged. This is strictly better than the temp-copy scheme the session proposed, and it is why `apply_unified_diff` and its literal-line-number hunk matching stay exactly as they are.

**The cost is prose, not code.** `blocks.md` has thirteen bundle lines and its §Inputs rule is load-bearing (*"A key: `loom bundle KEY --run $LOOM_RUN` … This is the complete context; you may assume nothing outside it"*); `orientation.md` §5, §6 and §8 are built around it (*"Read bundles, not directories. A bundle is complete by construction"*); `audit.md`, `brainstorm.md`, `draft.md`, `question.md`, `quick.md`, `referee.md` and `simplify.md` each name it, `ingest.md` alone does not. Three tests in `test_ai_layer.py` (`:163`, `:287`, `:333`) and five in `test_tex_layer.py` invoke the command, and `test_ai_layer.py:322` asserts `run.log`'s first entry is literally `"loom bundle dm-0003"`.

[[WQ-27]]'s design names `bundle --with` as the preview command and [[WQ-28]] relies on "the bundle machinery"; both are re-pointed at `compile --with`, and [[WQ-24]] names the deleted command.

## Part E — The modes

One editing pass over `src/loom/assets/ai/modes/*.md` and `orientation.md`, carrying Part C's and Part D's consequences together with this part's, because Appendix C and D reproduce these files verbatim and `gen_quilts.py` regenerates both fixture quilts from them — so every pass over an asset is also a pass over the book and the fixtures.

### Review mode

Mode 7 of the author's global rules, whose text is in the reminder and goes verbatim into `docs/source/global-rules.md`. `ai/modes/review.md` is a separate mode beside audit and simplify, writing annotations with severity and payloads plus a report; **no compiled LaTeX/PDF artifact** — declined, confirmed by the author on 2026-09-18, on the grounds that the annotation system supersedes it and WQ-28 exists for those who want one. This is a deliberate departure from the mode text's own "produce a latex/pdf pair", and the decision record says so.

Category → block: new citations → `[simplifications]` type `new-citation` plus `[citation-ledger]`; bad citations → `[citation-ledger]`; unnecessary hypotheses → `unnecessary-hypothesis`; merge-or-delete → `merge-or-delete`; sharpenings → `[sharpenings]`; self-containedness → `[self-containedness]`; **mathematical errors and grammar/wording/clarity → `[referee-review]`, reused.** An earlier draft proposed two new blocks on the grounds that the existing modes do not hunt errors, which is true of `audit.md` and false of `referee.md`. `[referee-review]` already carries Major Issues, Minor Issues, Clarity/Exposition and Reproducibility with severity, location, fix and annotation id per item. Blocks are output structures catalogued once in `blocks.md`; modes are procedures that select and order them, so review mode emitting `[referee-review]` no more makes it referee mode than both emitting `[summary]` makes them the same. Review mode's Major/Moderate/Minor grouping comes from the annotations' severity field, not from the block's own headings, which are left alone. **The completeness check learns no new blocks.**

### Quick mode returns

An earlier draft dropped it as producing nothing durable. Walking a session end to end found the gap it fills: between a clarification in chat, which vanishes, and a mode, which writes a five-block document, there was nothing.

> **Purpose.** A short, durable answer. Use quick when the author asks something in passing that is worth re-reading in a week but does not deserve a document — a definition recalled, a step explained, a constant checked. If the answer needs worked examples, edge cases or a stress test, that is `question`. If it turns up a defect, annotate it and say so.
>
> **Output.** `quick-SLUG.notes.md`: `[answer]` alone. This is the only mode with no `[summary]`, because a summary of a quick answer is longer than the answer.

The rule that decides between quick and chat belongs in the orientation: **if the author would want to re-read it next week it is quick; if it is a clarification of something you just said, it is chat.**

### A re-check edits; it does not reply

`referee.md`'s rule is *resolve if met, reply if not*, which is what makes pile-up look inevitable. The log allows better:

| the re-check found | event |
|---|---|
| the same fault, still standing | `edited` — one finding, restated |
| the fault is met | `resolved`, with the reason |
| the agent was wrong to raise it | `discarded` — "resolved" implies it was addressed |
| it became a different fault | resolve, then create |

**A reply is dialogue; an edit is restatement.** The **report** is a separate artifact and the reminder had no answer for it, having reasoned only about annotations: a re-check writes `referee-KEY.2.notes.md`, numbered passes, each immutable once written. `referee.md` already had this convention and it was dropped for a reason that applied only to annotations.

`blocks.md` §Findings gains `--severity`, `--payload`, `--placement` and the `citation` kind; §Inputs and §Outputs lose bundle; §Never keeps "never write the log by hand".

## Part F — Reference notes

`reference-notes.jsonl` at the quilt root, append-only, one object per accepted suggestion: `work` (free text as the agent described it), `for` (keys), `claim`, `identifier` with `verified: false`, `accepted` (`when`, `who`), `from` (`run`, annotation id). No dedupe, no resolution; it never touches `refs.bib`, `refs/` or the manifest.

Why this is enough, settled with the author on 2026-09-18: `loom:unresolved-work` fires on a citekey that *is* in `refs.bib` and states no identifier. An agent suggesting a paper that is not in `refs.bib` at all produces no such diagnostic, so there is nothing to nag and no second source of identity truth. The breadcrumb waits until the author adds the entry, and lint's behaviour is unchanged. Where a *confirmed* identity lives stays deferred with `refs/`'s overhaul.

The author's framing: an escape hatch to move on without being annoyed, with a breadcrumb trail to follow when they are no longer lazy.

The agent's suggestion is an annotation of kind `citation`. Accepting is `loom refs note --from RUN --accept ID [--reason TEXT]`, which appends and resolves; rejecting is `--reject ID [--reason TEXT]`, which resolves and appends nothing, the reason riding on the resolve event. Both are CLI-only here; they become buttons in 0.11, where the write API lands.

**`loom refs note` is denied to the agent**, and so is `reference-notes.jsonl`, which sits at the quilt root and matches none of the existing `Edit(/*.tex)` patterns — so denying the command alone would leave the file writable. Since the deny list is a deny list, a new write command is agent-accessible the day it ships; `settings_deny_paths()` already exists for tests and doctor, so this plan adds **the test that every loom command writing outside `ai/runs/` appears there**.

The overhaul's migration is mechanical: entries with identifiers become candidate records with provenance `asserted`, keys become `cited_by`, and the file becomes a view.

## Part G — Arras

### The verbatim toggle

Per node and per payload, in the box's upper right, revealed on hover and focus with a preference to always show; flips the body between rendered and source; paired with **copy** and **copy for chat** (the key in the author's tag syntax plus the text). Source comes from `build/source/<key>.tex` fetched lazily — the manifest is already 772 KB on relloc and would nearly double with source inline. `lib/paths.ts` has `dataUrl()` for build-directory files but there is **no source-fetch path and no `build/source/` in the interface**, so both the publisher's output and `specs/manifest.md` gain it. Needs no write API.

### One repair the log forces

**`Annotation.record` collapses.** It is a file path (`types.ts:189`), and `routes/review/+page.svelte:71` builds the "runs and comment sessions" list by `[...new Set(…map(a => a.record))]`. With one log that yields a single element and the list at `:177-180` stops distinguishing anything. **The grouping key becomes `run`** — a manifest field change, not additive, and the one place `interface_version` was worth re-examining. It stays 1: a viewer that reads `record` as an opaque grouping key is unaffected by what the string means.

Everything else here is additive but invisible until something renders it, and three things are worth writing down rather than discovering:

- **`placement` collides.** `CommentPlacement.where` in `lib/fragments/mount.ts` already means gutter / inline / count — a *viewer layout* decision — while the annotation's new `placement` is `replace` / `after` / `before`, a *content* hint. Two different things with one name in adjacent code; rename the viewer's to `slot`.
- **Kind is an open string used as a CSS class** (`mount.ts:87`, `:139`, `AnnotationBox.svelte:11` and the styles at `:46-62`), and `AnnotationPanel.svelte:23` is a literal four-option `<select>`. A `citation` kind renders unstyled and is unfilterable until both are extended.
- **`Reviews.open` is kind-keyed** (`types.ts:112`, `manifest.md:149`), so severity has no channel. Whether the manifest carries severity counts beside kind counts is a 0.11 question — review mode's grouping lives in the report pane — but the field's shape should be decided here, before two plans depend on it.

Payloads rendered inline in red beneath their anchor are 0.11.

## Risks

- **The mode assets are the book and the fixtures.** Appendix C and D reproduce them verbatim and `gen_quilts.py` regenerates both quilts from them, so a one-word change in `blocks.md` fails two tests in three places. Edit each asset once, and regenerate before running anything.
- **The log changes what "a record" means in four modules and five diagnostics.** The globs are duplicated; missing one leaves a command reading files that are no longer written, silently returning nothing.
- **Part B is the only part with no existing machinery.** Everything else is a move or a rename; the last-seen cache is new, and its failure mode is quiet — an annotation that should have been frozen simply is not, and nobody notices until a text is wanted and gone.
- **`apply_unified_diff` has no fuzz.** Hunk line numbers are taken literally, so `compile --with` inherits exactly the brittleness `bundle --with` had. Not this plan's to fix, but review mode will generate more diffs than anything before it.
- **Severity is the manifest's second use of the word** (diagnostics already have one), and `placement` is arras's second. Both collisions are in adjacent code and both should be named apart before they ship.
