# 0.24 — The library in the viewer

## Context

The library is driven from a terminal today. Works enter only by being cited: `loom library update` gathers the bibliography from the documents' `.bib` files into loom's own `.loom/digests/bibliography.bib`, looks identifiers up (zbMATH Open, Crossref), fetches (arXiv), extracts the digest and maps pages. `loom library add` files a PDF only under an entry that exists. The viewer's work page (Info) shows a title, the overview when an agent wrote one, BibTeX, provenance lines and results as bare ids; Review › Library is the proposal queue and a ledger table with filters; nothing in the viewer can add a work, fetch it or digest it.

The author asked (2026-11-02) for: adding works from the viewer by pasting an identifier or dropping a PDF, with each identifier type recognised and a bad one shown as unresolved; running the digest from Info; the extracted results laid out well on Info; a more useful Review › Library with actions; and an AI summary that agents write lazily. A clickable mockup was reviewed and approved with one change (no status dots in the column).

**The author's decisions (2026-11-02):**
- **A work added by hand goes into loom's bibliography,** `.loom/digests/bibliography.bib`, marked `loom-added` (who, when), as loom already marks the entries it makes itself (`loom-parsed`). It is loom-managed, never a document's `.bib`: there may be several, and writing into them surprises. To cite one, the person copies its BibTeX from Info.
- **Adding fetches and digests it at once,** by default: the dialog's "Fetch and digest it now" starts ticked.
- **"Ask an agent" writes a note on the whole work** in the selected session, which an agent picks up like any other. Annotations on a cited work no longer need a page.
- **ISBNs and MathSciNet ids are recognised and not looked up:** the dialog says what it is and asks for a DOI, an arXiv id or the BibTeX entry.
- **The column's Library lists works by title alone**; what each holds is said on its Info (a status line) and in Review. The shelf's "ledger" link becomes "Manage in Review".
- **"Update all" is "Fetch and digest everything".**

**What stays:** loom calls no model (P9), so an overview is always an agent's `loom write`. Verifying is the person's claim about one result, so there is no bulk verify. The network is used only with `[library] online`, or for one run the person allows in the viewer; an agent can never grant it.

## How this plan is carried out

One master document, this one, as 0.22 is. Each phase starts in plan mode: the code is explored, the concrete changes are proposed, and the author approves them. When a phase is built and `scripts/verify full` passes, what was built is appended to its **Implementation** section. Arras is re-vendored into loom with each phase; a phase that changes the manifest regenerates the fixtures (`docs/specs/tools/refresh-fixture.sh`).

## 0.24.1 · Library runs from the viewer

The foundation the others use: a library update the person starts in the viewer, which runs in loom and reports its progress.

- **A job runner in `loom serve`** (new `loom/jobs.py`). A library update can take minutes (a compile has a 600 s timeout), and every write today runs inside the request under `publication_lock`.
  - One worker thread and a queue, so two library runs never overlap.
  - A job runs `refs.build.build_refs(result, only=…, steps=…, refresh=…, progress=…)` on a fresh scan, outside the lock, then calls `ServeSession.rebuild()`.
  - Its `progress` callback, the `(stage, item, n, total)` that `build_refs` already speaks, records each step's state in the job.
  - The job's summary is taken from the `BuildReport`: what was looked up, fetched, extracted and mapped, and each lookup error and refusal.
  - Jobs live in memory, and a restart forgets them.
- **`POST /_api/library-update {works?, steps?, redo?, online?}`** answers `{job}` at once.
  - It is the author's act, refused to a declared agent.
  - `online: true` is the viewer's `--online`: the person allows the network for this run.
  - `NO_REBUILD`, since the job rebuilds when it finishes.
- **`GET /_api/jobs`** answers the recent jobs. It is checked against the origin like `GET /_api/here`.
- **The viewer:**
  - `lib/jobs.svelte.ts` polls `/_api/jobs` each second only while a job runs.
  - `WorkStatus.svelte` is the Info status line: Paper (filed or not, with "Get it"), Source (from arXiv, or none), Digest (n results, n verified, with "Digest" or "Update"), Overview. Each missing part becomes its action.
  - `JobProgress.svelte` shows the four steps ticking, under the status line and in Review.
  - Review › Library's header gains "Fetch and digest everything".
  - When a step needs the network and `[library] online` is off, the action asks "Allow the network for this run".
- **Specs:** `write-api.md` gets the endpoint, `/_api/jobs` and a job's shape.

## 0.24.2 · Adding works

- **Recognising** (`refs/identity.py`, a new `recognise(text)`). Every form below is told apart before anything is looked up:
  - a BibTeX entry, read with the existing parser (`scan/bib.py`);
  - a DOI, bare, `doi:` or a doi.org link;
  - an arXiv id, new or old style, with `arXiv:` or an abs or pdf link;
  - a zbMATH number or link, an MR number, an ISBN-10 or ISBN-13 with its checksum;
  - anything else is "not recognised".

  The comparisons that cut an arXiv id at `v` (`ingest.py`) mangle old-style ids whose category holds a "v", so they are fixed.
- **Looking up one identifier** (new `refs/lookup.py`, on `Resolver`'s HTTP client, cache, contact and spacing):
  - a DOI goes to Crossref's `works/DOI`, and a miss says the DOI did not resolve;
  - an arXiv id goes to the arXiv API;
  - a zbMATH number goes to zbMATH Open;
  - ISBNs and MR numbers say they cannot be looked up and ask for more.

  A miss and a network error are told apart. Each answer says:
  - the entry it found;
  - the key it would take, made by the existing `_free_key`;
  - whether a document can be fetched;
  - whether loom can digest it (from source), or an agent must propose from pages;
  - any work already in the library with the same identifier or title, perhaps another version.
- **Adding:**
  - `refs/scan.py`'s `append_entries` writes the entry to `bibliography.bib` with `loom-added = {who, when}`.
  - The manifest's reference carries `added`.
  - A work added by hand can be removed while nothing depends on it.
- **Uploading a PDF:**
  - The body stays JSON, with the file in base64, so the CSRF rule that a write is `application/json` stands; a size cap answers 413.
  - The upload is kept under `.loom/build/uploads/`.
  - It is identified by `identify_document` and filed by `plan_filing` and `file_document`, as `loom library add` files.
  - A PDF that matches no work is offered a new entry from its own first pages (`_own_account`, `_entry_for`, as gather adopts stored orphans).
- **Endpoints:**
  - `library-recognise` and `library-lookup` are reads;
  - `library-add`, `library-upload` and `library-file`, and `library-remove` for works added by hand, are the author's acts.
- **The viewer:** `AddWork.svelte`, the dialog of the mockup, opened from the "+" on the column's Library band and from Review.
  - The kind label shows as you type.
  - A BibTeX entry is read at once; an identifier is looked up on "Look up".
  - A notice offers "Allow this once" when the network is off.
  - The answer is a found, unresolved or cannot-look-up card.
  - A drop zone and file chooser take a PDF.
  - "Fetch and digest it now" starts ticked.
  - Adding opens the work's Info, where its run shows.

## 0.24.3 · Info: results, the overview, and asking an agent

- **Info in the mockup's order:**
  - title and byline, with "added by hand, not cited yet" where that holds;
  - the status line and any run;
  - the overview, or its empty state;
  - Results;
  - "Cited in your documents";
  - the bibliography entry folded at the foot, with "copy BibTeX";
  - the provenance lines (digest source and method, versions) in a "Details" fold.
- **Results as cards** (`ResultCard.svelte`). Each result's own fragment (`m.nodes[id].fragment`) is rendered with `Fragment … standalone`, as `ProposalCard.svelte` does. Each card has:
  - the number and name parsed from its `locator`, as `ProposalCard` already does;
  - a state badge (extracted, proposed, verified);
  - a page link (`Locator`), and a link to its source;
  - which of the person's results use it.

  The cards are grouped by the paper's sections, with filters for all, used here, verified and proposed; past a dozen, the rest fold.
- **"Cited in your documents"** comes from `cited_by`, through each citing node to its document.
- **The column:** the "filed" dot goes, and "ledger" becomes "Manage in Review".
- **Annotations on a whole work:**
  - `loom annotate CK` with no `--page` targets the work, and the API's `annotate` accepts it;
  - Info lists a work's annotations;
  - "Ask an agent" writes one, "Read this paper and write its overview", in the selected session.
- **The lazy overview:**
  - With no overview, `loom library read WORK`, and its MCP resource, add that an agent who reads the work through writes one (`loom write CK -`).
  - `rules.md`, the ingest mode and the orientation say the same.
  - `loom library WORK` reports "overview: none".

## 0.24.4 · Review › Library acts

- **Header:**
  - "+ Add a work" and "Fetch and digest everything";
  - a search box over title, author and key;
  - filters: all, needs you, no paper, no overview, not cited, beside today's proposed and verified.
- **Columns:**
  - Work, with its key, authors and "added by hand";
  - Paper;
  - Digest, its count and whether it came from the source or the pages;
  - Verified, with "n to verify" linking to the queue;
  - Overview;
  - Cited, the number of places.

  Each column explains itself on hover.
- **Each row's ⋯ menu:**
  - open its info;
  - digest it, or digest it again;
  - fetch the paper, or upload a PDF;
  - ask an agent for an overview;
  - copy BibTeX;
  - mark it unreadable;
  - stop asking for its paper (`loom library ignore`);
  - remove it, for a work added by hand.

  An action with no endpoint yet gets one wrapping its CLI function, as `library-verify` wraps `verify_result`.
- **Problems in their row, each with its fix:** a lookup that failed in the last run, a version mismatch, and `loom:no-readable-copy`.
- **Selecting rows** offers "Digest selected", "Fetch papers" and "Ask an agent for overviews".
- **Citation suggestions** are accepted or rejected in place (`library-cite`). The proposal queue stays at the top.

## Documents, each phase

- **Specs:** `write-api.md` (the endpoints and jobs), `manifest.md` (`references[].added`, annotations on a work).
- **Design:**

## Out of scope

- bulk verify;
- loom calling a model;
- editing an entry's fields in the viewer;
- ISBN and MathSciNet lookups;
- an agent starting a library run that uses the network.

## Implementation

### 0.24.1 · Library runs from the viewer — built 2026-11-03

**What was built:**
- `loom/refs/update.py`: `update()` is one library run, gather included when no work is named, which `loom library update` and a run started in the viewer both call. The command keeps its agent refusal of `--online`, its dry run and its progress on stderr.
- `loom/jobs.py`: a `Job` per run and a `Jobs` runner with one worker thread and a queue, owned by `ServeSession`.
  - A run calls `update()` on the quilt as it is, outside the publication lock, then rebuilds.
  - Each step is followed through `build_refs`' progress callback: `waiting`, `running`, `done`, or `skipped`.
  - The job carries the run's report as `loom library update` prints it.
- The write API:
  - `library-update {works?, redo?, online?}` answers with the job at once. It is the author's, `no-such-work` for a work that names nothing, and `no-runner` outside `loom serve`.
  - `GET /_api/jobs` needs the origin and the token.
  - `library-verify` and `library-discard` answer `library-busy` while a run acts on their work.
- The viewer:
  - **Info's status line** (`WorkStatus`): Paper, Source, Digest, Overview, with "Get it", "Digest" or "Update" where the publisher runs them.
  - **A run's progress** (`JobProgress`): each step ticking, then the verdict, with what the run said folded beneath.
  - **"Fetch and digest everything"** in Review › Library's header.
  - **The network question** (`NetworkAsk`), "Allow and run" or "Run offline", where the quilt has the network off and the run could use it. It stands under the status line on Info.
  - `jobs.svelte.ts` polls `/_api/jobs` only while a run is live. `write.ts` gained a token-carrying `read`.
  - Re-vendored.
- **Documents:**
  - `write-api.md` gives the endpoint, a job's shape, `/_api/jobs`, `library-busy` and `no-runner`;
  - `model.md` and `agents.md` describe runs from the viewer;
  - `invariants.md` gains "The network is the person's to allow", which had no entry of its own.

**Departures:**
- **A step that acted on nothing is `skipped`, not `done`.** Offline, look-up and fetch report no progress at all, and calling them done would claim they ran.
- **`library-cite` is not refused during a run.** It writes the reference notes and the annotation log, never a digest, so it cannot cross a run.
- **The network question moved.** It stood inside the part whose action asked it, which stretched that part across the line; it now stands under the whole status line.
- **There is no "steps" field.** A run on one work takes the four work steps, and "Get it" and "Digest" start the same run, which does nothing that is done.

**Checked by hand** on a copy of relloc, its network turned off in the copy:
- **`brion_EquivariantChowGroups1997`** (a DOI, no paper): "Get it" asked about the network. Allowed, it ran each step to the verdict "0 of 1 work digested … 1 blocked", with "blocked: no arXiv id to fetch a source on" under "What the run said".
- **`kresch_CycleGroupsArtin1999`** (a PDF, no source): "Digest" asked under the line, and ran offline, look-up and fetch skipped.
- **A verify during a run:** a re-extract of `manolache_VirtualPullbacks2012` made `library-verify` on one of its results answer `library-busy`, and the verify went through once the run finished.
- **"Fetch and digest everything",** with the network allowed once, gathered, looked up 3, fetched 6 and extracted 6, leaving 25 of 36 works digested and the 11 blocked each with its reason.

**Verification:** `scripts/verify full` passed but for two steps, each fixed and rerun:
- one import order (ruff);
- the tracked-files test, which caught a preview config left in `.claude/` and new files not yet added; it passed once they were added with `--intent-to-add`.

The suites: loom 2,156 unit and 16 TeX tests; arras 217 vitest, 334 e2e, 15 minimal, 42 write, 24 reading, 6 shots and 1 floor; the docs checks. The write suite's patch test passed in the full run, after the watcher fix merged as `8bd28d7b`.

### 0.24.2 · Adding works — built 2026-11-03

**What was built:**
- **Recognising:** `refs/identity.py`'s `recognise` tells apart, with no network:
  - a BibTeX entry;
  - a DOI, bare, `doi:` or a doi.org link; arXiv's own 10.48550 DOIs read as arXiv ids;
  - an arXiv id, new or old style, bare, prefixed or a link;
  - a zbMATH number or link, an MR number, an ISBN-10 or ISBN-13 by its checksum;
  - anything else.

  `arxiv_base` cuts only a trailing `vN`, where `refs/ingest.py` had cut at the first "v".
- **Looking up:** `refs/lookup.py`'s `look_up`:
  - a DOI is asked of doi.org by content negotiation, so a 404 means it does not resolve;
  - an arXiv id goes to the arXiv API, a zbMATH number to zbMATH Open;
  - a BibTeX entry is found from its own fields;
  - an ISBN or MR number asks for more.

  It answers found, missing, unreachable, offline or cannot, with the entry, a unique key (surname and year, `Gro19`), whether loom can digest from source, and the works it may duplicate.
- **Adding and removing:** `refs/added.py` writes a work into loom's bibliography with `loom-added = {when, who}`, keeping a pasted entry's fields and type; the manifest's reference carries `added`. A work added by hand that nothing cites is removed, and a document stored for it set aside.
- **Filing:** `refs/add.py` identifies a dropped PDF and files it under its work with the pieces `loom library add` uses. One that matches nothing is offered an entry from its own account; a reference manager's `Author - Year - Title.pdf` gives the author as well as the title.
- **The write API:** `library-recognise` and `library-lookup` (reads), and `library-add`, `library-upload`, `library-file` and `library-remove`, the author's. `fetch` queues a 0.24.1 run on the new work. A body over 96 MB answers 413 before it is read.
- **The viewer:** `AddWork.svelte`, opened from a "+" on the column's Library band (shown even for an empty library) and "+ Add a work" in Review › Library's header.
  - the kind of what is pasted, as you type;
  - an entry read at once, an identifier looked up on "Look up";
  - the network question, worded for a lookup or a run;
  - found, missing and unreachable cards, with duplicates linked;
  - a drop zone and file chooser for PDFs;
  - "Fetch and digest it now", ticked;
  - after adding, the work's Info, where its run shows.

  Info's byline says "added by hand". `NetworkAsk` takes its wording from the act that asks.
- **Documents:** specs (`write-api.md`, `manifest.md`) and design (`model.md`'s library and its Open note, `agents.md`).

**Departures:**
- **`loom library add` keeps its own loop.** The endpoint files through `refs/add.py`'s `identify` and `file_under`, built on the same pieces (`identify_document`, `plan_filing`, `file_document`), rather than through a function the command was moved into; the command's reporting is unchanged.
- **An entry is written by `entry_text`, not `_bibtex`.** `_bibtex` drops every field it does not list, and a pasted entry's volume or pages must survive.
- **Lookups are not cached.** A person looks a work up once.
- **Uploads are kept as `.loom/build/uploads/<sha256>/<name>.pdf`,** under their own name, since a reference manager writes the title and author into it.
- **After adding, Info opens with `?view=info`.** A work with a PDF would otherwise open on its paper, away from its run.

**Checked by hand** on a copy of relloc, its network off in the copy:
- **`arXiv:1909.07649`:** recognised as arXiv. "Look up" asked for the network; allowed, it found "Intrinsic Mirror Symmetry" (Gross, Siebert, 2019) as `Gro19`, digestible from its source. Added with "Fetch and digest it now", Info opened on the run, which fetched the paper and source, extracted 164 results and mapped them; the byline said "added by hand".
- **`10.9999/not.a.real.doi`:** "This DOI did not resolve: doi.org has no record of 10.9999/not.a.real.doi", and Add stayed disabled.
- **An ISBN:** recognised, and asked for a DOI, an arXiv id or the entry.
- **A BibTeX entry for Fulton's *Intersection theory*:** read at once as `Ful98`, with no network.
- **`Gro19`'s own PDF, dropped:** matched `Gro19`, "File it there" opened its Info, and the store already held that document.
- **A PDF named `Vale - 2018 - Widget categories and their duals.pdf`, matching no work:** offered `Val18` from its name and filed under it.
- **Removing:** `Ful98` and `Val18` were removed, the latter's stored paper set aside; a gathered work was refused with `not-added`.

**Verification:** `scripts/verify full` passed on its first run: loom 2,203 unit and 16 TeX tests; arras 217 vitest, 335 e2e, 15 minimal, 45 write, 24 reading, 6 shots and 1 floor; the docs checks.
