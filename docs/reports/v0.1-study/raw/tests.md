Auditor: tests. Checkout `v0.1-study` at 71621877 (equal to main), 2026-11-13. Method: read `scripts/verify`, the three workflows, the conftests, the Playwright configs and every test file's header; collected loom's tests with `pytest --collect-only` per marker; pulled the last 200 CI runs and the jobs of the last 30 per workflow (2026-11-04 to 2026-11-13) with `gh`; read the failed logs; sampled one file (304 items of `test_output.py`) for speed at load average 9 on 8 cores. Nothing else was run. A prior audit exists (`docs/reports/test-audit.md`, 2026-09-23); much of it is stale (the minimal, perf and editor-client suites it covers are gone), and nothing below relies on it.

## 2. Cost

What each lane runs (`scripts/verify:53-115`):

| lane | steps | CI job | CI verify step, median / worst (30 runs, Nov 4-13) |
|---|---|---|---|
| `fast` | loom ruff, format, mypy, pytest unit (xdist `-n auto`); arras svelte-check, vitest; docs: work queue, principles, fixtures, bundle, hard wrap | loom `unit` x3 Pythons; docs | loom 113 s / 150 s (job 135 s / 230 s); docs 2 s / 5 s |
| `full` | fast + pytest tex; arras build, then e2e, write, reading and shots concurrently | arras `verify` (`full --only arras`); loom `tex` (`--steps "pytest tex"`) | arras 291 s / 404 s (job 335 s / 717 s); tex 28 s / 78 s (job 74 s / 118 s) |
| `--only loom/arras/docs` | one lane | as above | |
| `paper`, `client` | by hand only | never | not measured |

Inside the arras step (CI tables from the failed-run logs): svelte-check 9-13 s, vitest 5-8 s, build 6-9 s, then concurrently e2e 205-310 s (383 tests, the critical path), write 120-230 s (76 tests, a `loom serve` per test), reading 97-202 s (49 tests), shots 45-68 s. Outside it, apt steps occasionally cost 90-390 s (Chromium libraries, poppler). The arras job triggers on every `loom/**` change too (`.github/workflows/arras.yml:7`), so a Python-only commit pays about 5.5 minutes of browser tests.

Failure rate over the last 30 runs: arras 9/30 (30%), loom 10/30 (33%; 9 in `tex`, 1 in `unit`), docs 0/30. Every run was attempt 1, so no failure was cleared by a rerun of the same commit. Five of them were on main (72a89691, ec739962, 6a29feea, c481ac18, 226a242c), i.e. main was pushed red five times in nine days. The causes (from the logs and the fixing commits):

- `tests/e2e-write/section-drafts.e2e.ts:33` failed at all three widths in four consecutive runs (6a29feea, c481ac18 and two on `ci-linux-tex`): a real break that local runs did not show.
- 7946d1a6, "Two tests from plan 0.30 pass on any machine, not only this one": `test_refs_layer.py` read a paper source kept out of git by the showcase's `.loom/.gitignore`, so it passed locally and returned `None` in CI; `annotations.e2e.ts:703` assumed macOS line breaks, and Linux fonts put two annotations on one line.
- 226a242c: the same refs test failed on Python 3.11 and 3.13 and passed on 3.12, so its outcome also depended on test order (the shared `Once` templates under `--dist loadgroup`).
- the nine `tex` failures were the move to TeX Live 2026 (`texlive/texlive:latest-medium` floats).
- single-test failures in `reading.e2e.ts:442`, `:542`, `marks.e2e.ts:83`, `:142`, `here.e2e.ts:32`, `write.e2e.ts:579` look like layout or timing on Linux; none was rerun, so flake versus regression cannot be told from CI.

Locally, plan records show the same pattern before 2026-11-05: "passed but for three suites, each then rerun and passing" (`docs/plans/0.22-open-quilt.md:498`, `:583`, `:623`, `:651`; `docs/plans/0.23-settings.md:183`). Growth since mid-October: loom unit 2,060 to 2,546, write 31 to 76, e2e 316 to 383.

Sampled speed: 304 items of `test_output.py` took 47 s in one process (0.15 s each, more system than user time: each item copies the demo quilt). At that rate the file's 767 items cost about 115 s serial, roughly a quarter of the unit tier's ~450 worker-seconds in CI.

## 6. Gaps for v0.1

There is no tier that runs a realistic sequence of writes against a realistic quilt and checks the person's files afterwards. What exists:

- `test_fixtures.py:173` runs a fixed list of read and record commands (lint, search, doctor, history, stamp, revert, fork, new, linearize, live, restore to a new file: `test_fixtures.py:183-213`) and checks author files are unchanged. It never calls a write-API capability, `suggest`/keep, `sync`, `adopt` or a tick, yet `docs/contributing.md:40` says it "runs every command on every fixture quilt".
- `test_write_api.py:1438` gives each of the 48 endpoints one success and one refusal, each on a fresh quilt.
- The write suite checks one Keep or Discard at a time (`e2e-write/changes.e2e.ts:89`, `:100`).
- `gen_quilts.py` plays a scripted story, but the only keep in it is `changes --keep-all` (`gen_quilts.py:492`), and its check is byte equality with a golden copy, not an invariant on the person's text.

Both recent damage bugs fell in that gap and were found in the author's own quilt: 1ac44c5e (a kept suggestion that opens a section read as untaken, so each press pasted it again, seven times) and 2e106a45 (after the author edited inside the pasted body, Keep wrote it once more). Each fix added unit reproductions in `records/test_edits.py` (`:362`, `:381`, `:412`, `:441`), which pin those two shapes but not the class.

The cheapest net is one in-process test, in the unit tier, about 20 s. Drive `loom.render.api.handle(root, endpoint, body)` (`loom/src/loom/render/api.py:694`, already used by `history/test_acts.py:50`) on a copy of the showcase and the synthetic quilt through a seeded random sequence of about 30 steps: an agent suggests (replace, before, after, whole body, a long insertion that opens a section), the person edits a file by hand, Keep, Discard, Keep all, Undo (history restore), tick a task, save settings. After every step assert four invariants: only the files the step names changed; repeating the same request changes nothing (this alone catches the seven-fold paste on the second press); Undo restores the bytes exactly; and no paragraph of 20 or more words occurs more often than before unless the step inserted it. Run 10 seeds. No new dependency is needed. Extend `test_fixtures.py:173` with the write capabilities that should leave author files alone, and correct `docs/contributing.md:40` to what it covers.

Other gaps: no macOS job anywhere, though the users are on Macs (`.github/workflows/loom.yml` runs `ubuntu-latest` only); the client tier exercises Claude Code (`client/test_claude.py`, 6), not Claude Desktop, whose entry is only checked as printed (`unit/test_clients.py:108-119`), and Codex has one smoke test.

## 7. Parallel sessions

What assumes exclusive use:

- The working tree. `test_tracked.py:46` fails on any untracked file under `loom/src`, `loom/tests/quilts` or `arras/src`, so one session's new file fails another session's unit run, and every agent's own new file fails until `git add`. `test_quilts_match_generator.py:24`, `test_cli_reference.py:11`, `test_mcp_tools.py:48`, `scripts/checks/fixtures.py` and `bundle.py` compare generated output with whatever is on disk, so another session's half-finished regeneration fails yours. `scripts/checks/hardwrap.py` judges every line added since HEAD in the shared tree, including other sessions' edits.
- The served template. `arras/tests/served-setup.ts:21` copies the quilt from `git ls-files` plus the working tree; an untracked file in a fixture quilt made `e2e-write/meta.e2e.ts` count one change too many (recorded 2026-11-05).
- The installed loom. The write and reading suites run `../loom/.venv/bin/loom` (`arras/tests/served.ts:20`), so a `uv sync` or a branch switch by another session in the same checkout changes the program under test mid-run; a worktree without its own venv cannot run them at all.
- Ports. Handled: `scripts/verify:187` claims the first free slot (claim port 4175 + 100 n, suites at 4173 and 4174 + 100 n, `arras/tests/sites.ts:27`); the served suites take port 0 with retries. Not handled: two suites started by hand both take slot 0 (`docs/contributing.md:44`).
- CPU. `pytest -n auto` takes every core; `share_cores` (`scripts/verify:132`) splits cores only among the steps of one verify run; the write and reading configs fix 4 workers each (`playwright.write.config.ts:17`, `playwright.reading.config.ts:15`). Two sessions' `fast` runs put 16 pytest workers on 8 cores; two `full` runs put about 8 pytest workers and 10 browser workers there, and every write or reading test also starts its own `loom serve`. The generous waits (`patient` 300 s per test and 120 s per expectation, `sites.ts:24`; `PATIENCE` 180 s, `loom/tests/helpers.py:23`) prevent false failures but make a real failure cost two minutes, up to `maxFailures: 10`.
- Path length. `test_output.py:111` allows 100 columns on stdout and doctor prints each tool directory on one line (`loom/src/loom/doctor.py:185-191`), so a long worktree path can fail `doctor[0]` (recorded 2026-11-05 for paths over 96 characters; this checkout's is 82).
- Shared caches: `.pytest_cache` and `__pycache__` in the checkout (harmless); biber's unpack cache is already per worker (`loom/tests/conftest.py:96`).

## Findings

**TEST-1. No sequence-level safety test.** Evidence: section 6; 1ac44c5e and 2e106a45 were found by the author in his quilt; the nearest tests are single-step. Weight: blocks (the v0.1 promise is that loom never damages a person's source). Effort: a day. Rec: fix, with the seeded in-process sequence test of section 6.

**TEST-2. The invariance test does not cover writes.** Evidence: `loom/tests/unit/test_fixtures.py:183-213` against `docs/contributing.md:40`. Weight: hurts (a reader trusts a guarantee that does not exist). Effort: hours. Rec: fix (add the write capabilities that must leave author files alone; correct the sentence).

**TEST-3. `test_output.py` dominates the unit tier.** Evidence: 767 items of 2,546 (`test_output.py:84`, `:119`); 395 cases over 75 commands, 372 run twice (text and `--json`); 0.15 s per item measured, ~115 s serial, ~25% of the tier; the width, verdict and no-hash rules (`test_output.py:96-115`) govern text no person types. Weight: hurts (time, and every wording or layout change fails it). Effort: hours. Rec: fix, by running each case once with `--json` and asserting exit code, envelope and `unchanged`; keep one text run per command; drop the 100-column and no-hash rules. Saves about 60-70 s serial, 15-20 s wall per unit run, and its share of agent turns spent on line widths.

**TEST-4. CI is after the fact, and its failures are environmental.** Evidence: section 2; main red on 72a89691, ec739962, 6a29feea, c481ac18, 226a242c; 7946d1a6 fixed two tests that passed only on macOS or only with gitignored files present. Weight: hurts. Effort: hours. Rec: fix: push to a branch and merge only on green; make tests independent of gitignored state (file the source in the test, as 7946d1a6 did); replace line-position assertions with structural ones where fonts decide the outcome.

**TEST-5. Copies of fixtures and quilts.** Evidence: `docs/specs/fixture`, `loom/tests/fixture`, `arras/tests/fixture` (198 files each); `loom/tests/fixture` is read by one test (`loom/tests/tex/test_fixture_vendored.py:15`); `demos/{demo,synthetic,showcase}` copy `loom/tests/quilts`; `loom/src/loom/assets/demo` is a third demo; `scripts/checks/fixtures.py` exists to keep them equal. Weight: hurts (two extra regeneration steps per output change, 34k lines of churn in a month). Effort: hours. Rec: remove: point loom's test and arras's `stage-fixture.mjs` and specs at `docs/specs/fixture`; make `demos/` links or drop them; then delete `fixtures.py`.

**TEST-6. Vendoring by hand.** Evidence: 33 "vendor" commits of 220, 29 touching nothing else, 74 touching the bundle; 44 MiB of the pack; hashed chunk names conflict across branches; `doctor.py:41` tells the user how to vendor. Weight: hurts. Effort: a day. Rec: fix: build and commit the bundle in a CI job on main (or attach it to a release wheel), and have a checkout's `loom serve` find `arras/build` when present; keep `scripts/checks/bundle.py` for that job only.

**TEST-7. No single regenerate command.** Evidence: section 4; seven independent scripts, three needing TeX; bd07ce44 assembled by hand. Weight: hurts (agents learn the order from failures). Effort: hours. Rec: fix: one `scripts/regen` that runs what applies, in order, and prints what changed.

**TEST-8. Exact sentences are pinned everywhere.** Evidence: 1,084 loom assert lines with a literal of 25+ characters, 369 `match=` phrases; 506 literal text expects in arras. Weight: hurts (the v0.1 work on "what does this control do" is mostly rewording). Effort: days, done as files are touched. Rec: fix: refusals asserted by error code (the write API already has codes, e.g. `test_write_api.py:1431`), UI by test id and state; keep literal text only where the words are the behaviour.

**TEST-9. Layout and feature tests for what v0.1 will hide.** Evidence: section 5; 124 bounding-box and 68 computed-style assertions; `workspace.e2e.ts` 42, `panel.e2e.ts` 21. Weight: hurts (each subtraction becomes a test-repair session). Effort: days, mostly deletion. Rec: remove with each hidden feature; for the kept shell, rewrite a few tests after the redesign instead of porting the old ones.

**TEST-10. Three levels and a mocked API.** Evidence: section 5; 66 `page.route` mocks in `arras/tests/e2e`. Weight: hurts (a mock can pass while the real API changed; the real paths are already covered by the write suite). Effort: a day. ## An everyday lane under three minutes

Run in a session's own worktree with its own venv:

- loom: ruff, format check, mypy (10 s); pytest unit with `test_output.py` merged and `test_tracked`, `test_cli_reference`, `test_quilts_match_generator` moved out, plus the new sequence safety test; xdist capped at half the cores. Estimate 60-90 s on this machine unloaded (CI does today's larger tier in 113 s on four cores).
- arras: svelte-check (10 s) and vitest (7 s).
- the write suite's core: keep, discard, keep all, undo and annotate against the real `loom serve`, about ten tests on one build (8 s), about 40 s at four workers.
- hard wrap (1 s).

Lanes run in parallel, so the wall time is about 2 to 2.5 minutes, and every step either guards a person's files or fails only on what the change did.
