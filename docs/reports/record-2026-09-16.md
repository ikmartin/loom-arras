### After review: five display faults on the real papers

The author read their own papers in the viewer and found five things wrong. Four had one cause each and one had none of its own.

**A diagram inside a numbered display reached the mathematics renderer.** The rule that sends a diagram to the LaTeX fallback fired only for a bare `\begin{tikzcd}`. Written inside `\begin{equation}` — the ordinary way to number a diagram — it arrived at the renderer as `\[\tag{2}\begin{tikzcd}…\]` and the whole block was set in error colour. Three such blocks in the relative localization quilt, sixteen in the ACGS import, all of the latter `\xymatrix`. A display block is now decided by an allowlist of what a renderer handles, so anything else is compiled by LaTeX, and the document's equation number travels on the figure (DR-100).

**The `\tag{2}` in those blocks was loom's own equation numbering**, not the author's `% !LOOM tags:`. They share a word and nothing else: `\tag` is the LaTeX command that prints an equation's number, added so the renderer shows the number the document gave it, while `tags:` is a directive carrying thematic labels that never reach the page. Nothing needed changing; the collision of names is worth knowing.

**An author's own macros reached the page as error text.** `\sHom` is defined as `\scalebox{1.2}{\ensuremath{\mathpzc{Hom}}}` and a renderer implements none of the three. Alphabets declared with `\DeclareMathAlphabet` are now published as the nearest alphabet the renderer has, and the commands it lacks as definitions that keep the content and give up only the presentation (DR-101).

**A paragraph of prose was set as a formula.** `\red{…}` is `\textcolor{Mahogany}{#1}`, plainly text, but the heuristic that decides whether an expanded macro is mathematics looked at the expansion rather than the definition — and the sentence contained a citekey with an underscore. It now looks at the macro's body (DR-102). The colour itself was being read and discarded, so the same sentence would have come out black; `\textcolor` now keeps it (DR-103).

**The display blocks that scrolled without seeming to need to** were scrolling vertically, not sideways, which is why the first measurement — of horizontal overflow — found nothing. The author's screenshot settled it. Naming one axis of `overflow` makes a browser compute the other to `auto`, so the block became a scroll container for everything inside it, and two invisible things were then counted as content: the renderer's per-expression glyph cache, a `<defs>` block whose paths sit some four thousand pixels above the formula in the SVG's coordinate space, and the hidden MathML copy it emits for screen readers, which is as tall as the formula is in its own units. Ten of the eighty-eight display blocks in the paper had a bar, at every type size and every line width, with nothing to scroll to. A display block now scrolls sideways only, the glyph cache is kept once for the page rather than once per expression, and the edge with content past it carries a shadow so a reader is never left wondering why a block moves (DR-104).

### After review: version control is the author's

The author asked why `loom init` ran `git init` at all, given that loom uses version control for nothing. Reading the code settled it: loom never stages, commits, branches, tags or reads history; the whole relationship is an ignore file, a `doctor` check, and a ledger format designed so that concurrent acceptances of different keys merge cleanly. The snapshots under `.loom/` exist because loom cannot assume the quilt is versioned.

So `git init` was the one place the tool reached outside its own files, it was on by default, and it was silent. It is now opt-in behind `--git`, and `--no-git` is withdrawn. The ignore file stays unconditional, because it costs nothing and is right the day the quilt becomes a repository. Both acts are now reported, the ignore file with a line saying what it ignores and why (DR-105).

### After review: the settings panel again, the lines a refusal names, and the quilt a refusal left behind

Three faults found by using the tool, in the order the author reported them.

**The settings panel was still clipping its rows, and its labels sat above them.** The earlier fix stopped the rows wrapping, which was one of two causes. The panel is absolutely positioned inside the settings control, so its containing block is that control — 44px wide in the icon strip — and a shrink-to-fit box is clamped to nearly nothing; the row then overflows the panel and its last option is cut off at the edge. `width: max-content` sizes the panel to its widest row instead, whatever it hangs off. The labels were `<legend>` elements, which a browser always renders above the fieldset's content box however it is displayed, so no fieldset could have put `Shell  [rail] [tabs] [strip]` on one line. Each row is now a grid of a fixed label column and its options. The end-to-end test asserts all three properties: one line per row, the label on that line, and nothing outside the panel's box.

It showed only in the master, which is why the existing test, whose violations are in an included file, never saw it: an included file is copied unchanged. The violations are now found in the author's own text; `--fix-anchoring` still rewrites the staged copy. On the relative localization draft the six reported lines now name exactly the six lines that are wrong.

## Design changes

**The manifest gained a field the plan said Part A would not need.** The plan stated that nothing loom publishes changes and that there would be no manifest change and no interface bump. Half of that held: the interface version is unchanged, because the change is additive. But the contents tree cannot be built correctly without knowing a section's own depth. The inclusion tree nests everything a section contains beneath it, so a `\section` following a `\section` is a tree child of the first while being its outline sibling, and a `\paragraph` unit is indistinguishable from a chapter. Section node entries therefore carry `"level"` (DR-91). Without it the ACGS paper's rail fills with paragraph units and indents them all wrongly.

**The publisher had to change for anchors to exist at all.** The plan put anchors in arras. In fact no fragment had a single `id`, so there was nothing for a link to land on and the viewer could not have been fixed alone. `section`, `div.env` and `details.env-proof` now carry an `id`, their key slugged by the rule display equations already used (DR-92). The dialect specification records it. This also means the publisher's own `\ref` hrefs, which were correct all along, now resolve; the fault the plan attributed to them was in the viewer, which overwrote them with a hash built from the bare label.

**The left panel needed a registry, not just the right rail.** Chapter 15.4 gives the left panel different contents per view: a document's contents in read and graph, a table page's filters elsewhere. The plan provided for a right-rail slot only. A second registry was added, symmetric with the first, so a page still draws no navigation.

**One graph fault was not in the plan.** The layout effect read the state it had just written, which made it depend on itself and re-lay the graph hundreds of times per navigation, blocking the page for five seconds. It was found by an end-to-end test timing out, not by eye, which is the argument for the timing assertions.

**`loom assemble` takes a destination, not a `--to` flag.** Plan 0.2 wrote `loom assemble MASTER --to $LOOM_RUN/<name>.tex` in three places, including the text of the brainstorm mode, which is quoted verbatim into the book. The command has always been `loom assemble MASTER DEST`. Found by running the plan's own use case rather than by reading it. The documentation was corrected to the real signature; the command was not changed, since positional source and destination is the right shape and nothing depends on the flag.

**A file-level `see:` reaches a node's proofs as well as the node.** Scope follows `tags:`, which applies a file-level directive to every node the file defines, and a proof is a node. A relation on a proof key is harmless but says nothing a reader wants, so the fixture declares its relation inside the node rather than at the head of the file. The rule was left as the plan wrote it rather than special-cased, because a rule with one exception is worse than a rule.

**`loom assemble` is not the only place the plan's text was ahead of the code.** See above. Two more surfaced in Part C and Part E.

**A language server needs ranges, and loom was throwing them away.** The plan listed the four loom changes as preparation, which they were, but two of them are not merely preparation: a diagnostic that points at a line rather than at the command is worse for `loom lint` too, and a scan that cannot see an unsaved buffer is the difference between an editor that is useful and one that is a save-and-wait loop. They are recorded as DR-97 rather than as internal details.

**`vscode-languageclient` appends the transport as a flag.** A server it launches over stdio is invoked as `loom-lsp --stdio`. An argument parser that rejects the flag exits 2 before writing a byte, and the editor reports only "server process exited with code 2" with no indication of why. This cost the longest single detour of the execution: the server answered a hand-written `initialize` correctly, answered one spawned from Node correctly, and failed only inside VS Code, which pointed at everything except the argument vector. The server now accepts `--stdio` and ignores it, and a test asserts that it does.

**The extension host does not inherit a shell's `PATH`.** A server living in a virtual environment therefore cannot be found by name, and writing an absolute path into the user's settings from a test is worse than the problem. `LOOM_BIN` and `LOOM_LSP` in the environment override the two path settings. This is how the integration suite names the executables, and it is also the honest answer for anyone launching the editor from a virtual environment.

**A comment's place depends on how much it says.** The chapter put the read view's comments in the shell's right rail. That rail is a third of a screen from the sentence a comment is about, and the author asked for them beside the node instead. A gutter is too narrow for a paragraph, so the rule is by size: a comment whose rendered text and replies run past 220 characters stays in the text as a box below its node, and everything shorter stands in the gutter. The threshold is a constant in the read view with its reason beside it, not a setting.

### Design changes

**Holding the manifest as raw state bought nothing.** The plan expected the deep proxy around a 772 KB manifest to be the cost of table pages. Measured, it made no difference, and a CPU profile showed why: the time was the browser's own layout and the removal of the previous page's DOM, which on the read view is 92,000 elements. The change was reverted. The cost was in the read view's size, which is what batching addresses.

**MathJax's lazy mode was rejected for batches.** Lazy typesetting would have cut the steady-state DOM further, but it leaves every unrendered formula at zero size, so the page moves under a reader scrolling up or following a link into the middle of a document, and Safari does not compensate. Batching from the reader's position, with everything above them typeset before the reveal, gets most of the speed without the movement.

**The layered graph had three faults, not one.** The plan named the coordinate frame. Fixing it showed the edges also ran from user to dependency, which put upstream below despite the chapter, and a section containing drawn nodes was drawn twice. A fourth surfaced from an end-to-end test: after toggling, the page drew layered boxes at the force positions until ELK answered.

**Two faults in the local graph were found only by using it.** The reading follower read the position it wrote inside the effect that started it, which Svelte reports as an update loop, and a preview card opened over the floating panel's own controls; cards from a drawing now open beside it.

**The whole-document typesetting time went up.** Batches yield to the page, so the last formula lands later than a single pass would place it. That is the trade chosen: a reader sees the page three times sooner and can scroll while the rest arrives.

**A quilt not upgraded to 0.5 silently loses its digests.** `demos/relloc` still keeps its digests under `refs/`, which the scanner has skipped entirely since DR-108, so served as it stands it shows every reference undigested and its accepted keys stale with `dependency-removed`. `loom upgrade` fixes it (run on a scratch copy here, not on the demo), but nothing tells the author to run it. This is a loom gap outside this round and is reported rather than fixed.

**Not done: re-vendoring arras into loom.** `loom/scripts/vendor_arras.py` stamps `VERSION` with arras's HEAD commit, and these changes are not committed, so vendoring now would label the new viewer with the old commit. It follows the commit.
